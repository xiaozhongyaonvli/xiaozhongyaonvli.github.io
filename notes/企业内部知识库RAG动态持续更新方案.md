# 企业内部知识库 RAG 的动态持续更新方案

> 最近在做一个日志排查 Agent 项目，里面用了 RAG 来匹配历史故障案例。搭完之后发现一个很现实的问题：知识库不是建好就完事了，故障案例在持续积累、错误码映射在变、排查 SOP 在更新……**怎么让 RAG 知识库跟着业务一起"活"起来**，才是真正的硬仗。研究了一圈，结合项目实际踩的坑记录一下。

## 先说背景：我的 RAG 知识库里存的是什么

这个要先交代一下，因为不同类型的知识内容，更新策略完全不一样。

我们的日志排查 Agent 里，RAG 知识库存三类东西：

| 类型 | 示例 | 特点 |
|------|------|------|
| 历史故障案例 | "2025-11-03，大量用户对话无响应，根因：TTS Pod OOM" | **持续增长**，每次故障复盘后新增 |
| 错误码/业务规则映射 | "错误码 5001 = ASR 模型加载失败" | **偶尔变更**，服务升级时可能改 |
| 排查 SOP | "遇到语音无回复：先查 ASR → 再查 NLU → 最后查 TTS" | **低频更新**，架构调整时才改 |

RAG 提供的是**离线经验知识**，和 MCP 工具调用提供的**实时数据**是两条完全不同的路径。Agent 先通过 RAG 看有没有历史案例可以快速匹配（命中了就不用浪费 Token 去查日志），没命中再通过 MCP 实时查 ELK 日志做推理。

> 所以 RAG 知识库的新鲜度直接影响"快速匹配"的命中率——知识库越新、越全，能短路掉的工单就越多，省时间也省钱。

## 为什么更新这么麻烦？

刚开始我的做法比较粗暴：有新案例就手动跑一遍全量索引。知识量少的时候还好，但随着故障案例越积越多，问题就暴露了：

1. **全量重建太慢**——所有文档重新走一遍 embedding + 入库，越来越耗时
2. **重建期间影响查询**——PGVector 在大量写入时，检索性能会有波动
3. **手动操作容易忘**——故障复盘完了，谁还记得去更新知识库？

看到一个案例挺有共鸣的：某金融公司的 RAG 系统每次加文档要 **14 小时**全量重建，优化成增量更新后缩到了 **8 分钟**。虽然我们的知识库没那么大，但道理是一样的——必须有一套自动化的增量更新机制。

## 两种基本策略

更新策略无非两种：

**全量重建（Full Re-indexing）**
- 所有文档重新走：摄取 → 分块 → embedding → 入库
- 优点：简单，数据一定是最新的
- 缺点：慢，费 embedding API 调用
- 适合：知识量小（几百条以内）、或换了 embedding 模型需要全部重新生成

**增量更新（Incremental Update）**
- 只处理**新增、修改、删除**的部分
- 优点：快，资源省，处理时间减少约 70%
- 缺点：实现复杂，需要可靠的变更检测
- 适合：知识持续积累、更新频繁的场景

实际中我们是**两者结合**：日常走增量更新，每月跑一次全量重建兜底确保一致性。

## 结合项目：三类知识的更新策略各不同

这是我觉得比较有价值的一个思考——**不同类型的知识，更新触发方式和频率完全不一样**，不能一刀切。

### 历史故障案例：事件驱动，复盘后自动入库

这是更新最频繁的一类。每次线上故障复盘后，都会产生新的案例。

```
故障复盘文档（人工编写）
        ↓
格式化提取（脚本自动）: 现象 / 根因 / 排查过程 / 解决方案
        ↓
Embedding 编码 → 768维向量（bge-base-zh-v1.5）
        ↓
写入 PGVector（content + embedding + metadata）
        ↓
metadata 包含：故障时间、涉及服务、严重等级（用于检索时过滤）
```

关键设计：
- 一条案例 = 一个 chunk，**不做切分**。因为案例本身就不长（200-500 字），切分反而会破坏因果链的完整性
- metadata 里带上服务名和严重等级，检索时可以用这些字段做过滤，提高精度

> 还有一个来源：线上反馈闭环。研发用完 Agent 给的结论后会点 👍/👎，标记为"结论错误"的 bad case 进入复盘队列。复盘后如果发现是新的故障模式，就补充进知识库。这条路是自动触发的，不需要人记着去更新。

### 错误码映射：随服务版本更新

错误码这类知识相对稳定，但服务升级时可能新增或修改。

```
错误码 5001 | 服务：ASR | 含义：ASR 模型加载失败 |
常见原因：模型文件损坏或路径配置错误 | 建议：检查模型路径配置
```

- 同样是一条映射 = 一个 chunk
- 更新触发：服务发版时，CI/CD 流水线里加一步——diff 错误码定义文件，有变更就自动触发知识库更新
- 低频但要可靠，不能漏

### 排查 SOP：手动维护，审核后入库

SOP 是最严肃的一类知识，不能随便改。通常是架构调整（比如新增了一个微服务）后，由有经验的研发更新。

- 一份 SOP = 一个 chunk（不超过 1000 字的话）
- 更新流程：人工编辑 → 审核 → 手动触发入库
- 频率最低，但影响最大

## 变更检测怎么做

知道了"什么时候该更新"，接下来是"怎么知道具体哪些内容变了"。

### 方案一：内容哈希比对（我们主要用的）

给每条知识算一个 SHA-256 哈希，存到元数据表里。更新时重新算哈希比对。

```python
import hashlib

def compute_doc_hash(content: str) -> str:
    return hashlib.sha256(content.encode('utf-8')).hexdigest()

def detect_changes(new_docs, metadata_registry):
    to_add, to_update, to_delete = [], [], []

    for doc in new_docs:
        new_hash = compute_doc_hash(doc.content)
        existing = metadata_registry.get(doc.id)

        if existing is None:
            to_add.append(doc)          # 新增
        elif existing.content_hash != new_hash:
            to_update.append(doc)       # 修改

    # 注册表里有但新列表里没有的 → 已删除
    existing_ids = set(metadata_registry.keys())
    new_ids = set(d.id for d in new_docs)
    for doc_id in existing_ids - new_ids:
        to_delete.append(doc_id)

    return to_add, to_update, to_delete
```

对于我们的场景，故障案例基本只有"新增"操作（历史案例不会改），错误码和 SOP 才有"修改"。所以哈希比对足够用了。

### 方案二：Webhook / CDC 集成

如果知识源头是 Confluence、飞书文档这类平台，可以直接用 Webhook 拿变更通知；数据库类的知识源可以用 CDC（比如 PostgreSQL 的 logical replication）实时捕获变更。

> 不过说实话，我们的场景用不到这么重的方案。故障案例是脚本从复盘文档提取后入库的，错误码映射跟着 CI/CD 走，触发链路很明确，不需要额外的变更检测机制。CDC 更适合知识来源分散、更新路径不可控的场景。

## 元数据注册表：增量更新的基石

不管用哪种变更检测方案，都需要一张表追踪已索引知识的状态：

| 字段 | 说明 | 示例 |
|------|------|------|
| doc_id | 知识条目唯一标识 | `case_20251103_tts_oom` |
| doc_type | 知识类型 | `fault_case` / `error_code` / `sop` |
| content_hash | 内容哈希 | `a3f2b8c...` |
| service_name | 关联服务 | `tts` / `asr` / `nlu` |
| severity | 严重等级（案例用） | `high` / `medium` / `low` |
| version | 版本号 | `1` |
| ingested_at | 入库时间 | `2025-11-04 10:00:00` |
| chunk_id | PGVector 中的向量 ID | `vec_case_001` |
| status | 状态 | `active` / `archived` |

这张表在 PGVector 同一个 PostgreSQL 实例里就能建，不用额外引入存储。

## 文档更新的三种操作

### 新增（最常见）

对我们来说就是"新故障案例入库"，流程很直接：

1. 脚本从复盘文档提取结构化内容
2. bge-base-zh-v1.5 编码成 768 维向量
3. 批量写入 PGVector（content + embedding + metadata）
4. 元数据注册表登记

注意用**批量插入**，别一条一条塞。攒够一批再写，效率高很多。

### 修改（偶尔发生）

比如某个错误码的含义改了。这个稍微复杂：

```python
def handle_doc_update(doc, vector_store, registry):
    # 1. 删除旧向量
    old_chunk_id = registry.get_chunk_id(doc.id)
    vector_store.delete(ids=[old_chunk_id])

    # 2. 重新编码
    new_embedding = embedding_model.encode(doc.content)

    # 3. 插入新向量（带元数据）
    vector_store.upsert(
        ids=[f"{doc.id}_v{doc.version + 1}"],
        embeddings=[new_embedding],
        metadatas=[{
            "doc_id": doc.id,
            "doc_type": doc.type,
            "service_name": doc.service,
            "version": doc.version + 1
        }]
    )

    # 4. 更新注册表
    registry.update(doc.id,
                    content_hash=compute_doc_hash(doc.content),
                    version=doc.version + 1)
```

（因为我们是一条知识 = 一个 chunk，所以不存在"分块数变了"的问题，处理起来比一般的长文档 RAG 简单不少）

### 删除（很少发生）

找到关联的向量 ID，从 PGVector 删除，注册表标记为 archived。建议**软删除**，保留一段时间再物理清除。

## 关键坑：分块策略和 Embedding 模型的一致性

这块单独拎出来说，因为踩过。

### 分块策略必须一致

我们的分块策略是**按语义单元**，不是固定长度切分：
- 故障案例 → 整条存，不切
- 错误码映射 → 单条存
- 排查 SOP → 按完整文档存（太长就按步骤段落切，保留标题上下文）

> 为什么不用固定长度（比如 512 token）？因为我们的知识条目本身就不长，是结构化的短条目，按语义单元切分检索精度更高。固定长度切分会把一个完整的故障因果链切断。

增量更新时，**新入库的知识必须沿用同样的分块策略**。如果哪天想换策略，那就必须全量重建。

### 换 Embedding 模型 = 全量重建

我们用的是 **bge-base-zh-v1.5**（768 维），部署在内网——因为日志内容不能出公网，不能用 OpenAI 的 text-embedding。

一旦要换 embedding 模型（哪怕同模型的新版本），所有向量都必须重新生成。因为不同模型产生的向量空间是不一样的，新旧向量混在一起检索效果会严重下降。

> 把 embedding 模型变更当成数据库 schema 迁移来对待——要有计划、有灰度、能回滚。

## 版本管理：给自己留条后路

更新出了问题怎么办？必须有回滚机制。

**文档级版本**
- 每条知识带版本号，向量 metadata 里也带 version
- 出问题时按版本回退

**快照版本**
- 每次批量更新前，保存元数据注册表快照
- 回滚时恢复快照，按快照信息重建向量

**命名空间隔离**（PGVector 可以用不同的 collection）
- 新版本写到新 collection，验证没问题后切换查询指向
- 类似蓝绿部署的思路

```
PGVector
  knowledge_v3 (当前线上)
  knowledge_v4 (更新中/测试中)
  knowledge_v2 (保留用于回滚，7-14 天后清理)
```

> 对于我们的场景，文档级版本就够了。故障案例基本只增不改，回滚需求不大。命名空间隔离更适合那种不能有任何服务中断的严肃场景。

## 异步处理：别阻塞 Agent 的查询服务

知识库更新不应该卡住 Agent 的正常排查服务。用异步队列解耦：

```
故障复盘完成 / CI 触发 / 手动触发
        ↓
  消息队列（Redis / RabbitMQ）
        ↓
  消费者：解析 → embedding → 写入 PGVector → 更新注册表
        ↓
  Agent 查询服务不受影响（PGVector 读写分离或新数据渐进可见）
```

一些性能参考数据：

| 优化手段 | 效果 |
|---------|------|
| 异步处理队列 | 入库延迟 2-5 分钟（可接受） |
| 并行 Embedding 生成 | 批量处理 100 条从 8 分钟降到 90 秒 |
| Embedding 缓存（相同内容跳过） | 成本降低 40%，速度提升 30% |
| 批量写入 PGVector | 比逐条快 6 倍 |

## 和 Agent 查询侧的联动：自适应 RAG

知识库更新做好了还不够，Agent 查询侧也要能**自适应**地利用最新的知识。我们的 RAG 节点设计了一个"路由-检索-评估-重写"的闭环：

```
用户异常描述
    ↓
路由判断：需不需要走 RAG？（明确的操作指令就不走）
    ↓
PGVector 向量检索（top_k=5, threshold=0.7）
    ↓
相关性评估（LLM 打分）
    ↓
confidence > 0.85 → 直接返回历史案例结论（短路，省掉后续所有查询）
confidence 0.5~0.85 → 作为辅助 context，继续走 Pipeline 查日志
confidence < 0.5 → 重写 Query 再检索一次（最多重试 2 次）
```

这个闭环和知识库更新的关系是：**知识库越全、越新 → 高置信度命中率越高 → 更多工单在 RAG 阶段就短路 → 省 Token、省时间**。

反过来，如果知识库不更新，新出现的故障模式在 RAG 阶段永远命中不了，只能走到 ReAct 动态推理去消耗大量 Token。

> 这也是为什么我们要在线上反馈闭环里把 bad case 自动收集回来——研发点了 👎 的 case 进入复盘队列，复盘后新案例入库，下次同样的故障 RAG 就能命中了。

## 线上反馈驱动的知识库更新闭环

这块我觉得是整个方案里最有价值的部分——**不是靠人记着去更新知识库，而是靠线上反馈自动驱动**。

```
Agent 输出排查结论
        ↓
研发点击 👍（正确）或 👎（错误，填写实际根因）
        ↓
👍 的 case → 如果是 ReAct 推理出来的新结论
               → 自动提取为候选案例 → 人工审核 → 入库

👎 的 case → 进入"待复盘"队列
               → 定期批量分析 bad case
               → 补充/修正知识库
               → 跑回归测试确认检索质量没退步
               → 灰度上线
```

关键点：
- **ReAct 推理成功的新 case 也要回流**——Agent 通过多轮推理定位到了一个新的故障模式，这个结论经过验证后就该入库，下次同样的问题 RAG 直接命中
- **回归测试不能少**——每次更新知识库后，跑一组标准测试 query（10-20 个），确保检索质量没有退化
- **审核环节必须有**——不能把所有 ReAct 结论都直接灌进知识库，万一是幻觉呢

## 监控指标

上线后要盯的几个关键数字：

- **RAG 命中率**：高置信度命中（直接短路）的比例，这个数字越高说明知识库越有效
- **知识库覆盖度**：线上出现的故障模式中，有多少能在知识库里找到相似案例
- **入库延迟**：从故障复盘完成到新案例可检索的时间差
- **检索质量回归**：每次更新后标准测试 query 的结果有没有变差
- **Embedding 成本**：bge-base-zh-v1.5 虽然是自部署不花钱，但如果用商业 API 这块容易超预算

## 整体架构

把上面的东西拼起来：

```
知识来源层
  故障复盘文档 / CI/CD 错误码 diff / SOP 手动更新 / 线上反馈
  （脚本提取 / 流水线触发 / 审核后触发 / 自动收集）
        ↓
变更检测 & 预处理
  格式化提取 → 内容哈希比对 → 生成变更清单（新增/修改/删除）
        ↓
异步处理队列 (Redis)
        ↓
Embedding & 入库
  bge-base-zh-v1.5 编码(768维) → 批量写入 PGVector → 更新注册表
        ↓                            ↓
PGVector 向量库               元数据注册表
(IVFFlat / cosine)           (同 PostgreSQL 实例)
        ↓
日志排查 Agent（自适应 RAG 检索）
  路由 → 检索 → 评估 → 重写闭环 → 命中则短路，未命中走 Pipeline
```

## 踩坑记录

几个实际遇到或差点踩的坑：

- **故障案例别切分**：一开始想把案例也按 512 token 切块，后来发现切完之后"根因"和"现象"分到两个 chunk 里了，检索只命中半截，结论不完整。改成整条存就好了
- **多角度描述提升召回率**：同一个故障，不同人的描述方式差别很大。"TTS Pod OOM" / "语音合成内存溢出" / "TTS 模型加载内存不足"——RAG 可能只对其中一种表述有高相似度。解决方法是一条案例存多个描述角度，或者在 RAG 评估不通过时用 LLM 重写 Query 再检索
- **相似度阈值别定太高**：一开始设 0.8，很多语义相近但措辞不同的案例检索不到。调到 0.7 之后命中率明显提升，也没引入太多噪音（因为后面还有 LLM 评估兜底）
- **回归测试必须做**：有一次更新了几十条新案例，结果检索排序变了，原来能命中的老 case 反而排到后面了。之后每次更新都跑一遍标准测试 query 确认

## 小结

企业知识库 RAG 的持续更新，核心就三件事：**知道什么变了**（变更检测）、**安全地更新**（版本管理 + 异步解耦）、**更新后验证**（回归测试 + 监控）。

但如果只做到这三点，知识库还是被动的——有人记着更新才会更新。真正让知识库"活"起来，靠的是**线上反馈驱动的闭环**：Agent 排查 → 研发反馈 → bad case 复盘 → 新案例入库 → 下次命中。这样知识库就跟着业务一起成长了，不需要专门的人去维护。

从简单方案开始就好，不用一步到位。我们一开始就是手动跑脚本入库的，后来工单多了才加了异步队列和自动反馈收集。过早优化是万恶之源嘛。
