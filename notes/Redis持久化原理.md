# Redis 持久化这块，真得好好搞明白

> 最近重新梳理了一遍 Redis 持久化机制，之前只知道 RDB 和 AOF 两种，用的时候也没深究过配置项到底啥意思。这次认真看了一圈源码分析和官方文档，发现里面门道还挺多的，特别是 fork + COW 这块，之前理解得太浅了。

## 为啥 Redis 需要持久化？

这个其实很好理解 —— Redis 数据全在内存里，机器一重启数据就没了。生产环境你总不能跟老板说"不好意思数据没了"吧……

所以 Redis 提供了持久化机制，目前主要三种方式：

- **RDB**（Redis Database）：定时快照，把某一时刻的内存数据 dump 成二进制文件
- **AOF**（Append Only File）：操作日志，把每个写命令追加到文件里
- **混合持久化**（Redis 4.0+）：RDB + AOF 的结合体

下面一个一个说。

## 一、RDB 快照持久化

### 基本原理

RDB 的思路很直接：定时把内存里的数据拍个"快照"，保存成一个 `dump.rdb` 文件。恢复的时候直接加载这个文件就行。

触发快照有两种命令：

- `SAVE`：在主线程里执行，**会阻塞所有客户端请求**（生产环境别用这个）
- `BGSAVE`：fork 一个子进程去干活，主线程继续服务（推荐）

还有自动触发的配置，在 `redis.conf` 里：

```conf
save 900 1      # 900秒内至少1个key变了，就触发快照
save 300 10     # 300秒内至少10个key变了
save 60 10000   # 60秒内至少10000个key变了
```

我理解的是，这几个条件是**或**的关系，满足任何一个就触发。如果想关掉 RDB，直接写 `save ""` 就行。

### fork + COW —— 这块是重点

刚开始我一直有个疑问：BGSAVE 的时候子进程要遍历整个内存去写文件，那这期间主线程还在处理写请求，数据不会乱吗？

答案就是 **写时复制（Copy-on-Write，COW）**，这是操作系统层面的机制：

1. 主进程调用 `fork()` 创建子进程
2. fork 的时候**不会真的复制物理内存**，子进程只是拿到了父进程的页表（虚拟地址 → 物理地址的映射）
3. 父子进程共享同一份物理内存，内核把所有内存页标记为**只读**
4. 子进程开始遍历内存，写入 RDB 文件
5. 如果这时候主进程收到写请求要改某个 key，就会触发**缺页异常**
6. 内核拦截到这个异常，把被修改的那个内存页复制一份给主进程用，子进程还是读原来的
7. 这样子进程写出来的就是 fork 那一刻的数据快照，不受后续写操作影响

画个图大概是这样：

```
fork() 之后：
                        物理内存页
父进程页表 →  [Page A] [Page B] [Page C]
子进程页表 →  [Page A] [Page B] [Page C]  (共享同一份物理页)

主进程修改 Page B 后：

父进程页表 → [Page A]  [Page B'] (新副本)  [Page C]
子进程页表 → [Page A]  [Page B] (原始数据)  [Page C]
```

注意这里复制是**以内存页（4KB）为单位**的，不是复制整个内存，所以开销可控。

> 这也解释了为啥 Redis 用子进程而不是子线程来做持久化 —— 线程共享内存空间，没法利用 COW，还得加锁，性能肯定差。

### RDB 的配置全貌

```conf
# 快照触发条件
save 900 1
save 300 10
save 60 10000

# RDB 文件名和目录
dbfilename dump.rdb
dir /var/lib/redis/

# bgsave 出错时停止写入（默认 yes，建议保持）
stop-writes-on-bgsave-error yes

# 压缩 RDB 文件（默认 yes，用 LZF 压缩，CPU 换空间）
rdbcompression yes

# 加载时做 CRC64 校验（默认 yes）
rdbchecksum yes
```

### RDB 优缺点

| 优点 | 缺点 |
|------|------|
| 文件紧凑，适合备份和灾备 | 两次快照之间的数据可能丢失（分钟级） |
| 恢复速度快（直接加载二进制文件） | 数据集大时 fork 会有短暂阻塞 |
| 对日常性能影响小 | 文件是二进制的，没有可读性 |

## 二、AOF 追加日志持久化

### 基本原理

AOF 的思路和 RDB 完全不同：它不存数据，而是**记操作**。每次执行写命令，Redis 就把这条命令追加到 AOF 文件末尾。恢复数据的时候，把 AOF 文件里的命令重新执行一遍就行了。

有个细节值得注意：Redis 的 AOF 是**写后日志**，也就是先执行命令、数据写入内存，然后才记录日志。这样做的好处是不用做语法检查（执行成功了才记），坏处是如果刚执行完还没来得及写日志就宕机了，这条数据就丢了。

### AOF 的三步流程

```
客户端写命令 → Redis 执行命令 → 追加到 AOF 缓冲区 → 写入 AOF 文件 → fsync 同步到磁盘
```

其中最关键的是 **fsync 策略**，决定了数据安全性和性能的平衡：

```conf
# 开启 AOF
appendonly yes
appendfilename "appendonly.aof"

# fsync 策略（三选一）
# appendfsync always    # 每次写操作都 fsync，最安全，但最慢
# appendfsync everysec    # 每秒 fsync 一次（推荐，最多丢 1 秒数据）
# appendfsync no        # 让操作系统决定什么时候刷盘，性能最好但最不安全
```

我一般用 `everysec`，算是安全性和性能之间的甜点。

### AOF 重写（Rewrite）—— 不搞懂这个迟早踩坑

AOF 有个天然的问题：文件会越来越大。比如你对同一个 key 执行了 100 次 `INCR`，AOF 文件里就有 100 条记录，但其实一条 `SET key 100` 就够了。

所以 Redis 有个 **AOF 重写** 机制，把 AOF 文件"瘦身"：

**手动触发**：执行 `BGREWRITEAOF` 命令

**自动触发**：靠两个配置项控制：

```conf
auto-aof-rewrite-percentage 100   # AOF 文件比上次重写后大了 100%，触发重写
auto-aof-rewrite-min-size 64mb    # AOF 文件最小达到 64MB 才考虑重写
```

**两个条件必须同时满足**才会触发。举个例子：
- 第 1 次重写：AOF 长到 64MB 时触发，重写后假设变成 40MB
- 第 2 次重写：从 40MB 涨到 80MB（翻倍了），触发
- 第 3 次重写：从 80MB 涨到 160MB，触发
- 以此类推...

重写的过程也是 fork 子进程来做的，跟 BGSAVE 类似。但有个额外的机制：重写期间主进程的新写命令会同时写到 **AOF 缓冲区** 和 **AOF 重写缓冲区**，等子进程写完新 AOF 文件后，再把重写缓冲区的内容追加上去，最后原子替换旧文件。这样就不会丢数据。

### AOF 优缺点

| 优点 | 缺点 |
|------|------|
| 数据安全性高（最多丢 1 秒） | 文件比 RDB 大 |
| 文件是文本格式，可读可修复 | 恢复速度比 RDB 慢（要重放命令） |
| append 模式，宕机不会损坏已有内容 | 写入有额外开销（fsync） |

## 三、混合持久化（Redis 4.0+）

这个其实是我觉得最优雅的方案。

### 原理

混合持久化在 AOF 重写的时候，不再是把内存数据转成一条条命令了，而是：

1. **前半段**：把当前内存数据按 RDB 格式写入（快！）
2. **后半段**：把重写期间产生的新写命令按 AOF 格式追加

这样得到的 AOF 文件 = RDB 快照 + 增量 AOF 命令。恢复的时候先加载 RDB 部分（快），再重放 AOF 部分（少量命令），兼具了两者的优点。

```conf
# 开启混合持久化（Redis 4.0+，5.0 以后默认开启）
aof-use-rdb-preamble yes
```

### 混合持久化就这么完美吗？

也不是。缺点是 AOF 文件的前半段是二进制 RDB 格式，可读性差了，没法像纯 AOF 那样直接看到操作记录。不过在我看来这不算大问题，毕竟谁也不会闲着去手读 AOF 文件（笑）。

## 踩坑记录

整理几个我自己遇到过的，或者看别人踩过的坑：

### 坑 1：fork 阻塞导致请求超时

数据量大的时候（比如 10GB+），`fork()` 虽然不复制物理内存，但要**复制页表**，这个过程是阻塞的。数据量越大，页表越大，阻塞时间越长。

> 在一台 8GB 数据量的 Redis 实例上，fork 耗时大概 200-300ms。如果你的超时设置比较敏感（比如 100ms），那在 BGSAVE 或 AOF 重写的瞬间就可能出现请求超时。

**解决方案**：
- 尽量让 Redis 数据量控制在合理范围（单实例建议不超过 10GB）
- 使用大页内存（Huge Pages）可能会让 COW 复制更重，建议关闭 Transparent Huge Pages

### 坑 2：AOF 文件损坏导致 Redis 启动失败

如果 Redis 写 AOF 的时候突然断电，AOF 文件末尾可能会有不完整的命令。重启 Redis 时就会报错拒绝启动。

**解决方案**：
```bash
# 用 redis-check-aof 工具修复
redis-check-aof --fix appendonly.aof
```

另外配置 `aof-load-truncated yes`（默认就是 yes），可以让 Redis 在加载时自动忽略末尾不完整的命令。

### 坑 3：RDB 和 AOF 都开了，到底用哪个恢复？

**答案：优先用 AOF。** 因为 AOF 的数据通常比 RDB 更完整。Redis 启动时的逻辑是：如果 AOF 开启了就用 AOF 恢复，不管 RDB 文件在不在。

## 小结

| 方案 | 适用场景 |
|------|----------|
| 只用 RDB | 纯缓存场景，丢几分钟数据无所谓 |
| 只用 AOF | 对数据安全要求高，能接受恢复稍慢 |
| 混合持久化 | **推荐**，兼顾恢复速度和数据安全 |
| 都关掉 | 纯缓存 + 数据可以从 DB 重建 |

我自己的项目里基本都用混合持久化，`aof-use-rdb-preamble yes` + `appendfsync everysec`，恢复快数据也不怎么丢。如果是纯缓存场景那就无所谓了，关掉也行。
