# 乐观锁与悲观锁 — 一次搞清楚它们的区别和用法

> 并发编程绕不开锁，最近把乐观锁和悲观锁这块重新梳理了一遍，发现之前理解得不够透彻，这里记录一下。

## 先说核心思想

其实乐观锁和悲观锁并不是某种具体的锁实现，而是两种**并发控制的思想**。这个之前一直没太注意，总觉得它们是某种具体的技术，后来才意识到它更像是一种策略。

**悲观锁**：就是比较"悲观"，每次去操作数据的时候都觉得别人会来修改，所以操作之前先把数据锁住，别人想动就得排队等着。用完了才释放锁。

**乐观锁**：相反，比较"乐观"，觉得一般不会有冲突，所以不加锁直接操作。等到要提交更新的时候再去检查一下这段时间有没有人改过数据，如果没人动过就更新成功，有人改过就放弃或者重试。

> 一句话总结：悲观锁是"先加锁再操作"，乐观锁是"先操作再验证"。

## 悲观锁的实现

悲观锁在 Java 和数据库里都有对应的实现。

### Java 层面

最常见的就是 `synchronized` 和 `ReentrantLock`：

```java
// synchronized 方式
public synchronized void updateCount() {
    // 同一时刻只有一个线程能进来
    this.count++;
}

// ReentrantLock 方式
private final ReentrantLock lock = new ReentrantLock();

public void updateCount() {
    lock.lock();
    try {
        this.count++;
    } finally {
        lock.unlock();  // 一定要在 finally 里释放，不然死锁就惨了
    }
}
```

（`ReentrantLock` 比 `synchronized` 灵活一些，支持公平锁、可中断、超时等特性，不过一般场景 `synchronized` 就够用了）

### MySQL 层面

用 `SELECT ... FOR UPDATE` 加排他锁：

```sql
-- 开启事务
BEGIN;

-- 查询并加排他锁，其他事务想改这行数据就得等着
SELECT * FROM product WHERE id = 1 FOR UPDATE;

-- 执行更新
UPDATE product SET stock = stock - 1 WHERE id = 1;

COMMIT;
```

这里有个容易踩的坑：**`FOR UPDATE` 走不走索引很关键**。InnoDB 默认是行级锁，但如果查询条件没有用到索引，就会退化成表级锁，直接把整张表锁住，性能会非常差。之前在项目里遇到过一次，排查了好久才发现是索引的问题...

## 乐观锁的实现

乐观锁主要有两种实现：**版本号机制**和 **CAS**。

### 版本号机制

思路很直观 — 给数据表加一个 `version` 字段：

```sql
-- 1. 先查出数据和版本号
SELECT stock, version FROM product WHERE id = 1;
-- 假设查出来 stock=10, version=3

-- 2. 更新时带上版本号条件
UPDATE product SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 3;

-- 如果 affected rows = 0，说明别人已经改过了，需要重试
```

这个方案简单好理解，而且不需要加锁，适合大部分业务场景。除了 version 字段，用时间戳也可以达到类似效果，不过 version 更常用。

如果用 MyBatis-Plus 的话就更方便了，它有现成的乐观锁插件：

```java
// 1. 实体类加 @Version 注解
@Data
public class Product {
    private Long id;
    private Integer stock;
    @Version
    private Integer version;
}

// 2. 配置乐观锁插件
@Configuration
public class MybatisPlusConfig {
    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
        return interceptor;
    }
}

// 3. 使用时自动带上 version 条件
Product product = productMapper.selectById(1L);
product.setStock(product.getStock() - 1);
productMapper.updateById(product); // MP 自动加 WHERE version = ?
```

### CAS（Compare And Swap）

CAS 是 CPU 层面支持的原子操作，核心逻辑就三个值：

- **V**：内存中的值
- **A**：预期的旧值
- **B**：要更新的新值

只有当 V == A 时，才把 V 更新为 B，否则不操作。整个过程是原子性的，由硬件保证。

Java 里 `java.util.concurrent.atomic` 包下的原子类都是基于 CAS 实现的：

```java
AtomicInteger count = new AtomicInteger(0);

// 原子自增，底层就是 CAS
count.incrementAndGet();

// 也可以手动 CAS
boolean success = count.compareAndSet(0, 1);
// 如果当前值是 0 就改成 1，返回 true；否则返回 false
```

看了下 `AtomicInteger` 的源码，它内部用的是 `Unsafe` 类的 `compareAndSwapInt` 方法，这个方法是 native 的，直接调用 CPU 指令。

## CAS 的 ABA 问题

CAS 有个经典问题 — **ABA 问题**，刚开始学的时候没太当回事，后来想了想还是有必要了解一下。

简单说就是：

1. 线程 1 读取值 A
2. 线程 2 把 A 改成 B，又改回 A
3. 线程 1 做 CAS，发现还是 A，以为没人动过，操作成功

虽然值看起来没变，但中间其实被改过了。大多数场景下这不是问题，但在某些情况下（比如链表操作）可能会出 bug。

解决方案是加个**版本号/标记**，Java 提供了 `AtomicStampedReference`：

```java
// 初始值 "A"，初始版本号 1
AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 1);

int stamp = ref.getStamp(); // 获取当前版本号
String value = ref.getReference(); // 获取当前值

// CAS 时同时比较值和版本号
ref.compareAndSet(value, "B", stamp, stamp + 1);
// 即使值被改回了 "A"，版本号对不上也会失败
```

> 本质上就是给 CAS 也加了版本号机制，跟数据库乐观锁的 version 字段是一个思路。

## CAS 自旋的问题

还有一个容易忽略的点：CAS 失败后通常会**自旋重试**（循环尝试），如果竞争非常激烈，线程会一直在那空转，CPU 直接飙上去。

JDK 8 引入的 `LongAdder` 就是为了解决这个问题的，它把一个值拆成多个 Cell，不同线程操作不同的 Cell，最后汇总，减少了竞争。高并发计数场景用 `LongAdder` 比 `AtomicLong` 性能好很多。

## 怎么选？

这块其实不复杂，记住一个原则就行：

| 场景 | 推荐 | 原因 |
|------|------|------|
| **读多写少** | 乐观锁 | 冲突少，不加锁省开销 |
| **写多读少** | 悲观锁 | 冲突多，乐观锁重试成本太高 |
| **竞争激烈** | 悲观锁 | 避免大量自旋浪费 CPU |
| **竞争不激烈** | 乐观锁 | 无锁操作吞吐量高 |

举几个实际例子：

- **商品详情页浏览量统计**：典型的读多写少，用乐观锁（或者 `AtomicLong`）
- **秒杀扣库存**：竞争激烈的写操作，用悲观锁（`SELECT FOR UPDATE` 或 Redis 分布式锁）
- **用户更新个人信息**：冲突概率低，版本号乐观锁就够了
- **银行转账**：数据一致性要求高，必须悲观锁

## 踩坑 / 易错点

- **FOR UPDATE 没走索引**：前面提到了，会退化成表锁，切记检查 WHERE 条件有没有命中索引
- **乐观锁重试次数**：用版本号乐观锁记得设置最大重试次数，不然极端情况下会一直失败一直重试
- **synchronized 和 ReentrantLock 选谁**：一般优先 `synchronized`（JVM 做了很多优化，够用了），需要高级特性时再用 `ReentrantLock`
- **CAS 只能保证单个变量的原子性**：如果要同时更新多个变量，CAS 搞不定，还是得用锁

## 小结

悲观锁和乐观锁本质上是两种并发控制策略，不是非此即彼的关系。实际开发中完全可以结合使用，比如在数据库层用乐观锁（version），在应用层用悲观锁（synchronized）来保护临界区。选哪个主要看业务场景的读写比例和冲突频率，没有绝对的好坏之分。
