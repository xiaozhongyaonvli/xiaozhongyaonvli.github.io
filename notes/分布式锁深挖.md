# 分布式锁深挖：从原理到踩坑，一次性搞透

> 最近项目里用到了分布式锁，之前只停留在"用 Redis 的 SETNX"这个层面，这次花时间把加锁、解锁、续约、误删、竞争、事务这些问题都捋了一遍。发现水挺深的，很多细节不注意就是线上事故。

## 为什么需要分布式锁？

单机环境下，用 `synchronized` 或 `ReentrantLock` 就能搞定并发问题。但在分布式场景下，多个 JVM 进程各玩各的，本地锁根本管不到别的机器上的线程。

举个最典型的场景——**库存扣减**：

```
用户A（服务实例1）：查库存=10 → 扣减 → 更新为9
用户B（服务实例2）：查库存=10 → 扣减 → 更新为9   // 也读到了10！
```

两个人各买一件，库存应该变成 8，结果变成了 9。这就是经典的并发超卖问题，必须用分布式锁来解决。

一个合格的分布式锁至少要满足：
- **互斥性**：同一时刻只有一个客户端能持有锁
- **不能死锁**：即使持锁的节点挂了，锁也要能自动释放
- **解铃还须系铃人**：谁加的锁只能谁来解

## 加锁：从 SETNX 到 SET NX EX

### 最原始的方式（有坑，别用）

```bash
SETNX lock_key unique_value   # 加锁
EXPIRE lock_key 30            # 设置过期时间
```

问题在于这是**两条命令，不是原子操作**。如果 SETNX 成功了但还没来得及 EXPIRE 节点就挂了，这把锁就永远不会过期——死锁了。

### 正确姿势：一条命令搞定

```bash
SET lock_key unique_value NX EX 30
```

- `NX`：key 不存在才设置（互斥）
- `EX 30`：30 秒过期（防死锁）
- `unique_value`：一般用 UUID + 线程ID，标识锁的持有者

对应到 Java 代码：

```java
// 加锁
String uniqueValue = UUID.randomUUID().toString() + ":" + Thread.currentThread().getId();
Boolean success = redisTemplate.opsForValue()
    .setIfAbsent("lock:order:" + orderId, uniqueValue, 30, TimeUnit.SECONDS);

if (Boolean.TRUE.equals(success)) {
    try {
        // 业务逻辑...
    } finally {
        // 解锁（这里也有坑，后面说）
    }
}
```

> 这里的 `unique_value` 非常关键，后面"误删"那块会讲为什么。

## 解锁：必须用 Lua 脚本

你可能会觉得解锁不就是 `DEL` 嘛，有什么好说的？问题是，你得**先判断这把锁是不是自己的，然后再删除**——这两步必须是原子的。

### 错误的解锁方式

```java
// 不要这样写！！
String value = redisTemplate.opsForValue().get("lock:order:" + orderId);
if (uniqueValue.equals(value)) {
    // ⚠️ 就在这个间隙，锁可能恰好过期了，被别人拿到了
    redisTemplate.delete("lock:order:" + orderId);  // 删掉了别人的锁！
}
```

GET 和 DEL 之间不是原子的，可能你判断完"是我的锁"之后，锁恰好过期、被另一个线程抢到了，你再 DEL 就把人家的锁给删了。

### 正确方式：Lua 脚本保证原子性

```lua
-- unlock.lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

Redis 执行 Lua 脚本是原子的，判断和删除在一个操作里完成，不会被打断。

```java
// Java 调用 Lua 脚本解锁
String luaScript =
    "if redis.call('GET', KEYS[1]) == ARGV[1] then " +
    "   return redis.call('DEL', KEYS[1]) " +
    "else " +
    "   return 0 " +
    "end";

DefaultRedisScript<Long> script = new DefaultRedisScript<>(luaScript, Long.class);
Long result = redisTemplate.execute(script,
    Collections.singletonList("lock:order:" + orderId), uniqueValue);
// result == 1 表示解锁成功，0 表示锁不是自己的
```

（Redis 8.4 引入了 `DELEX` 命令可以原子地做条件删除，但目前大部分生产环境还是 Lua 脚本的方案）

## 锁误删：到底怎么发生的？

这个问题刚学的时候我觉得"不会吧，谁会删别人的锁"，但仔细想想还真容易出问题。看这个时序：

```
时间线 →

线程A：  [拿到锁] → [业务执行很慢...] → [执行DEL] ← 删了线程B的锁！
锁状态：  [lock=A]   30秒到期自动释放    [lock=B]
线程B：                              [拿到锁] → [业务执行中...] → [锁没了??]
```

1. 线程 A 拿到锁，开始干活
2. 业务逻辑执行太久，超过 30 秒，**锁自动过期了**
3. 线程 B 趁机拿到了锁
4. 线程 A 终于干完活了，执行 DEL——**把线程 B 的锁删了**
5. 线程 C 又拿到锁，现在 B 和 C 同时在跑——并发问题又出来了

这就是为什么要用 `unique_value` + Lua 脚本：删之前先验证"这把锁到底是不是我的"。

> 不过即使解决了误删，还有一个更根本的问题：**线程 A 的锁过期了但业务还没跑完，这本身就已经破坏了互斥性**。光靠 unique_value 只能避免误删，不能避免"两个线程同时在临界区里"这个事实。这就需要续约机制了。

## 超时续约：Watchdog 看门狗

手动设置过期时间，太短了怕业务没跑完锁就没了，太长了节点挂了得等很久才能释放。怎么办？

Redisson 的 **Watchdog（看门狗）** 机制就是来解决这个问题的。

### 原理

1. 加锁时默认设置 30 秒过期（`lockWatchdogTimeout`）
2. 同时启动一个后台定时任务，每隔 `30 / 3 = 10 秒`检查一次
3. 如果发现当前线程还持有锁，就把过期时间**重新续到 30 秒**
4. 如果持锁的 Redisson 实例挂了，没人续约了，锁会在 30 秒后自动释放

```
时间线 →

锁TTL：  [30s] → [20s] → [10s] → 续约！[30s] → [20s] ...
看门狗：              每10秒检查一次，还持有就续期
```

### Redisson 使用示例

```java
RLock lock = redissonClient.getLock("lock:order:" + orderId);

// 方式1：自动续约（Watchdog 生效）
lock.lock();  // 不指定 leaseTime，Watchdog 自动续期
try {
    // 业务逻辑，执行多久都不怕锁过期
} finally {
    lock.unlock();
}

// 方式2：手动指定过期时间（Watchdog 不生效！）
lock.lock(10, TimeUnit.SECONDS);  // 指定了 leaseTime，10秒后自动释放，不续约
```

> **这里有个大坑**：只有不指定 `leaseTime` 的时候 Watchdog 才会启动！一旦你手动传了过期时间，Redisson 就认为你要自己管理，看门狗不会介入。`lock.tryLock(waitTime, leaseTime, unit)` 中指定了 `leaseTime` 也是一样的，不会续约。

### Watchdog 底层实现

Redisson 的看门狗用的是 Netty 的 **HashedWheelTimer（时间轮）** 来做定时调度，不是 Java 原生的 ScheduledExecutorService。续约的时候也是发一段 Lua 脚本到 Redis：

```lua
-- 续约 Lua 脚本（简化版）
if redis.call('HEXISTS', KEYS[1], ARGV[2]) == 1 then
    redis.call('PEXPIRE', KEYS[1], ARGV[1])
    return 1
end
return 0
```

检查这个 Hash 里有没有当前线程的记录，有的话就刷新过期时间。

## 锁竞争：没抢到锁怎么办？

### 非公平锁（默认）

大部分 Redis 分布式锁都是非公平的——谁抢到算谁的，不讲先来后到。没抢到的线程一般有两种策略：

**策略一：自旋重试 + 退避**

```java
// 简单的自旋重试
int retryCount = 0;
while (retryCount < 3) {
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent("lock:key", value, 30, TimeUnit.SECONDS);
    if (Boolean.TRUE.equals(success)) {
        break;
    }
    // 指数退避 + 随机抖动，减少竞争压力
    Thread.sleep((long) (Math.pow(2, retryCount) * 100 + Math.random() * 100));
    retryCount++;
}
```

**策略二：Redisson 的 Pub/Sub 通知**

Redisson 不会傻傻地自旋，而是用 Redis 的发布/订阅机制：没拿到锁的线程订阅一个 channel，等锁释放时收到通知再去抢，减少了无效的轮询。

```java
// tryLock 带等待时间
boolean acquired = lock.tryLock(5, TimeUnit.SECONDS);  // 最多等5秒
if (acquired) {
    try {
        // 拿到锁了
    } finally {
        lock.unlock();
    }
} else {
    // 5秒内没拿到，走降级逻辑
}
```

### 公平锁

如果业务场景要求严格按请求顺序获取锁（避免线程饥饿），可以用 Redisson 的公平锁：

```java
RLock fairLock = redissonClient.getFairLock("lock:order:" + orderId);
fairLock.lock();
```

底层是通过 Redis 的 List 维护一个等待队列，按请求顺序排队。不过公平锁的实现比较重，性能会差一些，实际用到的场景不太多。

> ZooKeeper 天然支持公平锁——利用临时顺序节点，创建节点时自动排序，序号最小的拿到锁，后面的 watch 前一个节点。相比 Redis 的公平锁实现要优雅得多。

## 可重入锁：同一个线程能重复拿锁吗？

可以，Redisson 默认就是可重入的。

### 什么场景需要可重入？

```java
public void methodA() {
    lock.lock();
    try {
        // 处理逻辑...
        methodB();  // 这里面也要加锁
    } finally {
        lock.unlock();
    }
}

public void methodB() {
    lock.lock();  // 如果不可重入，这里就死锁了
    try {
        // 处理逻辑...
    } finally {
        lock.unlock();
    }
}
```

### 底层实现：Redis Hash + 计数器

Redisson 不是用简单的 String 存锁，而是用 **Hash 结构**：

```
HSET lock:order:123
    "client-uuid:thread-1"    "2"     ← 加锁次数（重入计数）
```

加锁的 Lua 脚本（简化版）：

```lua
-- 加锁
if redis.call('EXISTS', KEYS[1]) == 0 then
    -- 锁不存在，直接获取
    redis.call('HINCRBY', KEYS[1], ARGV[2], 1)
    redis.call('PEXPIRE', KEYS[1], ARGV[1])
    return nil
elseif redis.call('HEXISTS', KEYS[1], ARGV[2]) == 1 then
    -- 锁存在，但是是自己的 → 重入，计数+1
    redis.call('HINCRBY', KEYS[1], ARGV[2], 1)
    redis.call('PEXPIRE', KEYS[1], ARGV[1])
    return nil
else
    -- 锁被别人持有，返回剩余过期时间
    return redis.call('PTTL', KEYS[1])
end
```

解锁的时候计数 -1，减到 0 才真正删除 key：

```lua
-- 解锁
if redis.call('HEXISTS', KEYS[1], ARGV[2]) == 0 then
    return nil  -- 不是自己的锁
end
local counter = redis.call('HINCRBY', KEYS[1], ARGV[2], -1)
if counter > 0 then
    -- 还有重入没释放完，刷新过期时间
    redis.call('PEXPIRE', KEYS[1], ARGV[1])
    return 0
else
    -- 计数归零，真正释放
    redis.call('DEL', KEYS[1])
    redis.call('PUBLISH', KEYS[2], ARGV[3])  -- 通知等待的线程
    return 1
end
```

> 这个设计我觉得挺巧妙的。用 Hash 代替 String，field 是线程标识，value 是重入计数，一个数据结构同时搞定了"谁持有锁"和"重入了几次"两个问题。

## 事务控制：锁和数据库事务的关系

这块容易搞混，也容易出 Bug。

### 经典问题：锁在事务里面还是外面？

**错误写法：锁在事务内部**

```java
@Transactional
public void deductStock(Long productId) {
    RLock lock = redissonClient.getLock("lock:stock:" + productId);
    lock.lock();
    try {
        // 查库存、扣减、更新数据库...
    } finally {
        lock.unlock();  // ⚠️ 锁释放了，但事务还没提交！
    }
    // Spring 的事务在方法返回后才 commit
}
```

问题出在哪？`lock.unlock()` 在 `finally` 里执行了，但 `@Transactional` 的事务是在方法返回后、由 AOP 代理去提交的。也就是说：

```
unlock() → [锁释放了] → 方法返回 → [事务才 commit]
                ↑
          这个间隙里别的线程拿到锁，
          读到的还是旧数据（事务没提交）
```

**正确写法：锁包裹在事务外面**

```java
public void deductStock(Long productId) {
    RLock lock = redissonClient.getLock("lock:stock:" + productId);
    lock.lock();
    try {
        stockService.doDeduct(productId);  // 这个方法上加 @Transactional
    } finally {
        lock.unlock();  // 事务已经在 doDeduct 里提交了，再释放锁
    }
}

@Service
public class StockService {
    @Transactional
    public void doDeduct(Long productId) {
        // 查库存、扣减、更新数据库
        // 方法结束后事务自动提交
    }
}
```

核心原则：**先提交事务，再释放锁**。确保别的线程拿到锁的时候，能读到最新的已提交数据。

> 这个坑我之前真踩过，排查了好久。现象就是偶尔出现库存多扣，日志里看锁确实是串行获取的，但数据就是不对。后来才发现是事务提交时机的问题。

## 更深层的问题：分布式锁真的安全吗？

到这里，Redis 分布式锁好像已经挺完善了。但 Martin Kleppmann（《DERTA》作者）在 2016 年写了一篇很有影响力的文章，指出了一些更根本的问题。

### GC 停顿导致的安全性问题

```
线程A：  [拿到锁] → [开始干活] → [GC STW 停顿很久...] → [恢复，继续写入] ← 危险！
锁状态：  [lock=A]    过期释放    [lock=B]
线程B：                        [拿到锁] → [写入数据]
                                                 ↑
                                           两个线程同时在写！
```

即使有 Watchdog，GC 停顿期间 Watchdog 线程也一样被暂停了，没法续约。

### Fencing Token（防护令牌）

Kleppmann 提出的解决方案是 **Fencing Token**：每次获取锁时，锁服务返回一个单调递增的 token。客户端写入存储时必须带上这个 token，存储端只接受 token 更大的写入。

```
线程A：拿到锁，token=33 → [GC暂停...] → 写入(token=33) → 被拒绝！
线程B：拿到锁，token=34 → 写入(token=34) → 成功
存储层：已记录最大 token=34，拒绝 token=33 的写入
```

但 Redis 的 Redlock 算法不支持生成这种单调递增的 token... 所以 Kleppmann 的建议是：

- **效率型锁**（偶尔重复执行也没事）：单节点 Redis 就够了，简单可靠
- **正确性型锁**（绝对不能并发执行）：用 ZooKeeper 或 etcd 这类基于共识算法的系统，并且加上 Fencing Token

### 主从切换导致锁丢失

还有一个 Redis 特有的问题：

1. 线程 A 在 master 上拿到锁
2. master 还没来得及把锁同步到 slave 就挂了
3. slave 晋升为新 master
4. 线程 B 在新 master 上也拿到了同一把锁

两个线程同时持有锁，互斥性被打破。Redlock 算法试图解决这个问题（要在多数节点上都拿到锁才算成功），但也有争议。

## 方案对比

| 维度 | Redis（Redisson） | ZooKeeper | etcd |
|------|-------------------|-----------|------|
| 性能 | 高 | 中 | 中 |
| 一致性 | AP 偏向，有丢锁风险 | CP，强一致 | CP，强一致 |
| 可重入 | 支持 | 支持 | 需自己实现 |
| 公平锁 | 支持 | 天然支持（顺序节点） | 需自己实现 |
| 自动续约 | Watchdog | 会话心跳（session） | Lease 续约 |
| 复杂度 | 低，API 友好 | 中等 | 中等 |
| 适用场景 | 大部分业务场景 | 对一致性要求极高 | 云原生环境 |

## 小结

分布式锁看着简单，但每一步都有坑：加锁要原子、解锁要验证身份、过期要续约、事务要注意提交顺序。实际开发中推荐直接用 Redisson，它把这些细节都封装好了。但了解底层原理还是很有必要的——出了问题至少知道从哪排查。对一致性要求极高的场景，认真考虑一下 ZooKeeper 或 etcd。
