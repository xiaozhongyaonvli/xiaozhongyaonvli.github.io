# 分库分表之后，跨库查询怎么搞？几种方案的取舍

> 分库分表解决了单库容量和性能瓶颈，但也带来了一个非常头疼的问题 —— 以前一条 SQL JOIN 就能搞定的查询，数据散在不同库里之后就不好使了。这篇笔记把主流的跨库查询方案都过一遍，顺便比较下各自的性能和适用场景。

## 为什么跨库查询是个大问题

先理解一下问题的本质。假设我们按 `user_id` 做了分片：

```
分片前（单库）：
  SELECT o.*, p.name FROM orders o
  JOIN products p ON o.product_id = p.id
  WHERE o.user_id = 123

分片后（数据散在不同库）：
  orders 按 user_id 分片 → 用户 123 的订单在 DB-2
  products 没有按 user_id 分 → 可能在 DB-0
  → 跨库 JOIN 做不了！
```

MySQL 本身是不支持跨库 JOIN 的。数据库引擎只能看到自己这个实例上的数据，另一个实例上的表对它来说压根不存在。

而且跨库查询不只是 JOIN 的问题。分页、排序、聚合（COUNT/SUM/AVG）这些在跨库场景下都变得很复杂 —— 你没法简单地对每个分片做 `LIMIT 10` 然后拼起来就得到全局的 Top 10。

---

## 方案一：从根上避免 —— 合理设计分片键

> 这是最重要的一条，也是成本最低的。**最好的跨库查询方案就是不做跨库查询。**

核心思路：**把经常需要一起查询的数据放在同一个分片上。**

### 数据共置（Data Colocation）

如果订单表和订单详情表都按 `user_id` 分片，那同一个用户的订单和订单详情一定在同一个库里，JOIN 就是本地操作，没有跨库问题。

```
用户 123 的数据全部在 DB-2：
  DB-2.orders        (user_id=123 的订单)
  DB-2.order_items   (user_id=123 的订单详情)
  → 本地 JOIN，没有跨库问题
```

Square 的工程博客里提到，他们用的就是 **Entity Group** 模型 —— 一个根实体（比如用户）和它所有关联的子实体（订单、支付记录等），共享同一个根 ID 作为分片键，保证同一组数据总是在同一个分片上。

这个思路说白了就是：**分片键的选择要跟着主查询场景走。** 如果你的业务 80% 的查询都是"查某个用户的 xxx"，那就按 `user_id` 分片，这样大部分查询天然就是单分片的。

但现实是，一个系统不可能只有一种查询模式。用户维度的查询是主场景，但运营后台要按时间范围查、商家要查自己的订单... 这些查询的维度跟分片键对不上，还是得面对跨库问题。

---

## 方案二：冗余数据 / 数据异构

既然跨库 JOIN 做不了，那就**提前把需要关联的数据冗余存一份**，查的时候就不用 JOIN 了。

### 字段级冗余

最简单的做法，在订单表里直接冗余存商品名称、用户昵称这些经常需要展示的字段：

```sql
-- 分片前：订单表 + JOIN 商品表
SELECT o.id, p.name, p.price FROM orders o JOIN products p ...

-- 分片后：订单表里直接冗余了商品名和价格
CREATE TABLE orders (
    id BIGINT,
    user_id BIGINT,
    product_id BIGINT,
    product_name VARCHAR(200),  -- 冗余字段
    product_price DECIMAL,      -- 冗余字段
    ...
);
-- 查询直接查订单表就行，不需要 JOIN
```

优点很明显 —— 查询变简单了，性能好。缺点也明显 —— **数据一致性要自己维护**。商品改名了，你得同步更新所有订单里的冗余字段。如果商品名不经常改还好，如果是价格这种敏感数据，一致性问题就比较严重。

> 这个方案适合那种"写入后就不变"的数据。比如订单创建时的商品快照 —— 下单那一刻的价格就应该被锁定，后续商品调价不影响历史订单，这种场景天然适合冗余。

### 表级冗余（数据异构）

更激进一点，按不同的查询维度把数据再存一份。比如订单按 `user_id` 分片是主库，再按 `merchant_id` 分片存一份副本给商家后台用：

```
主库（按 user_id 分片）：用户查自己的订单 → 单分片查询
副本（按 merchant_id 分片）：商家查自己的订单 → 也是单分片查询
```

两份数据通过 **Binlog 同步**（Canal/Debezium）或者消息队列来保持最终一致。

（这种做法本质上就是下面要说的 CQRS 思想的一种体现）

---

## 方案三：全局表 / 广播表

有些表数据量很小、很少更新，但几乎每个查询都要 JOIN 它 —— 比如字典表、地区表、配置表。这种表可以在**每个分片上都存一份完整拷贝**。

```
DB-0:  orders_0 + products(全量)  ← 本地 JOIN
DB-1:  orders_1 + products(全量)  ← 本地 JOIN
DB-2:  orders_2 + products(全量)  ← 本地 JOIN
```

ShardingSphere 里叫**广播表**（Broadcast Table），配置很简单：

```yaml
rules:
  - !SHARDING
    broadcastTables:
      - products
      - sys_config
      - region
```

写入的时候框架自动向所有分片同步写入，读取的时候就近从当前分片读，JOIN 变成本地操作。

**限制**：只适合小表（几千到几万条）。要是商品表有几百万条，每个分片都存一份，存储浪费严重，而且写入同步的开销也扛不住。

## 方案四：应用层组装（代码里做 JOIN）

最"笨"但也最灵活的方案 —— 分两次查询，在代码里手动关联。

```java
// 第一步：查订单（走分片路由，单库查询）
List<Order> orders = orderMapper.selectByUserId(userId);

// 第二步：提取所有商品 ID，批量查商品信息
List<Long> productIds = orders.stream()
    .map(Order::getProductId)
    .distinct()
    .collect(Collectors.toList());
// 商品表可能在另一个库，走自己的路由
Map<Long, Product> productMap = productMapper.selectByIds(productIds)
    .stream()
    .collect(Collectors.toMap(Product::getId, p -> p));

// 第三步：代码里组装
List<OrderVO> result = orders.stream().map(order -> {
    OrderVO vo = new OrderVO(order);
    vo.setProductName(productMap.get(order.getProductId()).getName());
    return vo;
}).collect(Collectors.toList());
```

这个方案看着 low，但实际上**很多大厂就是这么干的**。原因很简单：可控。你清楚地知道每一次查询走了哪个库，SQL 都是简单的单表查询，性能好优化，也容易加缓存。

缺点就是代码侵入性大，开发效率低。如果关联关系复杂（三四张表关联），代码会写得很啰嗦。

## 方案五：CQRS —— 读写分离到极致

CQRS（Command Query Responsibility Segregation）的核心思想：**写操作和读操作用不同的数据模型。**

```
写入路径：
  业务操作 → 分片数据库（按 user_id 分片，保证写入性能）
                ↓ Binlog / 消息队列
读取路径：
  查询请求 → 读模型（提前聚合好的宽表 / 搜索引擎 / 数据仓库）
```

具体来说就是：

**写入侧**：正常走分库分表，保证写入性能和数据一致性。

**读取侧**：通过 Binlog 订阅（Canal / Debezium）把变更事件发到消息队列，消费者把数据聚合成查询友好的格式，写入专门的读库。

读库的选择取决于查询场景：

| 查询场景 | 读库选择 | 为什么 |
|---------|---------|-------|
| 复杂条件搜索、全文检索 | Elasticsearch | 天然支持多维度查询 |
| 实时报表、聚合统计 | ClickHouse / Doris | 列式存储，聚合性能强 |
| 简单的跨维度查询 | 一个非分片的 MySQL 宽表 | 最简单，数据量不大时够用 |
| 运营后台多维度查询 | MongoDB | 文档模型灵活 |

```
实际例子 —— 订单搜索：

写入：订单创建 → orders 表（按 user_id 分片）

同步：Canal 监听 Binlog → Kafka → 消费者组装宽数据 → 写入 ES

读取：运营后台搜索 → ES（支持按用户、商家、时间、商品等任意维度查询）
```

> 我觉得 CQRS 是跨库查询问题的"终极方案"。它不是在分片数据库上硬做跨库查询，而是换了个思路 —— **写的时候按写的最优方式存，读的时候按读的最优方式存，两边各管各的。**

代价是什么？**一致性变成了最终一致。** 写入到读模型的同步有延迟（通常几百毫秒到几秒），这段时间内读到的可能是旧数据。对于运营后台、搜索、报表这种场景，几秒延迟完全可以接受。但如果是"下单后立刻查看订单详情"这种场景，就得做特殊处理（比如写完后短暂从主库读）。

## 方案六：中间件代理（ShardingSphere Federation）

ShardingSphere 从 5.0 开始引入了 **SQL Federation 引擎**，可以在中间件层面自动处理跨库查询。

原理是这样的：

```
应用发出跨库 SQL
  → ShardingSphere 解析 SQL
  → 路由引擎发现涉及多个分片
  → 触发 Federation 执行引擎（而不是普通的 Push Down 引擎）
  → SQL 优化器（RBO + CBO）生成最优分布式执行计划
  → 分别从各分片拉取数据
  → 在中间件层面做 JOIN / 聚合 / 排序
  → 返回结果给应用
```

对应用来说是透明的，SQL 写法不用变。但... 说实话我觉得**生产中要谨慎使用这个功能**。原因有几点：

1. **性能不可控** —— 中间件层面做 JOIN 意味着要从各分片拉大量原始数据到内存里再关联，数据量大了内存扛不住
2. **SQL 支持有限** —— 并不是所有 SQL 都能支持，复杂子查询可能还是不行
3. **黑盒** —— 你不确定中间件生成的分布式执行计划是不是最优的

适合的场景：偶尔用用的管理查询，数据量可控。不适合：高并发的在线查询。

## 方案七：Scatter-Gather（扇出-聚合）

有些查询确实没办法避免跨全部分片，比如"统计所有用户的总订单数"。这时候只能老老实实地**向所有分片发查询，然后聚合结果**。

```
应用 / 中间件
  并行发送 → DB-0: SELECT COUNT(*) → 1000
  并行发送 → DB-1: SELECT COUNT(*) → 1500
  并行发送 → DB-2: SELECT COUNT(*) → 800
  聚合结果 → 总计 3300
```

关键是要**并行发送**，别串行。并行的话，总耗时 ≈ 最慢的那个分片的耗时；串行的话就是所有分片耗时之和。

但这个方案有个严重问题 —— **跨分片分页**：

```
需求：全局按时间排序，取第 3 页（每页 10 条，即 offset=20, limit=10）

错误做法：每个分片 LIMIT 20, 10 → 拼起来 ← 结果不对！
正确做法：每个分片 LIMIT 0, 30 → 拉回来在内存排序 → 取 offset 20 的 10 条

问题：翻到第 100 页就是 LIMIT 0, 1000... 越往后越慢！
```

> 这就是分库分表后**深度分页**的经典难题。没有完美解决方案，通常做法是禁止深度翻页（只允许"下一页"不允许跳页），或者引入游标分页（`WHERE id > last_id LIMIT 10`）。

Square 的工程博客提到，他们分片后发现 **25% 的数据库流量都是 scatter 查询**。分片数增加后这个问题更严重 —— 每多一个分片，每次 scatter 就多一次查询。后来他们通过 Lookup VIndex（分布式索引表）把大部分 scatter 查询改成了定点查询，效果明显。

## 各方案性能对比

| 方案 | 查询性能 | 一致性 | 开发成本 | 适用场景 |
|------|---------|--------|---------|---------|
| **合理分片键** | 最好（单分片查询） | 强一致 | 低（设计阶段） | 主查询路径 |
| **冗余字段** | 好（单表查询） | 需维护 | 低 | 不常变的关联数据 |
| **广播表** | 好（本地 JOIN） | 强一致 | 低 | 小表（字典/配置） |
| **应用层组装** | 中等（多次查询） | 强一致 | 中 | 关联不复杂的场景 |
| **CQRS + ES/宽表** | 好（针对读优化） | 最终一致 | 高 | 多维度复杂查询 |
| **中间件 Federation** | 较差（内存计算） | 强一致 | 低（透明） | 低频管理查询 |
| **Scatter-Gather** | 最差（全分片扇出） | 强一致 | 中 | 聚合统计类查询 |

**哪个性能最好？** 没有绝对的答案，取决于场景。但有一个大原则：

> **能在分片设计阶段解决的问题，就不要留到查询阶段。** 分片键选得好，80% 的查询都是单分片的，剩下 20% 用冗余 + CQRS 兜底，基本就覆盖了。

## 实际项目中我会怎么选

如果让我设计一个分库分表后的查询架构，大概会是这样的层次：

```
第一层：分片键设计（解决 80% 的主路径查询）
  ↓ 剩下的非主路径查询
第二层：冗余字段 + 广播表（解决简单关联）
  ↓ 还是不够
第三层：CQRS 同步到 ES（解决复杂搜索和多维度查询）
  ↓ 极少数场景
第四层：应用层组装 / Scatter-Gather（兜底）
```

不到万不得已不会用中间件的跨库 JOIN 功能，太不可控了。

---

## 小结

分库分表后的跨库查询，核心思路就是**要么避免跨库（设计好分片键 + 数据共置），要么提前准备好数据（冗余 / CQRS），要么接受代价（应用层组装 / 全分片扇出）**。没有银弹，得根据自己的查询场景组合使用。最怕的是分片键选错了 —— 等数据量上去之后再改分片策略，基本等于数据大迁移，成本极高。所以分库分表之前，一定要先把查询场景梳理清楚。
