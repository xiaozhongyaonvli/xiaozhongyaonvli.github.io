> 最近在做一个视频平台的点赞功能，看起来简单——用户点一下，数字 +1 嘛。但一旦并发上来（热门视频几万人同时点赞），单靠数据库根本扛不住。最终用了 Caffeine + Redis + MySQL 的三级缓存方案，中间踩了不少坑，记录一下。

## 为什么需要多级缓存？

先说说不用缓存会怎样。

假设每次用户点赞，直接写 MySQL：

```sql
UPDATE video SET like_count = like_count + 1 WHERE video_id = 123;
```

一个热门视频每秒可能有上万次点赞请求。MySQL 单机的写入 QPS 撑死几千，而且每次 `UPDATE` 都要加行锁——并发一高，大量请求排队等锁，接口响应从毫秒级飙到秒级，用户体验直接崩掉。

加一层 Redis 缓存？好很多，Redis 单机轻松 10 万+ QPS。但如果你的服务部署了多个实例，每次点赞都要走一次网络请求到 Redis，在极端场景下（比如某个视频突然上热门），Redis 的这个 key 就成了**热 key**，单个 Redis 节点的网络带宽和 CPU 可能被打满。

所以最终方案是**三级缓存**：

```
L1: Caffeine（JVM 本地内存）    → 微秒级，零网络开销
L2: Redis（分布式缓存）          → 亚毫秒级，跨实例共享
L3: MySQL（持久化存储）          → 毫秒级，数据最终落盘
```

每一层解决不同的问题：L1 挡住最热的读请求不出 JVM，L2 在多实例间共享数据，L3 保证数据不丢。

## 整体架构设计

先画个全景图，再一块一块说。

```
用户点赞请求
  ↓
点赞服务（多实例）
  L1: Caffeine (本地缓存)    点赞去重 (Redis Set)
        ↓                        ↓
  写入 Redis 计数器: INCRBY video:likes:123
        ↓
定时任务 / 异步刷盘: Redis → MySQL 批量同步
        ↓
  MySQL (持久化)
```

核心思路：**点赞写入只到 Redis，不直接写 MySQL；定时任务批量把 Redis 的数据刷到 MySQL**。这就是所谓的 Write-Behind（写后）策略。

## 第一层：点赞去重

点赞功能的第一个问题不是性能，是**幂等**——同一个用户对同一个视频只能点赞一次。

```java
// 用 Redis 的 Set 做去重
// key: video:liked_users:{videoId}
// value: userId

public boolean hasLiked(Long videoId, Long userId) {
    String key = "video:liked_users:" + videoId;
    return redisTemplate.opsForSet().isMember(key, userId.toString());
}

public boolean doLike(Long videoId, Long userId) {
    String key = "video:liked_users:" + videoId;
    // SADD 返回 1 表示新增成功（之前没点过），返回 0 表示已存在
    Long result = redisTemplate.opsForSet().add(key, userId.toString());
    return result != null && result > 0;
}
```

> 这里用 Redis Set 而不是查 MySQL 的 `user_like` 表，是因为**高并发场景下查数据库做去重太慢了**，而且可能出现并发问题——两个请求同时查到"没点过"，然后都写入。Redis 的 `SADD` 是原子操作，天然去重。

不过 Set 有内存开销问题。如果一个热门视频有 1000 万用户点赞，这个 Set 就很大。如果内存紧张，可以考虑用 **Bloom Filter** 做初筛——它可能误判"已点赞"（放弃一些本可以点的），但不会误判"未点赞"（不会出现重复点赞），而且内存占用小得多。

## 第二层：Redis 计数器

去重通过后，更新点赞计数：

```java
public void incrementLikeCount(Long videoId) {
    String countKey = "video:likes:" + videoId;
    redisTemplate.opsForValue().increment(countKey);
}

public Long getLikeCount(Long videoId) {
    String countKey = "video:likes:" + videoId;
    String count = redisTemplate.opsForValue().get(countKey);
    if (count != null) {
        return Long.parseLong(count);
    }
    // Redis 没有，从 DB 加载
    Long dbCount = videoMapper.getLikeCount(videoId);
    redisTemplate.opsForValue().set(countKey, dbCount.toString(), 1, TimeUnit.HOURS);
    return dbCount;
}
```

Redis 的 `INCR/INCRBY` 是原子操作，多线程并发调也不会出数据问题，所以**不需要加锁**。这是 Redis 做计数器的天然优势。

### 热 key 问题

如果某个视频突然上热搜，`video:likes:123` 这个 key 会被几万个请求同时打。所有请求都打到同一个 Redis 节点上，可能导致：

1. 该节点 CPU 和带宽打满
2. 其他正常 key 的访问也被拖慢

**解决方案：本地缓存兜底**。对于读请求（获取点赞数），先查 Caffeine 本地缓存：

```java
// Caffeine 本地缓存配置
private final Cache<Long, Long> localLikeCountCache = Caffeine.newBuilder()
    .maximumSize(10_000)                // 最多缓存 1 万个视频的计数
    .expireAfterWrite(3, TimeUnit.SECONDS)  // 3 秒过期（允许短暂不一致）
    .build();

public Long getLikeCountWithLocalCache(Long videoId) {
    // L1: 先查本地缓存
    Long count = localLikeCountCache.getIfPresent(videoId);
    if (count != null) {
        return count;
    }

    // L2: 本地没有，查 Redis
    count = getLikeCount(videoId);

    // 回填 L1
    localLikeCountCache.put(videoId, count);
    return count;
}
```

> Caffeine 的 TTL 故意设得很短（3 秒），因为点赞数是高频变化的数据。3 秒内同一个实例的重复读请求全走本地内存（微秒级），不打 Redis。3 秒后过期，重新从 Redis 拉最新值。用户感知上"点赞数 3 秒内可能不是最新的"，但对于这个场景完全可以接受。

## 第三层：异步刷盘到 MySQL

Redis 里的数据不持久——Redis 挂了或者重启，数据可能丢。所以需要定时把 Redis 的计数同步到 MySQL。

```java
@Scheduled(fixedRate = 5000)  // 每 5 秒执行一次
public void syncLikeCountToDB() {
    // 1. 从 Redis 获取所有有变更的视频 ID
    //    （可以用一个额外的 Set 记录"脏数据"）
    Set<String> dirtyVideos = redisTemplate.opsForSet()
        .members("video:likes:dirty");

    if (dirtyVideos == null || dirtyVideos.isEmpty()) return;

    // 2. 批量读取计数
    List<Long> videoIds = dirtyVideos.stream()
        .map(Long::parseLong)
        .collect(Collectors.toList());

    // 3. 批量更新 MySQL（一条 SQL 搞定，不要循环单条更新！）
    for (List<Long> batch : Lists.partition(videoIds, 500)) {
        List<VideoLikeCount> counts = batch.stream()
            .map(id -> {
                String countStr = redisTemplate.opsForValue()
                    .get("video:likes:" + id);
                return new VideoLikeCount(id, Long.parseLong(countStr));
            })
            .collect(Collectors.toList());

        // 用 ON DUPLICATE KEY UPDATE 做 upsert
        videoMapper.batchUpdateLikeCounts(counts);
    }

    // 4. 清除脏标记
    redisTemplate.delete("video:likes:dirty");
}
```

对应的 SQL：

```sql
-- 批量 upsert，一条 SQL 更新多条记录
INSERT INTO video_like_count (video_id, like_count, updated_at)
VALUES
  (123, 50000, NOW()),
  (456, 12000, NOW()),
  (789, 8000, NOW())
ON DUPLICATE KEY UPDATE
  like_count = VALUES(like_count),
  updated_at = NOW();
```

> 为什么不每次点赞都写 MySQL？因为**批量写比逐条写效率高得多**。假设 5 秒内有 1 万次点赞分布在 200 个视频上，逐条写是 10000 次 INSERT，批量写只需要 1 条 SQL 更新 200 行。数据库压力差两个数量级。

### 数据丢失风险

Write-Behind 最大的问题是：**Redis 挂了但还没来得及刷到 MySQL，数据就丢了**。

应对方案：

1. **Redis 开 AOF 持久化**，`appendfsync everysec`（每秒刷盘一次），最多丢 1 秒数据
2. **Redis 主从 + 哨兵/集群**，主节点挂了从节点顶上
3. **缩短刷盘间隔**——从 5 秒改成 2 秒，丢失窗口更小
4. **接受"少量不精确"**——对于点赞数这种非金融场景，差个几十上百完全没人在意

（如果是金融场景——比如账户余额——千万不要用 Write-Behind，必须用 Write-Through 同步双写。）

## 缓存一致性怎么保证？

三级缓存最头疼的问题就是数据一致性。场景举个例子：

```
实例 A 的 Caffeine 缓存: video:123 → 50000
实例 B 的 Caffeine 缓存: video:123 → 50000
Redis:                   video:123 → 50100  （有新的点赞进来了）
MySQL:                   video:123 → 49500  （还没刷盘）
```

三个地方三个不同的值，哪个是"准"的？

### 我的一致性策略

**1. L1（Caffeine）→ L2（Redis）：靠 TTL 自然过期**

Caffeine 设 3 秒过期，意味着最多 3 秒的不一致窗口。过期后下次读会从 Redis 拉最新值。

如果需要更快的一致性，可以用 **Redis Pub/Sub** 做主动通知：

```java
// 点赞时发布消息
redisTemplate.convertAndSend("like_count_update",
    videoId + ":" + newCount);

// 各实例订阅消息，收到后清除本地缓存
@RedisListener(channel = "like_count_update")
public void onLikeCountUpdate(String message) {
    String[] parts = message.split(":");
    Long videoId = Long.parseLong(parts[0]);
    localLikeCountCache.invalidate(videoId);  // 清除本地缓存
}
```

但说实话，对于点赞数这种场景，**3 秒 TTL 就够了**，没必要上 Pub/Sub 增加复杂度。

**2. L2（Redis）→ L3（MySQL）：靠定时刷盘**

Redis 里的值永远 >= MySQL 里的值（因为新点赞先写 Redis，后刷 MySQL）。读的时候优先读 Redis，MySQL 只是兜底和持久化。

**3. 缓存击穿/穿透防护**

```java
// 缓存击穿：热 key 过期瞬间大量请求打到 DB
// 解决：用 Caffeine 的 refreshAfterWrite，后台异步刷新，旧值继续服务

private final LoadingCache<Long, Long> localCache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(5, TimeUnit.SECONDS)
    .refreshAfterWrite(3, TimeUnit.SECONDS)  // 3 秒后台刷新，5 秒才真正过期
    .build(videoId -> getLikeCountFromRedis(videoId));

// 缓存穿透：查一个不存在的视频 ID
// 解决：缓存空值
public Long getLikeCount(Long videoId) {
    String count = redisTemplate.opsForValue().get("video:likes:" + videoId);
    if (count != null) {
        return "NULL".equals(count) ? 0L : Long.parseLong(count);
    }
    Long dbCount = videoMapper.getLikeCount(videoId);
    if (dbCount == null) {
        // 缓存空值，防止穿透，但 TTL 设短一些
        redisTemplate.opsForValue().set("video:likes:" + videoId, "NULL",
            30, TimeUnit.SECONDS);
        return 0L;
    }
    redisTemplate.opsForValue().set("video:likes:" + videoId,
        dbCount.toString(), 1, TimeUnit.HOURS);
    return dbCount;
}
```

## 取消点赞怎么办？

别忘了用户还可以取消点赞。流程是反过来的：

```java
public boolean cancelLike(Long videoId, Long userId) {
    String likedKey = "video:liked_users:" + videoId;

    // 1. 先检查是否点过赞
    Boolean isMember = redisTemplate.opsForSet().isMember(likedKey, userId.toString());
    if (isMember == null || !isMember) {
        return false;  // 本来就没点过
    }

    // 2. 从 Set 中移除
    redisTemplate.opsForSet().remove(likedKey, userId.toString());

    // 3. 计数 -1
    redisTemplate.opsForValue().decrement("video:likes:" + videoId);

    // 4. 标记脏数据等待刷盘
    redisTemplate.opsForSet().add("video:likes:dirty", videoId.toString());

    // 5. 清除本地缓存
    localLikeCountCache.invalidate(videoId);

    return true;
}
```

> 这里有个细节：`DECR` 可能把计数减到负数（极端并发下）。可以在刷盘时加个 `Math.max(0, count)` 兜底，或者用 Lua 脚本保证 `DECR` 不低于 0。

## 完整的读写流程总结

### 点赞（写流程）

```
用户点赞
  → Redis SADD 去重（已点过则拒绝）
  → Redis INCR 计数 +1
  → Redis SADD 标记脏数据
  → 清除本地 Caffeine 缓存（下次读会拉最新值）

      ... 定时任务每 5 秒 ...

  脏数据 → 批量读 Redis 计数 → 批量 UPSERT MySQL
```

### 查看点赞数（读流程）

```
请求点赞数
  → 查 L1: Caffeine 本地缓存
    命中 → 直接返回（微秒级）
  → 未命中，查 L2: Redis
    命中 → 返回 + 回填 L1
  → 未命中，查 L3: MySQL
    命中 → 返回 + 回填 L2 和 L1
    未命中 → 返回 0 + 缓存空值
```

## 踩过的坑

**坑 1：Caffeine 的 TTL 设太长**

一开始设了 30 秒，结果用户点完赞刷新页面，数字没变——因为本地缓存还没过期。改成 3 秒就好了。点赞数这种高频变化的数据，本地缓存只是用来"削峰"的，TTL 必须短。

**坑 2：Redis 和 MySQL 的数据不一致**

刷盘任务出过 bug——读 Redis 计数和写 MySQL 不在一个原子操作里，中间又有新的点赞进来，导致 MySQL 的值偶尔比 Redis 小。后来改成在刷盘时用 `GETSET` 原子读取并重置增量（或者用 Lua 脚本），保证不丢数据。

**坑 3：服务重启时 Caffeine 缓存冷启动**

服务刚重启，Caffeine 是空的，所有请求都打到 Redis。如果恰好赶上流量高峰，Redis 压力骤增。解决方案是**缓存预热**——服务启动时主动从 Redis 加载 Top 1000 热门视频的计数到 Caffeine。

**坑 4：Redis Set 内存暴涨**

`video:liked_users:{videoId}` 这个 Set，热门视频可能有几百万个 userId。一开始没在意，直到 Redis 内存告警。后来对超过 10 万点赞的视频，把去重逻辑降级到 MySQL（毕竟这些视频的点赞增长已经不那么"爆发"了），并设置 Set 的过期时间。

## 什么场景适合多级缓存？

不是所有场景都需要三级缓存，杀鸡别用牛刀：

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 低并发读写（后台管理系统） | 直接读写 DB | 没必要加缓存增加复杂度 |
| 高并发读、低并发写（商品详情） | Redis 缓存 + DB | 一级 Redis 就够了 |
| 高并发读 + 高并发写（点赞/播放量） | Caffeine + Redis + DB | 本文方案 |
| 超高并发写 + 允许丢失（实时弹幕数） | 纯 Redis / 内存计数 | 不一定需要落 DB |

> 核心判断标准：**写并发有多高** × **数据能不能丢** × **一致性要求多强**。点赞数属于"高写并发 + 可以丢一点 + 最终一致就行"，所以 Write-Behind 是最合适的。

## 小结

多级缓存的核心思路就一句话：**读请求层层拦截，写请求异步下沉**。L1 Caffeine 用极短 TTL 挡住热点读，L2 Redis 做跨实例共享和原子计数，L3 MySQL 做持久化兜底。写入只到 Redis，定时批量刷 MySQL。一致性上接受"秒级延迟"的最终一致，换来的是几个数量级的性能提升。方案不复杂，但细节（去重、热 key、刷盘原子性、缓存预热）每一个都值得认真对待。
