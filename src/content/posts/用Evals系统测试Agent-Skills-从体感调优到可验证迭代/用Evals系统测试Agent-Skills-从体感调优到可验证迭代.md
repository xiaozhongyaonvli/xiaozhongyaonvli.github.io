> 写 Agent Skill 时，最大的错觉是“这次跑通了，所以它变好了”。这篇文章基于 OpenAI Developers 的 `Testing Agent Skills Systematically with Evals`，整理一套更工程化的 Skill 迭代思路：先定义成功，再捕获运行过程，再用规则和 rubric 做检查。

# 从“感觉变好了”到“可以被证明”：用 Evals 系统测试 Agent Skills

## 开场：Skill 真的是变好了，还是只是看起来变好了？

写 agent skill 时，最危险的优化方式是“凭感觉迭代”。

你改了一段 `SKILL.md`，重新跑一次任务，发现这次输出更顺、更像你想要的结果，于是判断它变好了。但问题是：下一次 prompt 稍微变一下，它还会好吗？另一个相邻场景会不会误触发？这次变快，是因为指令更清晰，还是因为它跳过了一个本该执行的步骤？

OpenAI 在《Testing Agent Skills Systematically with Evals》里讨论的正是这个问题。文章的核心并不是“如何写一个漂亮的 skill”，而是如何把 skill 的迭代从主观体感变成可重复验证的工程过程。

一句话概括：

```text
prompt -> captured run -> checks -> score -> revise skill -> rerun
```

也就是说，先让 agent 真正跑起来，捕获它做了什么，再用一组小而明确的检查来打分。这样每一次 skill 改动都能回答一个具体问题：它是否在同一批任务上更可靠了？

## Skill Eval 评估的不是“最后一句回答”

很多人第一次理解 eval，会把它理解成“让另一个模型判断最终答案好不好”。这只覆盖了一小部分问题。

Agent skill 的失败经常发生在过程里：

- skill 没有触发
- 触发了错误的 skill
- 应该执行的命令没有执行
- 执行顺序错了
- 生成了多余文件
- 输出格式不符合项目约定

官方文章给出的定义更接近轻量端到端测试：运行 agent，记录 trace 和 artifacts，然后用规则或 rubric 评分。文章还明确建议从四类成功标准开始：结果目标、过程目标、风格目标、效率目标。来源见官方文章的 “Define success before you write the skill” 部分。

只记一个判断标准，就是：**能被检查的成功标准，才适合进入 eval。**

## 第一步：先写“成功定义”，再写 Skill

官方文章提醒：在写 skill 之前，应该先写什么叫成功。

以文章中的 `setup-demo-app` 为例，这个 skill 的目标不是泛泛地“创建一个 demo app”，而是创建一个可以被检查的最小 React demo。它有明确的结构、命令和完成标准，比如项目要存在、依赖要安装、`package.json` 要生成、组件文件要出现。

这背后的工程原则是：没有约束，就没有可验证性。

一个实用的成功标准可以这样拆：

| 维度 | 要问的问题 | 示例 |
| --- | --- | --- |
| 结果 | 任务是否完成 | demo app 是否创建成功 |
| 过程 | 是否走了正确步骤 | 是否执行 `npm install` |
| 风格 | 是否符合项目约定 | 是否使用函数组件和约定目录 |
| 效率 | 是否避免无谓动作 | 是否没有重复安装或乱改文件 |

这类示例 skill 不需要一开始就复杂。更好的做法是先保持最小：只描述目标、步骤、约束和完成标准。这样你才能清楚观察 eval 如何约束 skill 行为。

## 第二步：把触发也纳入测试

`SKILL.md` 里的 `name` 和 `description` 不是普通文档字段。官方文章指出，它们是 Codex 判断是否注入 skill 内容的重要信号。如果这两个字段写得含糊，就会出现两个方向的错误：

- 该触发时没有触发
- 不该触发时误触发

这也是为什么 eval 数据集里不能只放正样本。你至少需要四类 prompt：

- 显式触发：直接点名 skill
- 隐式触发：不点名，但描述目标场景
- 上下文触发：带一些真实背景噪声
- 负样本：相邻但不该触发的任务

官方文章也建议先用 10 到 20 条小数据集起步，而不是一开始做很大的 benchmark。这个数据集可以很简单，比如一个 CSV，列出 `id`、`category`、`prompt` 和 `expected_behavior`。

小数据集的好处是定位快。你会很快知道失败属于哪一类：触发问题、执行问题、输出问题，还是环境假设问题。

## 第三步：用 JSONL Trace 做确定性检查

文章最实用的一点，是建议用 `codex exec --json` 捕获结构化事件流。

当 stdout 变成 JSONL 后，你不再只能看最终输出，而是可以检查 agent 运行过程里发生了什么。例如：

- 是否出现 `command_execution` 事件
- 是否执行了 `npm install`
- 是否按顺序执行初始化、安装、配置
- 是否创建了预期文件

这些检查非常适合写成确定性规则。确定性规则的价值是稳定、便宜、可解释。失败时你可以打开 JSONL，看清楚到底是哪一步没发生。

```text
读取 JSONL -> 提取事件文本 -> 执行规则检查 -> 输出结构化结果
```

对于早期 skill eval，这种“小脚本 + 小 prompt 集”的组合通常已经足够有价值。它不需要先变成完整平台，只要能稳定回答“这次运行是否做了关键动作”。

## 第四步：规则解决不了的，再交给 Rubric

确定性检查可以回答“有没有做”，但很难回答“做得好不好”。

例如：

- UI 结构是否清晰
- 输出说明是否适合交付
- PR 描述是否符合团队习惯
- 组件组织是否足够一致

这类问题适合 rubric。官方文章建议使用 `--output-schema` 约束评分输出，让模型返回稳定 JSON，而不是自由发挥一段评价文字。

这里有一个重要分工：

| 问题类型 | 推荐方式 |
| --- | --- |
| 文件是否存在 | 确定性检查 |
| 命令是否执行 | 确定性检查 |
| 顺序是否正确 | 确定性检查 |
| 风格是否清晰 | Rubric |
| 是否符合团队写法 | Rubric |

经验法则是：能写规则就先写规则，规则写不清楚的再用 rubric。

## 从官方文章到真实项目：Skill 应该长什么样

读完官方文章后，还可以去看一些真实仓库里的 skill 写法。它们很适合用来理解“文章里的原则如何落到真实项目”：

- `skill-creator`：展示 skill 的结构、资源分层和触发描述
- `code-change-verification`：展示如何把验证流程写成 skill 和脚本
- `pr-draft-summary`：展示如何约束最终输出格式和触发边界
- `validation-prompt.md`：展示真实 prompt 如何把规则、上下文和 JSON 输出约束合在一起
- `final-release-review`：展示高风险场景下如何定义 gate policy

官方文章给的是方法论，这些真实 skill 给的是工程形态。两者结合起来看，会更容易理解为什么 skill 不应该只是提示词堆叠，而应该包含触发边界、执行步骤、检查标准和必要资源。

## 一个可复用的 Skill Eval 工作流

如果你要为自己的 skill 建 eval，可以直接照这个顺序做：

1. 写成功标准，只保留最关键的 must-pass 行为。
2. 写或修改 `SKILL.md`，重点打磨 `name` 和 `description`。
3. 准备 10 到 20 条 prompt，包括正样本、上下文样本和负样本。
4. 手动显式触发几次，先暴露明显环境假设和执行顺序问题。
5. 用 `codex exec --json` 捕获 trace。
6. 先写确定性检查，比如命令、文件、顺序、产物。
7. 对风格和质量类问题补 rubric，并用 JSON schema 约束输出。
8. 每次真实失败后，增加一条 prompt 或一条检查。

这个流程的重点不是一次性把 eval 写完，而是让 eval 跟着 skill 一起成长。

## 结尾：把每次失败变成下一条测试

**每一次手动修复，都应该变成未来的一条 eval。**

当你这样做时，skill 不再是一个“看起来更聪明”的提示词文件，而是一个有回归保护的工程资产。你可以改它、扩展它、把它放进 CI，甚至用它维护真实开源仓库。

这就是 eval 对 agent skill 的真正价值：它把“我觉得变好了”变成“我能证明它在这些场景下没有退步”。
