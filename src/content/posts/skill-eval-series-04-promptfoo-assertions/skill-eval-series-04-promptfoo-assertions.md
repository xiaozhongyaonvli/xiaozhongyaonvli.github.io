> 这是系列的第四篇。这一篇主要学习 assertion 和 check，如何生成相关的 assertion，以及几种 checker 的学习。

## 一、先把“好的评估”说清楚

终于要开始第一部分的完善了：如何根据一个 `SKILL.md` 给出评估维度和对应的断言。

但直接上来生成 case 或 assertion 其实有点危险。因为评估这件事不是中立地“测一下”，它一定服务于某个决策。对这个工具来说，评估结果不是为了给 skill 排名，也不是为了证明某个 prompt 写得漂亮，而是为了决定：

> 这次自动优化能不能 promote？

所以一个好的评估至少要先想清楚这些事：

1. **评估服务于什么决策。**  
   我这里的决策就是：candidate skill 是否比当前 skill 更值得被采用。

2. **评估对象的边界是什么。**  
   现在容易混的是：被测对象到底是 prompt case，还是 skill？我的判断是，最终被测对象应该是 skill。case 只是让 skill 暴露行为的输入。

3. **评估隐含什么价值立场。**  
   评估不是纯客观测量。我的工具所有优化调整，都是朝着更贴合用户真实需求出发。所以我可能并不 care 原 skill 最初的职责范围是什么；我希望他能通过收集 case 来不断拟合用户的实际需求

4. **评估要区分事实、解释和判断。**  
   事实是 trace、产物、文件、工具调用；解释是为什么会这样；判断是好不好、能不能 promote。判断必须严格依赖事实，不能靠“感觉这次像是变好了”。

5. **评估不是寻找绝对真相，而是降低决策不确定性。**  
   尤其是让 LLM 自动优化 skill 时，不能让它永远在一个很小的局部范围里打补丁。评估结果除了给建议，还应该告诉它信心程度、缺哪些证据、下一步怎么验证。（我比较担心的是优化收敛到局部最优：而不敢去做大的改动，同时需要注意 skill 不应该过于约束，少点 MUST / NEVER，多点 why）

6. **评估有三类：判定、诊断、改进。**  
   判定是好不好、过不过；诊断是问题在哪里；改进是下一步怎么变好。我的工具明显是改进向，所以不能只输出一个分数，还要能指向具体改哪里。

7. **评估维度本身也要有好坏定义。**  
   什么证据算好？什么算一般？什么算差？如果没有这个定义，后面的 assertion 只是把模糊判断换了个名字。

8. **好评估要有反例意识。**  
   有没有一种情况，评分很高但实际很糟？在 skill 优化里，这个尤其重要。一个 candidate 可能靠过度贴合几个 case 拿高分，但抽象能力变差了。（所以我这里拆分了 train/test）

9. **评估系统本身也要被评估。**  
   这个很重要。否则工具会变成“用一套没人检查的评估去检查 skill”，最后只是把不确定性藏起来。

10. **想清楚用什么方法收集证据。**  
    是看 final output？看 trace？看文件产物？看工具调用？不同证据源能支撑的判断不一样。

写任何的评估工具，感觉可以都按照这个明确回答下，这是好的评估的需要先明确的问题，我也是按照这个一个一个会回答明确的

## 二、prompt -> assertion，还是 维度 -> case -> assertion？

这里是当前项目的第一个困惑点。

我想到的两种路线大概是：

```text
prompt -> assertion
```

直接生成 prompt case，然后针对每个 prompt 动态生成 assertions。`promptfoo` 和 `skill-creator` 基本都更靠近这个方式。

另一种是：

```text
维度 -> case -> assertion
```

先从 `SKILL.md` 抽稳定评价维度，再生成 cases 去覆盖这些维度，最后给每个 case 生成断言。

这两条路线的差别，本质上是：

> 要不要用维度去约束 prompt 的生成？

我拿自己的 `repo-theme-extract` skill 想了一下。它是一个“从大仓库抽主题精读样本”的工作流 skill。它的好坏不只是“有没有下载文件”，而是：是否能把一个庞大仓库压缩成一组可读、可对照、可练习的主题材料。

如果先定义评估维度，我大概会分成几类：

- 召回率和误召回率：主要看 name + description，尤其是 description 的触发边界。
- 流程是否按预期进行：有没有跳步，有没有少做研究、抽取、翻译、注释、阅读指南这些动作。
- 最终产物是否满足要求：主题是否界定清楚，文件是否少量必要，覆盖是否完整，翻译和学习注释是否准确。

但再仔细想，除了正反 case 需要在 prompt 生成阶段提示一下，其他很多维度并不真的影响 prompt 怎么生成。

比如“学习注释是否准确”，它更像一个输出检查项；“是否少量必要”，也更像结果判断。它们不一定要提前指导 case 生成。

所以目前的判断是：

> 先有维度不一定是为了指导 prompt 生成，它更可能是和 case 生成并行存在。

也就是说，case 可以先按使用路径生成，维度可以从 `SKILL.md` 的 Workflow / Guardrails / Completion Criteria 抽出来。真正汇合的地方，是 assertion 生成。

## 三、promptfoo 的启发：它先生成用户画像

接下来读 `promptfoo` 的 case synthesis。这个项目简要说就是用于评估 LLM 应用程序，也做红队演练。（这个项目背后的公司也被 OpenAI 收购了，所以应该还是非常不错的实现。）

它的 case 输入大概包括：

- 要测试的 prompt 模板
- 已有测试样例（避免重复）
- 额外生成要求
- 要生成几个用户画像
- 每个用户画像生成几个 case
- 使用哪个模型

它的 pipeline 很有意思：

```text
prompt 模板
  -> 生成用户画像
  -> 从 prompt 模板抽变量
  -> 结合用户画像、变量名、已有 tests 生成 case
```

第一步不是直接生成 case，而是先生成几种可能的目标用户。

这个设计背后是：不同用户画像会带来不同的测试输入分布。比如同一个客服机器人，普通用户、恶意用户、企业管理员、内部运营人员问出来的问题会很不一样。

但我的工具有一点不一样。我不是希望一个 skill 被优化得足够泛化，满足很多不同用户的要求。相反，我更希望这个工具能在用户使用中，不断把 skill 贴合到这个用户自己的需求。

换句话说，同一个原始 skill + 同一个优化工具，在一千个用户自己的使用下，最后可能变成一千个不同版本。

所以这里给我的启发不是“必须维护一组用户画像”，而是另一个问题：

> 要不要维护用户对这个 skill 的长期倾向？

因为这实际就是工具要把 skill 优化去拟合的方向。

我现在的判断是：用户倾向需要被保存，但不一定要单独抽成一份画像文件。因为我的工具本来就会沉淀用户真实使用 case，这些 case 本身应该能反映用户倾向。

但这里还有个未完全想透的问题：如果 case 留存足够完整，是否还需要显式存一份“用户偏好画像”？（现在看到的项目大多不存 case，而是动态生成；如果不存 case，可能就一定需要用户倾向持久化。但如果像我这样收集真实 case，用户倾向也许可以从 case 池里自然长出来。）

## 四、assertion 的关键：先决定检查什么

promptfoo 的 assertion 生成流程，我觉得是这一篇最关键的部分。

核心流程是：

```text
prompts + existing assertions
  -> 生成 evaluation question
  -> 判断每个 question 能否转成 Python 确定性检查
  -> 能转：生成 type: python assertion
  -> 不能转：生成 type: llm-rubric / g-eval / pi assertion
```

这句话可以压成一个原则：

> 先决定检查什么，再决定用什么方式检查。

这个顺序非常重要。

很多时候一上来会想“我要用 Python checker，还是 LLM judge？”但这其实是第二步。第一步应该是：

> 对这个 case 来说，什么事实或质量判断能支撑最终决策？

只有先把 evaluation question 想清楚，才知道它适合用什么 checker。

好的 assertion 应该满足几个条件：

- **objective**：尽量客观，把模糊标准改成可判断标准。
- **atomic**：一次只测一个东西。
- **independent**：避免重复，不要两个 assertion 测同一个东西，重复扣分。(尽可能分离真的挺重要，多个 assertion 测同一个维度，相当于给这个维度更高的权重了)
- **self-contained**：不依赖外部知识，更多依据当次任务的 trace、output、skill.md。
- **区分 skill 明确写的要求和模型经验补充的风险点**：这是 skill eval 里很特殊的一点。不能把模型凭经验做对的东西误算成 skill 的功劳。
- **给 question 打标签、短标题、来源、类型**：否则后面报告会很难读。
- **判断 question 能不能变成 Python**：如果只看 output 或某个产物就能确定判断，那就不需要语义 judge。

最后这点很聪明。不是盲目使用语义断言，而是先问：

> 这个检查能不能确定性地做？

能确定性做，就用 Python。不能，再交给语义 judge。

## 五、pi / g-eval / llm-rubric：三种语义判断各有位置

这里我还没有完全深入学习三种方式的具体实现（我的工具基本是对这些的简要实现，等后续真实体验了，确认优化点是这里我在升级，感觉最开始没必要太重），但先把当前理解记下来。

### pi：相对比较更稳定

`pi` 可以理解成一种比例不等式判断。它背后的想法来自 LLM-as-a-judge 里一个很常见的发现：

> 让模型直接打绝对分数不稳定，但比较两个答案哪个更好更可靠。

它会把实际输出和参考答案作为 A/B 候选，让模型判断哪个更好，并交换位置两次取平均，消除位置偏差。最后得到一个 0-1 的概率值，表示实际输出相对参考答案的胜率。

这种方式适合通用问答、摘要质量、RAG 等场景。它的优势是相对稳定，尤其是比“你给这个回答打几分”更靠谱。

### g-eval：适合复杂维度

`g-eval` 更像是让 LLM 按照一组评估步骤推理后打分。它适合那些标准比较复杂、需要拆步骤的判断。

比如：

```text
1. 是否覆盖所有要点
2. 是否有幻觉内容
3. 逻辑是否连贯
```

对 skill 来说，流程完整度、scope 控制、学习注释质量，可能都更适合这种方式。它不是简单问“过没过”，而是希望 judge 能沿着几个明确标准看。

### llm-rubric：最自由，也最要小心

`llm-rubric` 最接近自然语言测试用例。你直接写一段期望，让 LLM 判断是否满足。

比如：

```text
回答应当用中文，且不超过 3 句话，不包含任何代码。
```

它的好处是快，坏处也明显：自由度太高，稳定性不如 pi 和 g-eval。

所以我的直觉是：

```text
能 Python 就 Python
需要相对比较就 pi
复杂评分维度用 g-eval
快速语义约束才用 llm-rubric
```

这部分后面真正开始写 checker 组件时还要继续拆。

## 六、assertion 必须落盘

接下来还有一个决定：assertions 必须写入文件。

原因很简单：

> 评估标准必须落盘，否则评估不可复现，也不可被评估。

如果每次运行时临时让模型生成 assertion，然后直接拿去判断，最后只留下一个分数，那其实没人知道这次到底检查了什么。（而且我在想 assertion 的复用性，因为它是根据 skill 和 case 生成，所以如果调优的第一次，修改后的没有比过，那么其实可以不用修改 assertion，只有全局的 skill 被修改了才会清除）

所以更合理的是：

```text
case
  -> evaluation questions
  -> assertions
  -> cases.with-assertions.json
  -> checker 执行
```

生成和执行要分离。

assertion 不是靠自己执行自己，而是靠 `type` 分派到对应 checker：

```text
python      -> deterministic checker
llm-rubric  -> rubric judge
g-eval      -> step-based judge
pi          -> pairwise judge
```

## 七、现在的方向：维度和 case 并行，assertion 汇合

整理到这里，当前方案大概清楚了：

```text
SKILL.md
  -> 抽评价维度

SKILL.md + 历史 case + 用户真实使用
  -> 生成 / 收集 case

case + 评价维度
  -> 生成 evaluation questions
  -> 转成 assertions
  -> checker 执行
  -> aggregation
  -> semantic analysis
  -> optimizer

case 并行再跑
```
case 和维度并行生成（但我当前没有做维度这块，列为 TODO 吧，后续我还是想 skill 新老版 pk 的时候，能更细度一点，这里可能会用到维度划分），然后 case 测试和 assertion 并行跑，因为这两个也没有依赖关系
