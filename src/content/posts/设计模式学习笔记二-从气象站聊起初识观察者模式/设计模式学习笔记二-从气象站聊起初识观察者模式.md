> 继续设计模式系列。这一章是观察者模式，案例换成了气象站。写之前我又陷入了那个反复在想的问题：vibe coding 越爽，越觉得需要在 AI 协作流程里加一份代码工程架构文档，把核心设计的那 20% 拿回到人这边来。

## 写在前面：vibe coding 还要不要补一份架构文档？

最近在学设计模式的时候，我一直在想一件事：**怎么把设计模式真正融进 vibe coding 的流程里**。

我现在做校内项目和自己的项目，基本是纯 vibe——只看跟 AI 交互的文档，而这些文档基本只记载需求、验收标准、职责范围，几乎不涉及代码工程架构本身。我隐隐觉得，可能**需要再加一份"代码工程架构文档"类似的东西**。

这样做的代价当然是：工作量又回来了一部分。但我目前的判断是，这件事仍然值得做。

我的思路是这样的：

> 先学会**如何在与 AI 协作中创造出好的工程**，再慢慢思考如何把工程思想嫁接到 AI 上。

换句话说，从 100% vibe coding 退一步，让**人重新承担一部分核心代码设计的工作**——大约 20% 左右的核心部分——然后再随着方法论沉淀，慢慢提高 AI 承担的范围。

设计模式的学习就是这"20%"里非常重要的一块基本功。带着这个心态，进入第二章。

## 观察者模式：一句话定义

> **定义对象之间一对多的依赖：当一个对象（主题 Subject）改变状态时，它所有的依赖者（观察者 Observer）都会收到通知并自动更新。**

这个定义本身不复杂，但要看清它"为什么是这样设计的"，最好还是顺着一个具体场景推演一遍。

## 场景设定：气象站

这一章的案例来自《Head First 设计模式》的气象站：

- 已经有一个专有的 `WeatherData` 对象，负责追踪当前的天气情况
- 现在希望基于它做一个应用，提供三种布告板：
  - 当前状况显示
  - 气象统计显示
  - 简单预报显示
- 布告板必须**实时更新**
- 同时希望气象站是**可扩展**的，能对外公布一组 API，让其他开发者也能写出自己的布告板

`WeatherData` 类已经有 getter 方法可以取得温度、湿度与气压三个测量值，并且当新的测量数据备妥时，框架会调用它的 `measurementsChanged()` 方法。我们要写的，就是这个方法的实现。

## 初版实现：所有问题都堆在一起

最直觉的写法：

```java
public void measurementsChanged() {
    float temp     = getTemperature();
    float humidity = getHumidity();
    float pressure = getPressure();

    // 三个布告板都要刷新一次
    currentConditionsDisplay.update(temp, humidity, pressure);
    statisticsDisplay.update(temp, humidity, pressure);
    forecastDisplay.update(temp, humidity, pressure);
}
```

看起来短小直接，但仔细一看，**两个老问题全踩了**：

1. **针对具体实现编程，而不是针对接口编程**。
   `update()` 没有抽象成一个接口，三个具体布告板被硬编码在 `measurementsChanged()` 里。
2. **变化的部分和不变的部分混在一起**。
   "怎么取数据"是相对稳定的，"有哪些布告板要被通知"是会频繁变化的——可能新增、可能下线、可能由第三方接入——但它们现在被搅在了同一个方法里。

第一章学策略模式的时候已经反复见过这两个反模式了。**把变化的部分独立出来 + 针对接口编程**，几乎是所有设计模式背后的同一条主线。

## 引入观察者模式：四个角色

观察者模式的结构其实非常对称，一共就四个角色：

| 角色 | 职责 |
|---|---|
| **Subject 接口** | 定义"如何注册 / 撤销观察者，如何通知所有观察者"的契约 |
| **Observer 接口** | 只定义一个 `update()` 方法，主题状态变化时被调用 |
| **ConcreteSubject 具体主题** | 实现 Subject 接口，持有观察者列表，状态改变时挨个 `update()` |
| **ConcreteObserver 具体观察者** | 实现 Observer 接口，向具体主题注册自己以获取更新 |

用伪代码勾一下结构：

```java
// 主题接口：管理观察者 + 通知
public interface Subject {
    void registerObserver(Observer o);
    void removeObserver(Observer o);
    void notifyObservers();
}

// 观察者接口：只关心"我被通知了之后做什么"
public interface Observer {
    void update(float temp, float humidity, float pressure);
}

// 具体主题：WeatherData
public class WeatherData implements Subject {
    private List<Observer> observers = new ArrayList<>();
    private float temperature, humidity, pressure;

    public void registerObserver(Observer o) { observers.add(o); }
    public void removeObserver(Observer o)   { observers.remove(o); }

    public void notifyObservers() {
        for (Observer o : observers) {
            o.update(temperature, humidity, pressure);
        }
    }

    // 数据备妥时由框架调用
    public void measurementsChanged() {
        notifyObservers();
    }
}

// 具体观察者：某个布告板
public class CurrentConditionsDisplay implements Observer {
    public CurrentConditionsDisplay(Subject weatherData) {
        weatherData.registerObserver(this); // 自己来主题这边登记
    }
    public void update(float temp, float humidity, float pressure) {
        // 刷新自己的显示
    }
}
```

对照初版实现，关键的几处变化：

- `measurementsChanged()` 不再列举具体布告板，只调用 `notifyObservers()`
- 三个布告板对 `WeatherData` 来说都"长一个样"——都只是 `Observer`
- 新增第四种布告板时，**`WeatherData` 一行不用改**，第三方只要写一个新的 `Observer` 实现，往里 `registerObserver()` 一塞就行

> **主题是真正拥有数据的人，观察者只在数据变化时被动更新。** 比起让一堆对象互相操控同一份数据，这是更干净的 OO 设计。

## 为什么这是"松耦合"的胜利

观察者模式经常被作为"松耦合"的范例，原因可以拆成几条：

- 主题**只知道观察者实现了一个接口**，并不知道它们的具体类型
- 任何时候都可以增加或删除观察者，主题完全不需要被修改
- 改变主题或者改变某个观察者，只要接口契约不变，**两边互不影响**

回过头来看 OO 设计原则，这个模式至少踩中了三条：

- **开闭原则**：加新布告板不动 `WeatherData`，对扩展开放、对修改关闭
- **依赖倒置**：`WeatherData` 依赖 `Observer` 接口，而不是任何具体布告板
- **针对接口编程**：主题和观察者之间唯一的契约就是接口

这也是为什么前一章在策略模式之后接观察者模式——它们都在反复强化同一组原则，只是从"行为替换"换到了"事件广播"这个角度。

## 推 vs 拉：一个容易被忽略的小分支

观察者模式还有个**实现层面**的分叉：通知的时候，是主题**推**数据给观察者，还是观察者从主题**拉**数据？

| 维度 | 推（Push） | 拉（Pull） |
|---|---|---|
| 形式 | `update(temp, humidity, pressure)` 把数据一口气推过去 | `update(Subject s)`，观察者自己用 `s.getXxx()` 取需要的字段 |
| 优点 | 调用一次拿到全部，简单直接 | 每个观察者按需取数，互不干扰；新增字段不影响老观察者签名 |
| 缺点 | 观察者签名被绑死，新增字段要改所有人；不需要的数据也得收 | 多一次方法调用；观察者要懂主题的 getter 语义 |
| 适合 | 观察者种类少、需要数据高度一致 | 观察者种类多、各自感兴趣的字段不同 |

我自己的体感是：**早期可以推，后期等观察者一多就该考虑切到拉**。这其实又是一个"未来可能变化的点"——和第一章那条"找出可能需要变化的部分，把它独立出来"完全是同一类思考。

## 我从这一章拿到的最大收获

策略模式让我意识到**"行为是可以被替换的"**，观察者模式则让我意识到**"事件是可以被广播的"**。

更抽象一点说，它们其实都在做同一件事——**把"谁来定义" 和 "谁来使用"解耦**：

- 策略模式：使用者持有一个接口，**定义者**是各种行为实现类
- 观察者模式：主题持有一组接口，**定义者**是各种观察者实现类

当你脑子里有了这种"通过接口把两边解开"的本能之后，回头去看自己以前写的代码（包括以前指挥 AI 写的代码），会很容易看出哪些地方是把"会变的东西"和"不变的东西"焊在一起了。

## 再回到 vibe coding

写到这里我突然想到一个具体的应用方式。

如果我真的要在 AI 协作流程里加一份"代码工程架构文档"，那这份文档里该写清的，可能是这两件事：

1. **系统里有哪些"会变"的点**——是否对应一组接口
2. **系统里有哪些"广播 / 订阅"关系**——谁是主题、谁是观察者、走推还是拉

这两件事一旦在文档里说清楚，AI 在落地的时候就有了明确的结构约束，而不只是"按需求堆功能"。换句话说，**设计模式的语言，正好就是我和 AI 之间最好的工程对话语言**。
