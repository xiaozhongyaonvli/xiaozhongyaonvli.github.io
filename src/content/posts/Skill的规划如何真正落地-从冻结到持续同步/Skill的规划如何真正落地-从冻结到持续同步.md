> 很多 agent 或 skill 系统都说自己“有规划能力”，但这里真正值得追问的问题其实不是“会不会先列步骤”，而是：规划到底能不能在执行过程中持续生效，能不能防止任务跳步、能不能限制执行边界、能不能在多 agent 协作时维持唯一真相。

基于我对 `Vibe-Skills` 和 `planning-with-files` 两个项目的学习，我现在更倾向把“规划”理解成一套执行治理机制，而不是开工前的一段思考。

这篇文章不想做“谁优谁劣”的比较，而是想回答两个问题：这两个项目分别是怎么把规划落地的，以及它们共同说明了什么。

## 一、两个项目分别怎样让规划真正参与执行

### 1. `Vibe-Skills`：把规划做成受治理运行时的一部分

`Vibe-Skills` 最关键的一点，是它并不把规划理解成一个独立文档，而是把规划嵌进一条正式的受治理运行时链路里。对用户来说，入口只有一个 `vibe`；但在内部，它会按固定阶段推进：先做上下文检查，再做意图澄清，再冻结需求，再生成执行计划，最后才进入执行与清理。

这意味着，在这个项目里，规划的起点不是“我先想个 plan”，而是“我先把任务放进一个受治理的状态机里”。真正承担规划职责的，主要是 `deep_interview`、`requirement_doc` 和 `xl_plan` 这几个阶段。

- `deep_interview` 负责把用户原始意图整理成结构化契约，包括目标、交付物、约束、验收条件、非目标和假设。
- `requirement_doc` 负责把需求冻结成后续执行唯一可回溯的依据。
- `xl_plan` 负责从冻结后的需求继续派生出执行计划，并明确验证命令、回滚规则、阶段清理预期和 ownership boundaries。

这里最重要的不是“文档更多了”，而是执行合法性的来源发生了变化。后续实现不再直接依赖聊天上下文，而必须回溯到已经冻结的 requirement 和 plan。也就是说，规划不再是对执行的建议，而是执行的前置条件。

`Vibe-Skills` 进一步把这种约束推进到了权限层。它不仅冻结需求和计划，还会先冻结运行时输入包，把当前的路由结果、治理作用域、可用权限、专家技能调度状态都固定下来。这样一来，所谓“跑偏”就不只是做错事，还包括用错误的身份做事，或者在没有授权的情况下扩张执行边界。

这也解释了它为什么非常强调 root 和 child 的区分。root 可以冻结 canonical requirement 和 canonical plan，可以发布最终完成声明；child 只能继承这些冻结结果，写本地回执，不能再生成第二套 requirement、第二套 plan，也不能重新解释任务完成。对于多 agent 协作来说，这一点非常重要，因为很多系统表面上看是在分工，实际上却是在悄悄制造多套真相源。

所以从规划落地的角度看，`Vibe-Skills` 走的是一种更强治理的路线：先冻结目标真相，再冻结执行边界，最后才允许执行发生。它试图解决的不是“怎么列步骤”，而是“如何让后续执行没有机会绕开规划”。

### 2. `planning-with-files`：把规划做成持续维护的外部状态

`planning-with-files` 的做法没有那么“运行时治理化”，但它解决的是另一个同样关键的问题：即使一开始写了计划，执行过程中也很容易把计划丢掉。

它的核心思路是，把规划外部化成一组持续维护的文件，而不是让计划停留在脑内或者短期上下文里。最典型的是三份文件：

- `task_plan.md` 负责目标、阶段、关键问题、决策和错误。
- `findings.md` 负责调研证据和阅读结论。
- `progress.md` 负责执行过程和进度日志。

这个设计背后有一个很清楚的判断：执行之所以会跑偏，很多时候不是因为没有计划，而是因为计划没有持续参与执行。工具调用一多，目标会被挤出上下文；研究内容只看不记，后面就会丢；状态不更新，计划和现实就会脱节；会话一中断，下一轮执行就可能从错误位置继续。

所以它做的不是“冻结”，而是“持续同步”。在执行前，hook 会回读 `task_plan.md`，把计划重新推回当前上下文；在调研过程中，它用类似 `2-Action Rule` 的规则要求把关键信息及时写入 `findings.md`；在执行后，又会提醒更新 `progress.md` 和阶段状态；在任务结束前，还会检查是否仍有 `pending` 或 `in_progress` 项，避免在“感觉差不多了”的状态下草率收尾。

这套机制的关键价值，在于它把规划从“一次性设计物”变成了“伴随执行更新的外部记忆”。它并不强求一开始把一切冻结完毕，而是不断把目标、证据和状态重新注入执行链条里。

因此，`planning-with-files` 对规划的贡献不在于强控制，而在于高频校正。它不是严格意义上的硬门禁系统，更像是一套把模型不断拉回计划中心的运行习惯系统。它的重点不是宣布“你不允许偏离”，而是尽量降低偏离发生的概率，并在偏离发生后，尽快把状态重新拉回可控范围。

如果说 `Vibe-Skills` 更像是在回答“规划怎样成为执行的治理边界”，那么 `planning-with-files` 更像是在回答“规划怎样持续驻留在执行现场，而不是写完就失效”。

## 二、对 skill 路径更有价值的，不是二选一，而是它们共同揭示的方法

把这两个项目放在一起看，我觉得真正值得提炼的不是差异本身，而是它们其实都在把同一件事做实：规划不能只存在于模型的临时上下文里，必须变成外部化、可验证、可继承、可约束执行的真实对象。

### 1. 规划必须写入文档，而不是停留在聊天历史里

这是两个项目最明显的共同点。

在 `Vibe-Skills` 里，这些文档表现为 requirement、plan、intent contract、cleanup receipt 等正式工件；在 `planning-with-files` 里，它们表现为 `task_plan.md`、`findings.md`、`progress.md` 这样的长期工作文件。两者形式不同，但方向一致：规划要离开脑内，变成外部可读、可检查、可回溯的状态。

只要规划不落盘，它就只是当下这一轮上下文里的“好主意”；而不是后续执行可以真正引用的依据。

### 2. 规划必须约束执行，而不是只在执行前出现一次

这也是两个项目都非常明确的一点。

`Vibe-Skills` 的方式是冻结。先冻结 requirement，再冻结 plan，之后执行必须沿着受治理阶段继续，不能直接跳进 ad-hoc coding。子 agent 也只能继承，而不能重新解释这些冻结结果。

`planning-with-files` 的方式是同步。执行前回读计划，调研后外部化发现，写入后更新状态，结束前检查完成度，会话恢复时重新注入当前阶段。

看起来一个更硬，一个更软，但它们想解决的问题是同一个：规划不能只在开头出现一下，然后把后面的执行完全放飞。

### 3. 规划必须留下验证材料，而不只是留下结论

这两个项目都不是只写“决定了什么”，而是会同时留下“为什么这么决定”和“如何验证已经做到”。

在 `Vibe-Skills` 中，这体现在 verification commands、rollback rules、cleanup receipts，以及对 no silent fallback、no silent degradation 的强调。它希望系统不仅能说“完成了”，还要说清楚“凭什么算完成”。

在 `planning-with-files` 中，这体现在 `findings.md`、错误记录、阶段状态和 stop/check 机制里。它同样要求把依据留在文档里，而不是让执行过程只剩一个模糊的最终结果。

对 skill 路径来说，这一点非常关键。一个真正有规划能力的系统，不应该只是生成漂亮的步骤列表，而应该顺带生成后续验证所需的证据结构。

### 4. 规划不只是任务分解，还包括真相面和权限面的定义

这一点在做多 agent 协作时尤其重要。

很多系统会认为“规划”就是拆阶段、列任务、分工给子 agent。但 `Vibe-Skills` 很清楚地提醒了另一件更重要的事：谁有权冻结需求，谁有权扩展计划，谁有权宣布完成，谁只能继承和执行，这些都属于规划的一部分。

`planning-with-files` 虽然没有把权限治理做到这么强，但它至少也在做另一种真相面管理：目标、发现和进度分文件维护，避免所有信息挤在一个平面里，减少执行阶段对计划的误读。

也就是说，规划不只是“做什么”，还包括“什么算唯一真相”以及“谁能改动这份真相”。

### 5. 子 agent 不应该重写规划，只应该继承规划

这是我觉得最值得带回 skill 设计里的经验。

一旦允许子 agent 自己重新写需求、重新解释计划、重新定义完成条件，整个系统很快就会从“分布式执行”退化成“分布式漂移”。表面上大家都在努力推进，实际上每个节点都在沿着不同的任务定义前进。

`Vibe-Skills` 把这个问题讲得最透，它明确禁止 child 生成第二套 canonical requirement 和 canonical plan。`planning-with-files` 虽然没有用 root/child 语义表达，但它通过持续回读 `task_plan.md` 和同步状态，事实上也在做同一件事：后续动作应该继承当前计划，而不是另起一个隐形计划。

所以如果要把这条经验翻译成一句更抽象的方法论，我会写成：

**规划应该是执行链条共享的上游真相，而不是每个执行单元各自临时生成的局部解释。**

### 6. “冻结”和“动态维护”不是对立关系，而是两种治理强度

这也是我现在最大的体会。

很多时候我们会把方法分成两类：一种是严格治理，一种是灵活迭代。但从这两个项目看，更合理的理解可能是，它们都在做“规划外部化并持续约束执行”，只是治理强度不同。

- 当任务复杂度高、涉及多 agent、需要明确权限边界时，更适合采用冻结式治理。
- 当任务更强调长期推进、持续调研和频繁上下文恢复时，更适合采用动态同步式治理。

两者不是互斥关系。相反，一个成熟的 skill 路径，往往需要同时吸收两边的优点：既有冻结后的 canonical truth，也有执行过程中的状态同步和证据回灌。

## 结语

如果只用一句话概括这次阅读带给我的收获，我会这样总结：

**规划不是执行前的准备动作，规划本身就是执行系统的一部分。**

一旦接受这个前提，很多设计问题都会重新变得清晰起来。你不会再只问“如何把任务拆成步骤”，而会开始问：

- 这份规划是否已经外部化为可追溯文档？
- 后续执行是否必须继承这份规划？
- 子 agent 是否被禁止重写 canonical truth？
- 当前状态、调研发现和验证证据是否都能持续回写？
- 系统最终宣称“完成”时，是否能拿出对应的工件和依据？

从这个角度看，`Vibe-Skills` 和 `planning-with-files` 其实都在做同一类工作：努力把“规划”从一种会消散的上下文能力，变成一种可以治理执行、限制偏离、留下证据并支撑协作的外部结构。

这也是我现在理解 skill 路径时最想抓住的一点：真正难的不是让模型先想一想，而是让“想清楚的结果”在后续所有动作里都持续有效。
