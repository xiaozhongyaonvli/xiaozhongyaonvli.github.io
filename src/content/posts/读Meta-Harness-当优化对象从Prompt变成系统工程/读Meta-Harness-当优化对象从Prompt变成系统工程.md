> Meta-Harness 最值得关注的地方，不是又提出了一个新的提示词优化技巧，而是把 LLM 系统优化从 prompt 推到了完整的 harness 工程：保存历史、读取 trace、比较版本、改代码并持续迭代。

论文：*Meta-Harness: End-to-End Optimization of Model Harnesses*  
作者：Yoonho Lee, Roshen Nair, Qizheng Zhang, Kangwook Lee, Omar Khattab, Chelsea Finn  
时间：2026 年 3 月 30 日  
项目页：https://yoonholee.com/meta-harness/  
代码/产物：https://github.com/stanford-iris-lab/meta-harness-tbench2-artifact

这篇论文最打动我的地方，不是它又提出了一个新的提示词优化技巧，而是它把一个更底层的问题摆到了台面上：LLM 系统的能力不只取决于模型本身，还取决于包在模型外面的那层代码，也就是论文里说的 `harness`。

所谓 harness，可以理解成模型的运行脚手架。它决定哪些信息要被存下来，什么时候检索，如何组织上下文，怎样把信息展示给模型，以及每一步之后如何更新状态。论文开头提到，同一个固定模型，只是换一套 harness，在同一个 benchmark 上就可能产生最高 6 倍的性能差距。这个观察很重要，因为它把问题从“模型够不够强”转向了“系统有没有把模型用好”。

过去我们谈优化 LLM 应用，常见抓手是 prompt、RAG、few-shot 示例、工具调用模板，或者更重一些的微调。但 Meta-Harness 的视角更像一个系统工程师：既然 harness 本身是一段可执行程序，那为什么不直接让一个 coding agent 去搜索、调试、重写这段程序？

## 1. 这篇论文到底在优化什么？

Meta-Harness 优化的不是模型权重，也不是单条 prompt，而是完整的任务级 harness 实现。论文把 harness 定义成一个包裹固定语言模型的有状态程序。给定任务输入后，harness 负责构造提示词、调用模型、处理返回、更新内部状态，并最终产出任务结果。

因此，优化目标不是“找到一句更好的提示词”，而是“找到一套让固定模型在目标任务分布上表现更好的程序”。当任务涉及长程状态、检索、记忆、路由、多轮交互时，这个区别非常大。

传统文本优化方法的问题在于反馈太薄。OPRO、TextGrad、GEPA、OpenEvolve 这类方法各有价值，但很多方法依赖标量分数、短摘要、固定模板反馈，或者只看当前候选体。对于简单 prompt 优化，这可能够用；但对 harness 工程来说，一个错误的状态更新、检索策略或上下文裁剪规则，可能要在很多步之后才表现为最终失败。把执行过程压缩成一个分数，等于把最有诊断价值的信息扔掉了。

Meta-Harness 的核心判断是：harness 优化需要“可追溯的历史经验”，而不是被提前压缩好的反馈。

## 2. Meta-Harness 的搜索循环

论文中的 Meta-Harness 外循环很朴素，但设计很关键：

1. 一个 coding agent 作为 proposer，读取文件系统里已有候选 harness 的源代码、评估分数和执行轨迹。
2. proposer 根据这些历史材料提出一个新的 harness 实现。
3. 系统在搜索集上评估这个候选 harness。
4. 新候选的代码、分数、推理过程、执行 trace 被写回文件系统。
5. 下一轮继续。

这里最关键的工程选择是“文件系统”。Meta-Harness 没有把所有历史强行塞进一个超长 prompt，而是把它们组织成可查询的目录结构。proposer 像普通程序员一样使用 `grep`、`cat`、diff 等工具选择性阅读历史材料。论文说，在最复杂的设置中，一次评估可以产生最高 1000 万 token 的诊断信息；proposer 在一个迭代中位数会读取 82 个文件，并引用 20 多个历史候选。这已经不是普通 prompt optimizer 的工作负载，而更像一个带日志仓库的自动化调试系统。

这也是我读这篇论文时最强烈的感受：它把“上下文管理”从提示词技巧推进到了工程基础设施。历史不是一段 summary，而是一套可导航、可比较、可复盘的文件系统。

## 3. 为什么 coding agent 比单次 LLM 调用更合适？

如果只是让模型一次性读完历史，然后输出新 prompt，Meta-Harness 的意义会小很多。论文强调 proposer 是 coding agent，而不是裸 LLM，这一点有实际原因。

harness 搜索中的信息量远超上下文窗口。agent 必须决定读什么、不读什么，必须能检查代码结构，必须能定位失败样本，必须能把新的想法落成可执行代码，还要在正式评估前通过轻量验证。这个过程天然接近软件开发：看日志、猜原因、改代码、跑测试、比较结果。

论文里的接口验证也很工程化。候选 harness 在进入昂贵评估前，先要通过小型验证脚本，例如检查能否 import、类能否实例化、方法能否在少量样本上跑通。这个细节看起来不炫，但很重要：自动搜索最怕把预算浪费在低级不可运行候选上。Meta-Harness 把“先做廉价 sanity check”放进流程里，说明作者不是只在讲概念，而是真正在跑一套工程系统。

## 4. 三个实验场景：它学出了什么？

论文选了三个任务族：在线文本分类、检索增强数学推理、agentic coding。它们覆盖了比较典型的 LLM 系统问题：上下文管理、检索路由、终端环境交互。

**在线文本分类。**  
Meta-Harness 在文本分类任务中学出了一种“草稿-验证”机制。系统先用很少上下文给出一个初始标签，再围绕这个标签去检索支持和反对的证据，最后再修正判断。这个设计的味道很像人类做分类时的流程：先形成假设，再找证据验证，而不是一开始就把大量上下文全塞进去。论文报告它相对 ACE 提升 7.7 个点，同时上下文 token 用量少了 4 倍。

**IMO 级数学推理。**  
在数学检索任务里，Meta-Harness 学出了一套面向题型的检索路由。它会根据组合、几何、数论、代数等线索选择不同检索策略。论文报告，一个被发现的 harness 在 200 道 IMO 级问题上，跨 5 个未参与搜索的模型平均提升 4.7 个点。这里的重点不是“数学题多检索几条参考答案”，而是检索策略被程序化了：先判断问题类型，再决定该从什么索引、用什么规则拿上下文。

**TerminalBench-2。**  
在 agentic coding 场景中，Meta-Harness 发现了一个非常朴素但有效的策略：环境自举。很多终端 Agent 会在任务前几轮浪费 token 去摸环境，比如 OS、语言版本、文件结构、已安装工具。优化出的 harness 会在任务开始前主动采集环境快照，再把关键信息注入初始上下文。论文报告该 harness 在 TerminalBench-2 上超过了当时已有的 Haiku 4.5 agent harness，并在图中给出 37.6 的 pass rate。

这三个案例的共同点是：提升来自系统策略，而不是模型突然变聪明。它们都在回答同一个问题：应该在什么时候把什么信息交给模型。

## 5. 我最在意的部分：失败归因能力

原草稿里提到附录 A.2，我也觉得这是最值得反复看的部分。Meta-Harness 的 proposer 在面对分数下降时，不只是机械地产生新变体，而是会回到历史 trace 里找原因。

一个典型过程是：早期迭代里，agent 同时改了 bug 修复和 prompt 模板，结果分数下降。后来它通过查看原始执行轨迹发现，问题并不只是代码 bug，而是新的 prompt 模板改变了状态保留方式，导致某些状态在任务完成前被删除。也就是说，一个看似有益的结构修复，被另一个有害的 prompt 改动混淆了。后续它转向更保守的“纯加法”策略：不大幅改控制流，只把环境快照注入初始 prompt。

这段让我意识到，Meta-Harness 真正想证明的不是“LLM 会写代码”，而是“当反馈足够完整、历史足够可查询时，agent 可以做跨迭代的失败归因”。这对自动化优化非常关键。没有原始 trace，系统只能知道“这个候选分数低”；有了 trace，系统才可能回答“为什么低、是哪一步改坏了、下次应该避开什么”。

## 6. 对开发者的几个启示

**第一，日志要记录过程，不只记录结果。**  
很多 LLM 应用只保存最终输入、最终输出、最终分数，这对调试太薄了。Meta-Harness 的经验说明，真正有价值的是完整执行轨迹：每一步 prompt、模型输出、检索内容、状态更新、工具调用、失败样本。只有这些信息存在，后续 agent 或人类开发者才有机会做归因。

**第二，把上下文当作可查询资产，而不是一次性 prompt。**  
当历史材料很大时，不要试图压缩成一个万能摘要。更好的做法是把它组织成结构化文件、JSON、目录、索引和小型 CLI，让 agent 能按需读取。论文附录的实践建议也提到：合理命名、机器可读格式、可 grep 的日志、能查看 Pareto frontier 和 diff 的小工具，都能显著改善搜索质量。

**第三，优化集要小而有区分度。**  
Meta-Harness 不建议一上来就用巨大搜索集。作者建议先有一个简单 baseline，然后构造 baseline 会犯错的困难样本；分类任务里大约 50-100 个样本，数学检索里用了 88 个问题。原因很现实：搜索集要快，且必须能区分候选好坏。一个慢而钝的大评估，反而会拖垮迭代。

**第四，代码层面的策略通常比 prompt 祈祷更可靠。**  
很多 LLM 应用的问题，本质上是状态管理、路由、检索、缓存、验证和预算控制问题。与其在 prompt 里反复要求模型“请认真使用证据”，不如在 harness 里明确写出证据检索和验证流程。Meta-Harness 的三个实验都在说明这点。

**第五，自动化优化仍然需要工程边界。**  
Meta-Harness 并不是把所有东西丢给模型自由发挥。它仍然需要 skill 文本定义角色、目录布局、命令和输出格式；需要验证脚本拦截坏候选；需要独立评估器写分数；需要搜索集和测试集隔离；需要 Pareto frontier 同时考虑效果和成本。换句话说，好的自动化系统不是“无约束自治”，而是给 agent 一个清晰、可运行、可复盘的工程环境。

## 7. 我的结论

这篇论文给我的最大启发是：LLM 应用的下一层竞争，可能不只是模型能力，而是 harness 工程能力。

当模型被固定住，外部代码仍然有很大的优化空间。这个空间里包含 prompt，但远不止 prompt；它还包含记忆写入、检索路由、状态生命周期、工具调用顺序、上下文预算和失败恢复策略。Meta-Harness 的价值在于，它把这些东西当成一个完整程序来搜索，而不是把它们压扁成一句提示词。

如果把 Agent 系统看作一个软件系统，那么 Meta-Harness 的思路非常直接：保存完整历史，暴露可查询接口，让 coding agent 像工程师一样阅读日志、比较版本、改代码、跑验证、再迭代。它并没有神秘化智能，反而把智能放回了工程流程里。

我觉得这也是这篇论文最值得学习的地方：真正可复用的不是某个发现出来的 prompt 模板，而是一套面向长期反馈、执行轨迹和代码搜索的系统工程范式。
