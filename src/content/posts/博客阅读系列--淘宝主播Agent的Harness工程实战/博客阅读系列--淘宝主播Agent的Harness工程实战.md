## 工作区设计

个人认为该项目的工作区设计是非常值得深入学习的。

它并不是文件系统，也不是单纯的 RAG，而是针对不同的数据选择了最合适的存储后端。接下来将深度分析（仅依靠我和 AI 以及一些当前开源实现来剖析，如有出错，可以发在下方讨论区哈哈）。

这里并没有采用文件系统来存事实。实际上文件系统适合个人助手、单机下，而该 Harness 需要针对海量主播，需要多副本水平扩容，承载高并发的实时读写。

工作区实现，对外的接口支持：

- 加载上下文。
- 读写记忆。
- 调用技能。
- 持久化状态。

抽象的好处是替换内部实现，外部不需要跟着修改。

## 不同数据对应不同后端

这块我理解大概是：

- Holo 表：负责记忆板块，向量 + 全文 + 标量 JSONB 混合检索。
- GitLab 仓库：负责 Skill，包括版本管理、预检、灰度发布。
- MySQL：负责记录会话管理、场次管理、运行时消息、checkpoint 状态。

## Holo 表负责记忆

简单介绍下 Holo，也就是 Hologres 表，实时分析引擎。

它的存储格式可能如下：

```text
id              记忆 ID
user_id         用户 ID
content         记忆原文
embedding       记忆向量
tags            JSONB 标签
memory_type     记忆类型
created_at      创建时间
updated_at      更新时间
importance      重要性分数
```

不同字段能支撑不同检索方式：

- 向量检索：按照语义相似度匹配，但对一些精确词不一定稳定。
- 全文检索：适合精确关键词匹配，专有名词匹配。
- JSONB 标签：结构化过滤，权限隔离，业务条件筛选。

JSONB 是一种字段类型，并不直接将 JSON 当做文本存，而是更适合数据库查询的二进制格式。好处是字段结构灵活，添加标签，不需要频繁修改表结构。

读取记忆时，可以先语义匹配加上全文补充，然后 JSONB 去做过滤，最后重排序。

PostgreSQL 也能实现这三种检索的功能：

- GIN 索引查询 JSON 文档的 kv，倒排索引，类似 ES。
- 内置全文检索。
- 通过 pgvector 扩展支持向量相似度。

Holo 兼容 PG。PG 适合规模和用户量、并发相对较低的情况。如果是更多的文档和高并发，实时写入时考虑 Holo。同时 Holo 的实时分析能力，能够支持海量数据进入后进行实时的复杂分析。

## Skill 为什么用 GitLab 存

Skill 选择使用 GitLab 来存。

这里的原因，我认为可能有这么几个：

1. 一个 Skill 可能包含非常多的文件，包括描述、脚本、校验等，GitLab 适合管理多个文件组成的一个版本快照。
2. diff 的可读性更好，不需要额外的逻辑和新增的处理。
3. CI/CD 可以在上传前做一些校验，比如 schema 合法校验、样例回归测试、脚本语法检查。
4. 回滚是整包回滚。如果使用 SQL 去做版本控制，如果回滚未处理好，可能导致部分回滚。

（其实感觉首先得第一点是明确需求是什么，需要什么样的工具，然后这时候就可以看看当前开源的是否有相符合的一些工具，或者说简易改造就能满足的）

## MySQL 负责会话和状态

会话、状态的管理采用 MySQL。

选型主要考虑：

- 需要状态持久化（Redis 可能可以缓存，但不能够作为持久层，因为它适合的数据是可重建的）。
- 在线频繁地读写。
- 通过事务来保证强一致性。
- 能按照各个 id 来精确查找。
- 由于状态在 MySQL 这类共享存储而非本地内存，能做到多副本对等部署，跨节点状态一致。

## 上下文工程同样值得关注

上下文工程同样值得关注。

（我觉得目前没有通用适合所有项目的上下文工程，或者整个 Harness，针对不同的场景，可能需要选择不同的设计。也就是代码的设计需要针对待解决的需求）

首先看明白直播场景的特点：

- 多话题交织。
- 高频切换。
- 单轮对话可能同时涉及播前、播中、播后多个场景。

下面是针对的手段。

### 手段一：分层压缩，而不是无脑截断

对于直播场景来说，主播的关键信息可能并不在最近几轮，可能在开播前。所以不能直接进行截断。

常规情况 token 超过阈值：

- 压缩历史工具调用（仅保留用于后续决策的信息，去掉冗余的字段信息）。
- 摘要历史对话轮次。
- 压缩当前轮次信息（用户可能粘贴了大量的商品信息，也需要去提取）。

当对话超过 N 轮触发 Session 级话题分段，将多轮对话压缩为结构化摘要，并打上场景标签（播前/播中/播后）。

这里就是该直播场景下还有非常清晰的小场景，并且相互隔离，支持后续按场景聚合检索。

### 手段二：借鉴前端状态管理的 Reducer 思想

这里是博客中强调值得强调的设计，这也是我感觉这个上下文工程针对直播场景进行特别优化的地方。

传统的 Agent 将每轮工具调用的 JSON 结果直接追加到聊天历史，让 LLM 从一长串历史消息中读懂当前状态。

这带来的几个严重问题：

1. 状态模糊，LLM 要自己去推断现在在讲的是哪个商品，价格改为了多少。
2. 上下文膨胀。
3. 不可回放。

借鉴前端状态管理的 Reducer 思想做职责分离。

每个模块不直接修改状态，而是通过发 action，通过统一的状态更新处理器来进行状态转移。LLM 只负责决策（产生 action），Reducer 函数负责状态变更（纯函数，确定性）。

每轮对话前将最新的结构化 State 序列化注入，这样模型每轮看到的都是干净的、确定的、最新的快照（当前商品、当前价格、当前库存）。

我认为非常关键的两点提升：

1. 将历史信息转为清晰的结构信息。

在实际的直播场景中，可能商品的价格会频繁地变动，让大模型去消息中看到价格可能变为 125，过几条消息降为 98，需要模型自行去做判断。而通过维护一个结构化信息并动态注入，模型能直接明确商品的价格等信息。

2. 确定性与不确定性分离。

如果说可以通过确定性的代码去解决，其实是非常好的方案。因为一个它是确定性的，不会偏差；二个它也能节省 token 的消耗。

将状态转移交给代码来实现，我们可以加一些强制的校验，确保状态的转移是合理的 a 到 b，而不是跳的 a 到 c 这些不合理情况。

额外的，带来了可回放和可复现。通过 Reducer，每步都有旧 state 和 action，并且产生新的 state。这对生产环境下去做排障更方便，而不是从散落的聊天记录去捞。

### 手段三：大上下文卸载

大上下文卸载：将体量大但不必时刻在场的，进行外存储卸载，消费时再提取、摘要。

## DAG 并行子任务

DAG 并行子任务，全局规划，增量 replan（子任务失败，只重新规划后续的节点），计划步骤进度独立于对话上下文维护，任务状态实时注入。

并且 planner 基于小模型进行 SFT 微调和强化学习，这里我需学习后再进行了解。

## 一个关于记忆冲突的 tips

tips：我觉得记忆系统中值得关注的一点，是关于记忆矛盾和冲突进行的优化。

不选择直接覆盖，而是引入对账：累计矛盾多次达到阈值后，由 Agent 主动和主播确认。

这样既能基于客观事实进化，而且尊重了主播的主观意图。
