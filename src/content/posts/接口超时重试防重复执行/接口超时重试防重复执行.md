> 这个问题其实挺实际的。场景是：一个接口超时时间设了 10 分钟，但任务实际跑了 20 分钟。调用方在第 10 分钟收到超时异常，以为失败了就触发了重试。但其实第一次的任务还在跑，这时候第二次请求进来了——同一个任务被执行了两次。支付扣了两次款、订单生成了两份、数据入库了两遍...都是灾难。

## 先搞清楚问题的根源

画个时间线就能看明白：

```
调用方                         服务端
  → 第一次请求 →               开始执行任务（需要 20 分钟）
                               ...
    （10 分钟到了，超时了）       ...还在跑...

  → 重试请求 →                 又开始执行同一个任务！
                               ...
                               第一次任务执行完了
                               第二次任务也执行完了
                               → 任务被执行了两遍
```

关键矛盾在于：**超时 ≠ 失败**。调用方收到超时异常只是说"我没收到响应"，并不代表服务端没有在正常执行。但调用方不知道啊，它只能按失败处理，于是重试。

> 所以解决思路不是"怎么避免超时"（有时候任务就是慢），而是**怎么保证就算重试了，任务也不会被重复执行**。

## 方案一：幂等性设计 + 唯一请求 ID

这是最根本的思路——让接口具备**幂等性**：同样的请求执行一次和执行多次，结果是一样的。

### 实现方式：客户端生成唯一 ID

```java
// 调用方：每次业务操作生成一个唯一的 requestId
// 重试时带上同一个 requestId
String requestId = UUID.randomUUID().toString();
taskService.execute(requestId, taskParam);

// 如果超时了，重试用同一个 requestId
taskService.execute(requestId, taskParam);  // 同一个 ID
```

服务端拿到 requestId 后，先查有没有处理过：

```java
@Service
public class TaskService {

    @Autowired
    private TaskRecordMapper taskRecordMapper;

    public Result execute(String requestId, TaskParam param) {
        // 1. 先查这个 requestId 有没有记录
        TaskRecord record = taskRecordMapper.selectByRequestId(requestId);

        if (record != null) {
            // 已经处理过了
            if (record.getStatus() == TaskStatus.COMPLETED) {
                // 任务完成了，直接返回上次的结果
                return Result.success(record.getResult());
            }
            if (record.getStatus() == TaskStatus.PROCESSING) {
                // 任务还在跑，告诉调用方别急
                return Result.processing("任务执行中，请稍后查询");
            }
        }

        // 2. 没处理过，插入一条记录（状态为 PROCESSING）
        //    注意：requestId 字段要加唯一索引！
        try {
            taskRecordMapper.insert(new TaskRecord(requestId, TaskStatus.PROCESSING));
        } catch (DuplicateKeyException e) {
            // 并发插入冲突，说明另一个线程已经开始处理了
            return Result.processing("任务执行中，请稍后查询");
        }

        // 3. 执行业务逻辑
        try {
            Object result = doActualWork(param);
            taskRecordMapper.updateStatus(requestId, TaskStatus.COMPLETED, result);
            return Result.success(result);
        } catch (Exception e) {
            taskRecordMapper.updateStatus(requestId, TaskStatus.FAILED);
            throw e;
        }
    }
}
```

对应的表结构：

```sql
CREATE TABLE task_record (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    request_id VARCHAR(64) NOT NULL,
    status TINYINT NOT NULL COMMENT '0-处理中 1-完成 2-失败',
    result TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE INDEX uk_request_id (request_id)  -- 唯一索引是关键！
);
```

> 核心在于 **requestId 的唯一索引**。即使两个请求几乎同时到达，数据库的唯一约束也能保证只有一个能插入成功，另一个会抛 `DuplicateKeyException`。

## 方案二：Redis 分布式锁

如果觉得查数据库太重，或者需要更快的判断速度，可以用 Redis 来做。

```java
@Service
public class TaskService {

    @Autowired
    private StringRedisTemplate redisTemplate;

    public Result execute(String requestId, TaskParam param) {
        String lockKey = "task:lock:" + requestId;

        // SETNX + 过期时间，原子操作
        // 30 分钟过期（要大于任务最大执行时间）
        Boolean acquired = redisTemplate.opsForValue()
                .setIfAbsent(lockKey, "PROCESSING", 30, TimeUnit.MINUTES);

        if (Boolean.FALSE.equals(acquired)) {
            // 锁已存在，说明有人在处理或已处理完
            String status = redisTemplate.opsForValue().get(lockKey);
            if ("COMPLETED".equals(status)) {
                return Result.success("任务已完成");
            }
            return Result.processing("任务执行中");
        }

        // 拿到锁了，执行任务
        try {
            Object result = doActualWork(param);
            // 执行完把状态改成 COMPLETED（保留一段时间供查询）
            redisTemplate.opsForValue().set(lockKey, "COMPLETED", 24, TimeUnit.HOURS);
            return Result.success(result);
        } catch (Exception e) {
            redisTemplate.delete(lockKey);  // 失败了释放锁，允许重试
            throw e;
        }
    }
}
```

这里 `setIfAbsent` 就是 Redis 的 `SET key value NX EX` 命令，原子性地完成"检查是否存在 + 设置值 + 设置过期时间"。

（有个细节：过期时间一定要设得比任务最大执行时间长，不然任务还没跑完锁就过期了，重试请求又能进来）

## 方案三：数据库状态机

对于订单、支付这类有**状态流转**的业务，用状态机天然就能防重。

```java
// 任务状态流转：PENDING → PROCESSING → COMPLETED / FAILED
//                                ↑
//                          重试不能回退到这里

public Result processOrder(String orderId) {
    // 用乐观锁 CAS 更新状态
    int affected = orderMapper.updateStatusWithCas(
        orderId,
        OrderStatus.PENDING,      // 期望的当前状态
        OrderStatus.PROCESSING    // 要更新成的状态
    );

    if (affected == 0) {
        // 更新了 0 行 → 当前状态不是 PENDING
        // 可能已经在处理中或已完成
        Order order = orderMapper.selectById(orderId);
        if (order.getStatus() == OrderStatus.COMPLETED) {
            return Result.success("订单已处理完成");
        }
        return Result.processing("订单处理中，请勿重复提交");
    }

    // 成功抢到任务
    try {
        doProcessOrder(orderId);
        orderMapper.updateStatus(orderId, OrderStatus.COMPLETED);
        return Result.success();
    } catch (Exception e) {
        orderMapper.updateStatus(orderId, OrderStatus.FAILED);
        throw e;
    }
}
```

对应的 SQL：

```sql
-- 乐观锁更新，只有当前状态是 PENDING 时才更新
UPDATE orders
SET status = 'PROCESSING', updated_at = NOW()
WHERE order_id = #{orderId} AND status = 'PENDING';

-- affected rows = 0 说明状态已经变了，不是 PENDING 了
```

> 状态机的妙处在于：**状态只能往前走，不能回退**。已经是 PROCESSING 或 COMPLETED 的任务，不可能被再次更新成 PROCESSING。靠数据库的行级锁保证原子性。

## 方案四：组合拳（推荐）

实际项目里，一般不会只用一种方案，而是组合起来用：

```
请求进来
  第一层：Redis 分布式锁（快速去重，扛住并发）
    SETNX requestId → 拿不到直接返回
  第二层：数据库唯一索引（兜底，防止 Redis 故障时重复）
    INSERT task_record → DuplicateKey 则返回
  第三层：业务状态机（最终保障）
    UPDATE ... WHERE status = 'PENDING' → 0行则返回
```

```java
public Result execute(String requestId, TaskParam param) {
    // --- 第一层：Redis 快速判断 ---
    String lockKey = "task:lock:" + requestId;
    Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, "PROCESSING", 30, TimeUnit.MINUTES);
    if (Boolean.FALSE.equals(acquired)) {
        return getExistingResult(requestId);
    }

    // --- 第二层：数据库唯一索引兜底 ---
    try {
        taskRecordMapper.insert(new TaskRecord(requestId, TaskStatus.PROCESSING));
    } catch (DuplicateKeyException e) {
        return getExistingResult(requestId);
    }

    // --- 第三层：执行任务 ---
    try {
        Object result = doActualWork(param);
        taskRecordMapper.updateStatus(requestId, TaskStatus.COMPLETED, result);
        redisTemplate.opsForValue().set(lockKey, "COMPLETED", 24, TimeUnit.HOURS);
        return Result.success(result);
    } catch (Exception e) {
        taskRecordMapper.updateStatus(requestId, TaskStatus.FAILED);
        redisTemplate.delete(lockKey);
        throw e;
    }
}
```

## 别忘了调用方也要配合

服务端做好防重是一方面，调用方也有责任：

**1. 合理设置超时时间**

如果任务可能跑 20 分钟，超时时间设 10 分钟本身就不合理。要么调大超时时间，要么改成异步模式。

**2. 改成异步调用**

对于耗时长的任务，最好别用同步接口：

```java
// 调用方：提交任务，拿到 taskId，之后轮询结果
String taskId = taskService.submit(param);   // 快速返回

// 然后轮询或者回调
while (true) {
    Result result = taskService.query(taskId);
    if (result.isCompleted()) {
        break;
    }
    Thread.sleep(5000);  // 每 5 秒查一次
}
```

这样就不存在超时重试的问题了——提交是秒级完成的，不会超时。

**3. 重试时带上相同的请求 ID**

```java
// 不管重试几次，requestId 是同一个
String requestId = generateRequestId(userId, orderId, bizType);

for (int i = 0; i < maxRetry; i++) {
    try {
        Result result = taskService.execute(requestId, param);
        if (result.isSuccess() || result.isProcessing()) {
            return result;
        }
    } catch (TimeoutException e) {
        log.warn("第 {} 次超时，准备重试", i + 1);
        // 退避一下再重试
        Thread.sleep((long) Math.pow(2, i) * 1000);
    }
}
```

> 指数退避（Exponential Backoff）也很重要——别超时了就立刻重试，给服务端喘口气。1 秒、2 秒、4 秒...逐渐拉长间隔。

## 方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 唯一 ID + 数据库 | 可靠，持久化 | 有 DB 开销 | 对可靠性要求高的核心业务 |
| Redis 分布式锁 | 快，并发性能好 | Redis 故障时可能失效 | 高并发场景的第一层过滤 |
| 数据库状态机 | 业务语义清晰 | 需要业务有状态概念 | 订单、支付等有状态流转的业务 |
| 异步化改造 | 根本解决超时问题 | 改动大，需要轮询/回调 | 执行时间不可控的长任务 |

## 小结

这个问题的本质是**分布式环境下的幂等性保证**。不管用哪个方案，核心思想就两条：用唯一标识追踪请求，用某种锁或状态机保证"只执行一次"。实际项目里最稳的做法是 Redis 快速去重 + 数据库兜底 + 业务状态机三层防护。另外，如果任务本身就很耗时，最好一开始就设计成异步模式，从根源上避免超时重试的问题。
