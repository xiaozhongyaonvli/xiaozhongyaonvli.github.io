> 这篇笔记是我跟着 [claude-code-book](https://github.com/lintsinghua/claude-code-book) 学习 Claude Code 时整理下来的阶段性记录。这个仓库不是单纯的使用说明，更像是把 Claude Code 背后的框架设计、运行时机制和工程化思路拆开来讲清楚的一套学习材料。

最近在集中补 Claude Code、Agent Harness 和上下文工程这条线时，我发现真正值得反复琢磨的，不是“某个命令怎么用”，而是它为什么要这样设计。比如为什么要把智能体当作运行时系统来构建，为什么工具调用、记忆写回、上下文压缩、权限边界和多智能体协作要一起考虑。这份笔记就是沿着这个思路，把我读到的关键点、容易忽略的工程细节，以及自己的一些理解先整理下来。

如果把这份内容当成定位，它更像是一份学习中的结构化摘记，而不是一篇完整教程。后面这些条目，主要记录的是 Claude Code 这套框架和思维方式里，我目前觉得最值得反复回看的部分。

## 学习笔记

记录自己学习每个章节得一些小笔记和体会：

1. 基础篇：
    1. 智能体编程的新范式：
        1. LLM 的真正价值不在于生成文本，而在于作为推理引擎来编排工具调用
        2. Agent Harness 是围绕 LLM 构建的运行时框架，它将 LLM 从一个文本生成器提升为一个能够安全、可靠、高效地与外部世界交互的自主智能体
    2. 对话循环-Agent的心跳
        1. 为什么选用 AsynGenerator而非回调或Promise的原因 流式(promise缺点) 回调地狱(回调缺点)
        2. 对话循环 可变状态容器存储迭代传递全部状态，再回到循环顶部时重写，避免迭代过程中的部分更新导致的不一致问题
        3. 轻量压缩 --缓存友好，避免自动压缩导致缓存全面失效(偏向锁 轻量锁 重度锁)
        4. 对 Continue 路径记录原因，当行为异常时可追溯
    3. 工具系统-Agent的双手
        1. 工程实践原则: 公开API中，重命名是"只增不减"的操作，避免依赖旧名称的配置，脚本和用户习惯被打破
        2. tool校验除了输入参数验证，权限校验，还有运行时属性判断，看工具是否可以并行执行
        3. tool包含可选的上下文修改器(eg:修改agent维护的文件缓存(避免频繁的io))
        4. tool延迟发现机制，显示标记总为加载的不延迟，其余延迟加载完整schema
        5. 工具池按名称排序去重，排序目的确保prompt缓存稳定性，子agent的工具集与主agent相同，避免kv cache失效，通过回调筛选
        6. bashtool的快速失败(执行失败会取消所有并行的Bash工具调用，因为Bash命令之间往往存在隐式依赖链)
        7. 精准编辑文件采用old_string->new_string的精准替换模式，而非行号范围
        8. 抢跑机制：不等待模型响应完全结束，而是流式接收到工具调用就立即启动执行
        9. 当流式回退发生时(模型切换到fallback模型)，标记所有待执行和执行中的工具为废弃，当模型决定改变策略时，所有基于旧策略的工具调用结果都应该被丢弃
        10. 每个工具执行使用独立的子取消控制器，形成层次化的取消信号链，兄弟工具的错误或用户的 Ctrl+C 都会通过信号传播到正确的工具
    4. 权限管线-Agent的护栏：
        1. 子agent权限冒泡确保子agent获取的权限不会大于主agent的权限
2. 核心系统篇:
    1. 设置与配置 - Agent的基因:
        1. 两种策略：
            1. 后者合并前者(深度合并而非直接替换)
            2. 第一个非空
    2. 记忆系统-Agent的长期记忆:
        1. 四种记忆类型: user 用户画像 feedback 反馈指导(记录用户对Agent行为的纠正和确认)(不仅记录失败(纠正),也记录成功(确认)。如果只保持纠正，Agent会过于谨慎，偏离已验证方法) project 项目状态(决策，截至日期，正在进行的工作)(为什么这样做) reference 外部系统引用(哪里找更多信息)
        2. 时间记忆采用绝对日期
        3. 格式: name desc type(四种类型之一)
        4. 记忆写入采用fork子进程后台提取，避免影响用户体验，记忆与主进程共享(有记忆标志互斥，避免主子进程重复加载)
        5. 节流计数器，规定阈值的对话才进行一次记忆
        6. 记忆是一个时间点的快照，而非事实，是被信任线索而非结论
    3. 上下文管理-Agent的工作记忆
        1. 断路器模式: 3次压缩失败，熔断不再尝试自动压缩
        2. 四层压缩：
            1. snip 裁剪，最轻量，将不需要的信息中的工具调用结果替换为简短的标记文本
            2. MicoCompact，基于时间触发(claude api的提示缓存过期时间),保留最近N个可压缩工具结果，将其余结果替换为清除标记文本，不破坏缓存前缀(未过期)
            3. autocompact 用llm进行摘要
        3. 三种压缩提示词:
            1. 全量压缩 2. 指定消息到当前 3. 摘要指定消息之前的上下文
            2. 摘要时要求仅以文本回复，不调用工具，最多1轮，避免产生新的对话历史，从而导致递归问题
        4. 双阶段输出，<analysis> 块:思维草稿本(不进入上下文)， <summary> 块：正式摘要内容，思考空间避免摘要遗漏重要信息
        5. 压缩完成后在消息流中插入压缩前后的分界线，该标记携带了压缩的元数据，避免重复压缩
        6. 分阶段工作，当前阶段结束时压缩，确保下一阶段有充足的上下文空间。 利用记忆系统补充上下文
    4. 钩子系统-Agent的生命周期扩展点
        1. 观察者模式结合责任链模式，多个钩子可以监听同一个信号(生命周期事件)，按优先级依次处理，任何钩子都可以选择阻断信号传播
        2. 钩子类型: Command, Prompt(llm推理), Agent(llm多步),http,function
        3. 三种执行模式: 同步模式(阻塞当前操作，等待钩子完成) 异步模式(后台运行，钩子结果对模型不可见，适合发完即忘得日志记录场景) 异步唤醒模式(后台运行，当钩子发生错误退出(退出码为2)时，注入错误信息唤醒模式继续对话)
        4. 钩子依赖事件触发，类似java得aop? eg: 工具调用生命周期(PreToolUse执行前拦截，PostToolUse,PostToolUseFailure)
        5. 钩子响应协议: 输出json响应(需要精准控制cc的行为)，保留stdout作为非结构化输出通道(用于日志与调试)
        6. 纵深防御，全cc都体现了这个思想
3. 高级模式篇
    1. 子智能体与Fork模式
        1. 智能体同名覆盖，多层级别
        2. 对Agent的约束(eg:只读搜索智能体:禁止写等工具，可选择低模型降低成本，系统提示和工具层面物理禁止双重锁，对git 部分命令的限制)
        3. 读写层(General(执行) Verification(验证)) 只读层(Explore(搜索) Plan(规划))
        4. 验证智能体的深层哲学:系统提示明确警告两种失败模式: 1.验证回避(模型倾向于找借口不运行测试)2.前百分之80的表面正确(未考虑边界条件，并发场景)
        5. fork模式: 轻量并行模式，将同一上下文分发到多个独立子任务(子智能体是字节级继承 kv cache),禁止fork自己进行fork
        6. 根据任务类型合理设置子智能体的最大执行轮次
    2. 协调器模式-多智能体编排
        1. 与fork互斥，Coordinator模式，采用协调者-工作者架构(不共享缓存前缀)
        2. 禁止工作者检查工作者，避免链式传递引起信息衰减，调试困难(需要逐层追溯)
        3. 工作者的工具池独立于父级组装，不应该被权限问题阻碍
        4. 团队管理--一个领导者只能管理一个团队，生成唯一名称，创建团队文件，只有当所有成员都完成工作后才允许清理
        5. 消息传递的寻址模式:1.向指定工作者发送指令 2.向所有工作者发布公共信息 3.跨进程通信(不同cli实例) 4.跨会话/跨机器通信
        6. 停止-恢复模式:工作者做完工作后，释放一些资源，仅存较小工作上下文,当协调者追加任务，被重新激活，不需要从头构建上下文
        7. Scratchpad--跨工作者共享的临时文件空间
        8. 工作者完成后，结果以<task-notification> XML格式传递给协调者(通过这个区分用户消息和工作者结果报告)(模型处理xml格式更优于json)
        9. 工作者失败的处理策略(1. 工具执行失败->分析失败原因重试或调整策略 2.模型输出截断(评估已完成部分，决定是否重新分配) 3.mcp连接断开->降级 4.上下文过长->压缩或者拆分更小子任务)
        10. 协调者应该充分利用已完成的工作，而不是等待完美信息(即使只完成部分也开始工作)，协调者使用置信度标注各个信息([HIGH][MEDIUM][LOW])
    3. 技能系统与插件架构
        1. 去重使用realpath解析
        2. 可以在子目录中创建自己的技能，这样减少技能选择的负担
        3. 插件是比技能更高层级的扩展单元(一个插件可以包含技能，agents,hooks等多种组件)
        4. 技能不是孤立使用的，可以与其他技能，智能体，hooks和工具组合形成强大的工作流(不要创建万能技能)
    4. MCP集成与外部协议
        1. 客户端通过先声明后使用的模式，双方可以在互相不了解内部实现的情况下协作
        2. 传输无关性: 同一个MCP服务器可以通过stdio,http,websocket等多种方式提供服务
        3. 工具名称前缀 mcp__server__tool(双下划线),服务器名和工具名拼接为全限定名(同名工具但不同服务器也不会冲突)
        4. 纵深防御(黑白名单->allow规则deny规则->用户确认)
        5. Bridge 系统是cc与外界双向通信的核心层，与vscode jets等的集成,其中他的UUID重复检测使用环形缓冲区而不是set(原因:避免持续增长，只保留最近N条，在内存效率和重复准确性中取得了平衡)(数据结构的选择不是可选而是关乎正确性)
4. 工程实践篇
    1. 流式架构与性能优化
        1. 流式处理工具调用(前文工具章节有提及)，不等完全回复而是接收到工具调用即调用，但通过yield保证工具输出顺序与工具到达顺序一致，此外工具的并行
        2. 成本异常检测: 单轮输入超过100k token(可能工具返回了过大的结果) 单论输出过大，可能模型冗余输出， 缓存命中率突然断崖下降，可能上下文出现问题
    2. plan模式与结构化工作流
        1. plan模式: 理解->发现->比较->澄清->设计->呈现。 step 1-2发散阶段，尽可能收集信息，3-4收敛过度阶段 5-6完全收敛
        2. plan的持久化与恢复: 多级尝试恢复(文件， 文件缓存， 消息历史)
        3. 本地定时任务:1. 使用一次后消失 2.循环任务，任务包含durable标志(是否持久化写入磁盘)，false为短期临时任务，如果当时未触发也没有意义了
        4. Jitter机制:为避免大量会话在同一时刻触发推理请求(惊群效应)，循环任务增加了正向延迟，对于每小时执行的任务，实际触发时间会在:00到:06之间随机分散
    3. 构建你自己的Agent Harness
        1. 工具系统，工厂模式，每个工具只需定义自己特有部分，通用行为由工厂提供，默认值为并发不安全，串行
        2. 记忆系统的设计挑战: 1.提取什么(并不是所有对话内容都值得记住) 2.存储多久(记忆有衰减曲线，一周前的对话上下文可能已经不再相关(代码已重写)，需要根据记忆的时效性和引用频率来决定保留时间) 3.何时注入(记忆不应该每个请求都全量注入，而是根据当前对话的相关性，选择性注入最相关片段)
        3. (重点****)可观测性的深度讨论:
            1. 第一层:结构化日志(每个关键操作都输出结构化的日志条目，包含操作类型，持续时间，输入摘要和输出摘要)
            2. 第二层:聚合指标，从结构化日志中提取聚合数据用于仪表盘展示和告警
                1. 延迟分布:每轮循环的模型调用耗时，工具执行耗时
                2. Token预算：输入/输出Token消耗趋势，压缩频率
                3. 错误率:按错误类型分类的失败率(模型错误，工具错误，权限拒绝)
                4. 行为指标:平均每轮工具调用数，平均完成轮次，用户中断率
            3. 第三层:分布式追踪:在多 Agent 场景中，一个用户请求可能触发多个子 Agent。分布式追踪通过唯一的 query_chain_id 将所有相关的操作串联起来，使得你可以从一个用户请求出发，追踪到所有子 Agent 的行为。
            4. 异常检测。 基于历史数据的异常检测，自动识别异常行为模式：单轮工具调用数异常增加 -- 可能是 Agent 陷入了循环 Token 消耗突然飙升 -- 可能是工具返回了意外的大量数据 错误率突然上升 -- 可能是外部 API 出现问题
        4. harness未来发展:
            1. 多模态引入(语音图片视频)
            2. 长期运行守护进程
            3. mcp更成熟驱动cc工具系统从单体到微服务
            4. 执行模式从被动(等待用户指令)到主动
            5. 从隐式记忆(文本片段)到显示知识图谱
