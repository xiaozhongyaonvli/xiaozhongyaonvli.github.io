## 开头抛出的三个痛点

文章开头抛出三个痛点：

- 非确定性：是否稳定能跑。
- 黑盒化：模型升级。
- 错误级联放大：几十步工具调用，前序小偏差沿链路逐渐放大。

首先是确定性。现在基本我看针对一个 case 都是去跑多次的。

模型升级确实是一个我感觉比较重要的点，因为模型正在不断内化各种能力，同时可能新的版本更关注某个方向，而弱化了其他方向（比如说最近 gpt 正在追赶 code 领域，个人感觉人味感也是在下降的。claude 也是，最好的对话感应该是 4.6）。

所以依附于 llm，或者说作为 llm 的外壳，需要去尝试切换新的模型。同时相应的工程可能也需要去做相应的调整：被内化的能力的部分我们需要简化，原有的变得漂移的部分，我们需要重新考虑一些约束。

错误级联，是我第一次看到这个关注点。因为 llm 每次的决策是结合历史对话去做的，所以确实会有这种情况。

但我比较好奇，如何去做定位，也就是如何去溯源找到第一个偏移的部分。或许作为训练调优的 case 集，预期答案需要包含对多个工具包括顺序调用和预期结果的内容。

具体这部分可以看上一篇博客：

其中有提到关于多个 tool 的调用的问题。

## 三个评分器

接下来提到三个评分器：

- 确定性评分器：脚本、断言。
- 模型评分器：语义。
- 人工评分器：专家，昂贵。

感觉目前基本都是这么做的，可能是共识了？

我的这篇博客里有关于评分器的讲解：

- https://xiaozhongyaonvli.github.io/posts/skill-eval-series-04-promptfoo-assertions/skill-eval-series-04-promptfoo-assertions/

能够使用代码准确判断的，应该用脚本去 check，因为稳定并且不费 token。同时需要注意，在评测的过程中沉淀一些新的脚本，它们可能被多次创立和使用。

人工的评分用于校准。这里我觉得不仅是对 case 的打分，同时也是对搭建的评测体系的一个打分，需要根据人工专家的意见去做优化，从而让脚本 + 模型的评分更贴近真实。

这篇文章也提及：能自动化的坚决不找专家，专家时间应百分之 60 以上花在校准 LLM 评委和诊断异常上。

## 五大维度

关注的五大维度：

- 功能正确性。
- 过程质量。
- 效率与成本。
- 鲁棒性与安全。
- 体验与对齐。

其中第五个感觉很棒，回答的问题是「用户愿意用它吗」，p2 等级，但是是决定产品生死的。

子维度为语气风格、回复清晰度、同情心等。

早期用 rubric + 人工抽样，成熟后引入线上 A/B 和用户反馈闭环。

这个应该是比较难做好的地方。这里我也没有更多的体会，但觉得确实很重要，遂记录下来。

## 测评集的构建

然后是关于测评集的构建。

四个场景：

- 触发。
- 核心逻辑。
- 产物质量。
- 异常容错。

同时包含正反例。

触发关注 Agent 的职责范围是否明确和收敛，其中需要关注过度触发。claude 也提到，避免提供虚假信心。

核心逻辑部分，需要做到覆盖 skill 的所有分支。这里我之前也提到无法针对 skill 去自动生成所有的路径 case，这里我推测应该是人工去做生成的，因为一个 case 感觉在跑之前很难知道它会走向哪个路径，除非 skill 中明确有一些不同的参数导向不同路径。

异常容错，检测在异常输入、边界条件、环境故障下能否合理处理，而非崩溃或静默失败。
