> 之前写过一篇分布式锁的笔记，把 SETNX、Lua 脚本释放锁、Redisson 看门狗这些基础都过了一遍。但有个东西一直没深入 —— Redis 作者 Antirez 提出的 Redlock 算法，以及 Martin Kleppmann（《DERTA》作者）对它的公开质疑。这场分布式系统领域的"神仙打架"，把问题挖得很深，值得好好梳理一下。

## 先回忆一下：单节点 Redis 锁的致命缺陷

用单个 Redis 实例做分布式锁，大家都会写：

```bash
SET resource_name my_random_value NX PX 30000
```

加锁没问题，但有个绕不开的隐患：**Redis 主从切换时锁会丢失。**

```
1. 客户端 A 在 Master 上加锁成功
2. Master 挂了，锁还没同步到 Slave（Redis 异步复制）
3. Slave 升级为新 Master
4. 客户端 B 在新 Master 上加锁成功
5. A 和 B 同时持有锁 —— 互斥性被破坏了
```

这不是理论上的问题，是真实存在的。所以 Antirez 提出了 Redlock：用多个独立 Redis 实例 + 多数派投票来解决这个问题。

---

## Redlock 的核心逻辑（5 步）

假设有 **N 个完全独立的 Redis 实例**（推荐 N=5），注意是互相独立的，不是主从或集群，没有任何复制关系。

加锁过程：

```
客户端 同时向 5 个独立 Redis 发 SET NX PX
  → Redis-1  ✓
  → Redis-2  ✓
  → Redis-3  ✓  ← 拿到 3 个（过半），加锁成功
  → Redis-4  ✗  (超时/网络不可达)
  → Redis-5  ✗
```

**具体步骤：**

**Step 1**：记录当前时间戳 T1（毫秒）。

**Step 2**：依次（实际建议并行）向 N 个 Redis 实例发送加锁请求：

```bash
SET resource_name my_random_value NX PX 30000
```

每个请求设置一个很短的超时时间（比如 5~50ms），避免某个节点挂了把整个流程卡住。

**Step 3**：记录当前时间戳 T2，计算获取锁花了多久：`elapsed = T2 - T1`。

**加锁成功的条件**（两个都要满足）：
- 在 **N/2 + 1** 个（即多数派）节点上成功获取了锁
- `elapsed < 锁的有效时间`（获取锁的耗时不能超过锁的 TTL）

**Step 4**：如果加锁成功，锁的**实际有效时间**要减去获取过程的耗时：

```
实际有效时间 = TTL - elapsed
```

（这个设计挺重要的 —— 你花了 2 秒才拿到锁，那这把锁实际可用时间就少了 2 秒）

**Step 5**：如果加锁失败（没过半数，或者耗时超限），**必须向所有节点发送释放锁的请求**，包括那些没成功加锁的节点。

为什么没成功的也要释放？因为可能请求实际上到了，但响应丢了（网络问题），锁其实加成功了你不知道。

释放锁用 Lua 脚本，保证只删自己的锁：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

### 重试机制

加锁失败后不是立刻重试，而是**等一个随机延迟**再重试。这样做是为了避免多个客户端同时竞争导致谁都拿不到多数派（类似 Raft 选举里的随机超时）。

## 看起来很完美？Martin Kleppmann 说不行

2016 年 2 月，Martin Kleppmann 发了一篇博客 "How to do distributed locking"，直接公开质疑 Redlock 的安全性。随后 Antirez 写了 "Is Redlock safe?" 反驳。这场辩论在分布式系统圈子里影响很大。

我把争议点整理了一下，主要集中在三个方面：

### 争议一：GC 停顿（或进程暂停）可以让锁"悄悄过期"

这是 Kleppmann 举的最经典的例子：

```
时间线：
T1: 客户端 A 成功获取锁（TTL=30s）
T2: 客户端 A 触发 Full GC（Stop The World），暂停了 35 秒
T3: 锁过期了（30s 到了），Redis 自动删除
T4: 客户端 B 成功获取锁
T5: 客户端 A 的 GC 结束，它还以为自己持有锁
T6: A 和 B 同时操作共享资源 —— 互斥性被破坏
```

```
客户端A:  |---获取锁---|   [====GC暂停 35s====]   |--以为还持有锁--|
客户端B:                           |---获取锁---|--操作资源--|
Redis:    |------锁有效 30s------|过期|
                                              ↑
                                        两个客户端同时操作！
```

这个问题不光是 GC，任何导致进程暂停的原因都行：操作系统换页、CPU 被抢占、甚至就是 debug 断点... 而且这不只是 Redlock 的问题，**单节点 Redis 锁甚至 ZooKeeper 锁都有这个问题**。

> 我觉得 Kleppmann 这个例子确实很有杀伤力。虽然 30 秒的 GC 暂停在现实中极少见，但 Kleppmann 的意思是：**你没办法对进程暂停时间设上界**，所以基于 TTL 的锁在理论上就不安全。

**Antirez 的反驳**：这种情况确实存在，但可以通过合理的实践来缓解。而且任何基于 TTL 的锁（包括 ZooKeeper 的 session）都有类似问题，不是 Redlock 独有的。

### 争议二：时钟跳变会破坏安全性

Redlock 依赖多个节点各自计算 TTL 过期时间，这就暗含了一个前提：**各节点的时钟大致同步，且匀速流逝。**

但如果某个节点的时钟发生跳变呢？

```
1. 客户端 A 在节点 1、2、3 加锁成功（5 节点过半）
2. 节点 3 的时钟因为 NTP 同步突然往前跳了 30 秒
3. 节点 3 上的锁因为时钟跳变而"提前"过期了
4. 客户端 B 在节点 3、4、5 加锁成功（也过半）
5. A 和 B 同时持有锁
```

Kleppmann 的观点是：**Redlock 对时钟做了"同步系统模型"的假设**，假设时钟误差有界，网络延迟有界，进程暂停有界。但在真实世界中，这些假设随时可能被打破。他列举了 GitHub 曾经出现过网络包延迟 90 秒的案例。

**Antirez 的反驳**：
- 现代操作系统的时钟漂移是可控的，NTP 配置合理的话不会出现大跳变
- 可以用多次小步调整代替一次大跳变
- Redis 用 `gettimeofday()` 获取时间，在合理运维的系统上误差可控

> 说实话我觉得两边都有道理。Kleppmann 说的是"理论上不安全"，Antirez 说的是"实践中可控"。看你站在什么角度了。

### 争议三：缺少 fencing token 机制

这是 Kleppmann 认为**最致命的问题**。

什么是 fencing token？就是一个**单调递增的数字**，每次获取锁时拿到一个更大的 token，写入共享存储时带上这个 token，存储端拒绝比当前已见过的 token 更小的写入。

```
客户端A: 获取锁，token=33 → [GC暂停...锁过期]
客户端B: 获取锁，token=34 → 写入存储（附带 token=34）✓
客户端A: GC 恢复，写入存储（附带 token=33）✗ 被拒绝！
                                                  ↑ 存储端发现 33 < 34，拒绝
```

有了 fencing token，就算锁过期了也不怕——存储端能兜底。

但 Redlock **没有提供这个机制**。它用的是随机字符串作为 value，不是单调递增的数字。Kleppmann 认为这意味着 Redlock 就算其他方面都没问题，也缺少最后一道安全防线。

**Antirez 的反驳**：
- 如果存储端能自己做 fencing 了，那你还要分布式锁干嘛？这不就等于把互斥的责任推给了存储端吗？
- Redlock 的随机字符串虽然不是递增的，但也是唯一的，可以用来做唯一性校验
- 而且不是所有存储系统都支持 fencing token 这种机制

> 这个争论我来回想了好几遍... Kleppmann 的逻辑是"分布式锁不能 100% 可靠，所以需要 fencing token 做兜底"，Antirez 的逻辑是"如果 fencing token 能解决问题，那分布式锁本身就不需要那么强的保证"。各有各的道理，但站在**防御性编程**的角度，我倾向于 Kleppmann 的观点 —— 多一层保护总不是坏事。

## 两边的核心立场

| | Martin Kleppmann | Antirez |
|--|-----------------|---------|
| **立场** | Redlock 不安全 | Redlock 足够安全 |
| **核心论据** | 依赖时钟假设；无 fencing token | 时钟漂移可控；实践中够用 |
| **系统模型** | 应该假设异步模型（时钟不可靠） | 可以假设半同步模型（时钟大致可靠） |
| **建议方案** | 要正确性用 ZooKeeper/etcd | Redlock 在合理运维下安全 |
| **背景** | 分布式系统学术大佬 | Redis 作者，工程派 |

用一句话概括这场争论：

> **Kleppmann 说的是"这个算法在理论上有安全性缺陷"，Antirez 说的是"在实际工程中这些缺陷可控"。** 一个学术严谨，一个工程务实，屁股决定脑袋吧（不是贬义）。

## 那实际工作中到底该怎么选？

争论归争论，落到实际得有个结论。我的理解是这样的：

**场景一：锁只是为了提升效率（偶尔重复执行也能接受）**

比如避免重复计算、防止缓存击穿等。这种场景用单节点 Redis 就够了，Redlock 都不需要。就算偶尔锁失效导致两个客户端同时执行，最多浪费一些资源，不会有数据一致性问题。

**场景二：锁是为了保证正确性（绝对不能并发执行）**

比如扣款、库存扣减、订单状态变更。这种场景 Kleppmann 的建议更靠谱：
- 用 **ZooKeeper / etcd** 这类基于共识算法的系统做分布式锁
- 或者用**数据库乐观锁**（版本号机制）做兜底
- 如果非要用 Redis，至少在业务层加 fencing 机制（比如数据库 CAS 操作）

**场景三：折中方案**

很多公司其实就是用 Redisson（内置了 Redlock 的实现 + 看门狗续约），再加上业务层的幂等设计来兜底。不追求理论完美，但实践中基本没问题。

```
Redisson 的 MultiLock（Redlock 的 Java 实现）：

RLock lock1 = redisson1.getLock("lock");
RLock lock2 = redisson2.getLock("lock");
RLock lock3 = redisson3.getLock("lock");

RedissonMultiLock lock = new RedissonMultiLock(lock1, lock2, lock3);
lock.lock();
try {
    // 业务逻辑 + 幂等校验兜底
} finally {
    lock.unlock();
}
```

## 面试怎么说

如果面试官问到 Redlock，我觉得可以这么组织：

> Redlock 的核心逻辑是：用 N 个（通常 5 个）完全独立的 Redis 实例，客户端同时向所有实例发送加锁请求，如果在多数派（N/2+1）上加锁成功，且获取锁的总耗时没有超过 TTL，就认为加锁成功。锁的实际有效时间要减去获取过程的耗时。
>
> 争议主要来自 Martin Kleppmann 的公开质疑，集中在三点：第一，进程 GC 暂停可能导致锁过期而客户端不知道；第二，算法依赖各节点时钟同步，时钟跳变会破坏安全性；第三，Redlock 没有 fencing token 机制做兜底。Antirez 反驳说时钟漂移在合理运维下可控，且 fencing token 实质上是把互斥的责任转嫁给了存储端。
>
> 我个人的理解是：如果锁只是优化手段，单节点 Redis 就够了；如果锁攸关正确性，应该用 ZooKeeper 或 etcd 这类基于共识算法的方案，或者至少在业务层加幂等校验做兜底。

---

## 小结

Redlock 这个话题的价值不只是算法本身，更在于那场争论暴露出来的深层问题：**分布式系统中，你对时间的假设到底能有多强？** 这其实是 FLP 不可能定理的一个实际投影 —— 在异步系统中，你没法同时保证安全性和活性。Redlock 选择了相信时钟，就不得不承担时钟不可靠带来的风险。
