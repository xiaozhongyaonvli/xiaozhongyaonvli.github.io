> 很多 agent 系统都会调用工具、保存历史、做一点 memory，但这还不等于“会进化”。真正值得追问的是：一个 agent 能不能把任务经验沉淀成未来还能持续生效的系统能力。

最近在看 Hermes Agent 时，我越来越觉得，这个项目最值得研究的地方并不是它接了多少平台、支持多少工具，而是它已经在工程层面认真回答了一个问题：一个 agent 怎样才能在长期运行里逐步变强，而不是每次都从头开始。

这篇文章不想写成一篇功能盘点，也不是安装或使用教程。我更想借 Hermes 这套设计，梳理我现在对“agent 自主进化”这件事的理解，以及为什么我认为它本质上不是 prompt engineering，而是 runtime engineering。

## 这篇文章想回答什么

这篇文章不是要介绍 Hermes Agent 的全部功能，也不是一份安装或使用指南。  
我真正关心的问题只有一个：

`一个 agent，怎样才能不只是“会调用工具”，而是能够在长期运行中逐步变强。`

Hermes Agent 之所以值得研究，不是因为它支持很多平台，也不是因为它工具很多，而是因为它已经把“agent 自主进化”拆成了几块可以落地的工程机制：

- 任务完成后的后台复盘
- procedural memory，也就是 skills
- curated memory，也就是稳定事实和用户偏好的长期记忆
- session retrieval，也就是可检索的历史经验库
- user model，也就是跨 session 的用户理解
- skill patch / update 机制

如果只看表面，Hermes 像一个多平台、多工具的 agent。  
但如果从“自主进化”这个角度看，它更像一个持续学习系统。

## 我现在对“自主进化 agent”的一个基本判断

在读完 Hermes 的核心实现之后，我越来越觉得，一个真正有进化能力的 agent，至少要解决下面几件事：

1. 它必须能从任务中提取经验，而不只是完成任务。
2. 它必须能把经验写回系统，而不只是临时总结一下。
3. 它必须区分不同层级的知识，而不是把所有东西都塞进一个 memory store。
4. 它必须能在未来任务里重新取回这些经验，而不只是“存过”。
5. 它必须允许旧经验被修正，而不是把第一次总结永久固化。

Hermes 的价值就在于，它基本把这五件事都做成了明确的工程结构。

## Hermes 的自主进化闭环

如果用一句话概括 Hermes 的主线，我会写成：

`任务执行 -> 经验判断 -> memory/skill 写回 -> 跨 session 检索 -> 下次任务复用 -> 再次修正`

这条链路非常重要，因为它说明 Hermes 的目标不是“记录历史”，而是“让历史持续参与未来”。

把它展开一点，可以理解成下面这个闭环：

1. agent 先完成正常任务。
2. runtime 根据轮次、上下文和任务复杂度，判断这次经历值不值得沉淀。
3. 如果值得，就在后台触发 review。
4. review 不是简单总结，而是决定要不要写 memory、user profile，或者创建 / patch skill。
5. 原始 session 也会进入可检索状态库，供未来搜索和聚合。
6. 未来遇到相似任务时，agent 通过 skills、memory、session search、user model 再次利用过去经验。
7. 如果复用时发现旧经验不够好，就继续 patch，而不是把旧资产当成不可变文档。

这就是我现在理解的 Hermes 式自主进化：  
不是一次性“学会”，而是不断在任务中沉淀、在使用中修补。

## Hermes 最值得学的，不是 agent loop，而是 background review

很多 agent 系统都会做主循环：读消息、调模型、调工具、返回结果。  
Hermes 当然也有这部分，但真正让我觉得它“有进化味道”的，不是主循环本身，而是任务之后的后台复盘机制。

从学习角度看，这一点特别关键。

很多系统也会让模型“反思一下”或者“总结一下”，但这类反思经常只是一次对话里的附加文本，随着上下文结束就消失了。  
Hermes 不是这样。它把复盘单独做成一个后台阶段，而且这个阶段的目标不是多说几句，而是决定：

- 这次经验是否值得记住
- 应该记成事实、偏好、历史证据，还是方法
- 应不应该修改已有 skill

这意味着 Hermes 把“学习”从 prompt 层的小技巧，提升成了 runtime 层的一等机制。

这也是我目前最想借鉴的一点：

`自进化不是让模型多想一会儿，而是让系统在任务之后有正式的复盘和写回流程。`

## Skills：Hermes 把方法沉淀成 procedural memory

Hermes 在 skill 系统里最重要的一个定义是：  
`skill = procedural memory`

这个定义比“技能模板”要强很多。

因为它强调的不是静态知识，而是方法知识：

- 某类任务应该怎么做
- 哪些步骤有效
- 哪些坑需要避开
- 什么情况下要走什么流程

这让我对“agent 学习”的理解更清晰了一层。  
如果 memory 更像“记住事实”，那 skill 解决的其实是“记住做法”。

Hermes 并不会因为一次任务结束就机械地生成一个新 skill。  
它更偏向在下面这些场景里沉淀 skill：

- 完成了复杂任务
- 经历了 trial and error，最终走通
- 用户修正了错误方法，修正版本被验证有效
- 发现了可复用的 workflow

这其实是在给 skill 增加门槛，防止技能系统被偶然经验污染。

另外，Hermes 对 skill 的处理也不是“频繁重写”，而是明显偏向 patch。  
这背后的思想非常工程化：经验不是每次都推倒重来，而是在稳定资产上做增量修正。

这一点我很认同。  
真正长期运行的 agent，不应该总是追求“重新生成一版最优文档”，而应该更像维护软件资产一样维护方法资产。

## Memory：Hermes 把长期记忆做成分层系统

Hermes 另一个非常值得学的点，是它没有把长期记忆做成一个大而混杂的 memory blob。

从整体实现看，它至少把长期积累分成了三层：

### 1. curated memory

这一层主要由 `MEMORY.md` 和 `USER.md` 承担。

它保存的是高价值、低频变化、应该稳定保留的内容，比如：

- 环境事实
- 项目约定
- 工具特性
- 用户偏好
- 用户的工作方式和预期

这一层更像“长期稳定认知”。

### 2. session retrieval

这一层不是把内容提炼成几条事实，而是保留过去发生过什么，并允许以后按主题找回。

它回答的问题是：

- 过去有没有做过类似任务
- 当时怎么处理的
- 出现过哪些错误
- 最终结果是什么

这一层更像“可检索经验库”。

### 3. user model / Honcho layer

如果说 `USER.md` 还是比较静态的偏好记录，那 user model 更进一步。  
它试图维护的是：

- 这个用户是谁
- 这个用户和 agent 之间的关系如何变化
- 相同任务在这个用户身上应该怎样调整处理方式

这已经不只是记偏好，而是走向持续的个体化建模。

所以 Hermes 的长期记忆不是一个存储桶，而是明确分层的：

- facts 用 memory 记
- experiences 用 session retrieval 记
- relationship 用 user model 记

这是我从这个项目里学到的一个很重要的设计原则：

`不要把所有长期信息都叫 memory。真正可持续的 agent，需要按知识层级拆开设计。`

## frozen snapshot：一个很小但很聪明的设计

在 memory 系统里，我觉得有一个特别值得记住的设计：frozen snapshot。

Hermes 会在 session 开始时把 memory snapshot 注入系统提示。  
中途如果发生 memory 写回，它会立即落盘，但不会实时刷新当前 session 的 system prompt。

这个设计乍看很普通，但其实很关键。

它把两件容易冲突的事情分开了：

- 学习可以持续发生
- 当前推理上下文保持稳定

如果一个 agent 每次学到一点东西就立刻改写当前 session 的系统前缀，上下文会持续抖动，prefix cache 也会被破坏，推理稳定性会下降。  
Hermes 没有这么做，而是选择：

- 当前会话稳定
- 新学习的东西从下个 session 再进入主上下文

这是一种非常工程化的折中。  
它让我意识到，agent 的学习系统不能只追求“越快注入越好”，还要考虑运行稳定性。

## session retrieval：真正重要的不是存历史，而是让历史可消费

普通 agent 也会保存历史对话。  
但 Hermes 的 session retrieval 更进一步，它不是简单存档，而是把历史变成未来可调用的资源。

从学习角度看，这很关键。

因为“记住”本身没有那么难，难的是：

- 未来什么时候想起它
- 想起的是完整证据还是模糊印象
- 能不能以低成本把历史经验重新压缩成当前任务可用的上下文

Hermes 在这方面的思路很清楚：

- 原始会话进入状态库
- 使用 FTS5 之类的方式做检索
- 取出相关片段
- 再做 focused summarization

这说明它不是把历史当作冷存储，而是把历史当作可以加工成“可消费回忆”的原材料。

这个设计非常像人的经验系统：  
不是把过去逐字背出来，而是在需要的时候，从过去提取足够相关的经验结构。

## 工具层为什么是自主进化的基础设施

如果只看 high-level 设计，很容易把 Hermes 的进化系统理解成“复盘 prompt + memory store”。  
但继续往下看，会发现工具层同样关键。

因为一个 agent 想完成自主进化，不能只会总结，它还必须有地方把总结落成系统资产。

Hermes 的工具层恰好覆盖了这几个动作：

- 写 memory
- 写 user profile
- create / patch skill
- 搜过去 session
- 操作终端和文件
- 调用 delegate、MCP 等外部能力

也就是说，Hermes 的学习闭环不是纸面闭环，而是有真实执行面的闭环。

这一点对我启发很大。  
如果一个系统没有正式的写回接口，那所谓“学习”大概率只是文本层的幻觉。  
Hermes 更像一个能真正修改自己工作资产的系统。

## Hermes 和普通 memory agent 的差别

如果只粗略比较，很多 memory agent 做的事情大概是：

- 记住用户偏好
- 检索历史对话

Hermes 在此基础上又加了几层：

- background self-review
- procedural memory
- skill patch / update
- 分层长期积累
- 跨 session user model

所以 Hermes 和普通 memory agent 的差异，不是“记得更多”，而是“沉淀得更有结构”。

我现在更愿意把它理解成：

`Hermes 不是一个有记忆的 agent，而是一个有经验沉淀机制的 agent。`

这两者差别很大。

前者重点在存储。  
后者重点在学习、写回、复用、修正的完整链路。

## gateway 和 cron 让我重新理解了“持续学习”

如果只把 Hermes 当成 CLI agent，会低估它。

它还有 gateway、多平台接入、cron、后台任务这些能力。  
从自主进化角度看，这意味着它不是只在“终端里的一次对话”中学习，而是可以在更长期、更持续的运行形态里学习。

这一点非常重要。

因为一个真正的自主进化 agent，最后大概率不会只是一个本地对话程序。  
它更像一个长期运行的 service：

- 有多个入口
- 有统一状态
- 有后台任务
- 有周期性整理和复盘

Hermes 已经明显朝这个方向走了。

cron 尤其有意思。  
当 skill 可以绑定到 cron job，而 cron 的执行结果又可能继续反哺 memory 和 skills 时，学习闭环就不再只发生在“聊天”里，也会发生在自动化工作流里。

这让我意识到：

`未来更强的 agent 进化系统，很可能不是对话产品，而是持续运行的 agent service。`

## 通过 Hermes，我现在对 agent 自主进化的理解

如果让我把这次观察浓缩成几个判断，我会写下下面这些。

### 第一，自主进化不是 prompt engineering，而是 runtime engineering

关键不在“提示词写得多聪明”，而在系统有没有正式的复盘、写回、取回、修正机制。

### 第二，长期积累一定要分层

事实、经验、方法、关系，这几类信息不能混在一起存。  
混在一起，最终只会得到一个越来越臃肿、越来越难用的 memory store。

### 第三，skill 是方法层资产，而不是文档装饰

如果不能被创建、调用、修补、复用，那它就不是真正的 procedural memory。

### 第四，历史的价值不在保存，而在未来可消费

session retrieval 的关键不是 archive，而是 retrieval + summarization + reuse。

### 第五，学习系统必须允许增量修正

真正的进化不是每次重建，而是在已有资产上持续 patch。

## 为什么我觉得 Hermes 值得继续学

我现在并不觉得 Hermes 已经完美解决了 agent 自主进化。  
相反，我觉得它真正有价值的地方，是它已经把这个问题拆成了可研究、可修改、可扩展的若干工程部件。

它让“自主进化”不再只是一个抽象口号，而变成了一组可以逐个检查的问题：

- learning loop 在哪里触发
- 什么经验会进入 memory
- 什么经验会变成 skill
- 历史如何被重新取回
- 用户模型如何跨 session 持续加深
- 旧经验如何被 patch 而不是僵化

这也是我接下来继续研究这个项目时最想追踪的方向。

## 当前结论

如果只用一句话总结这篇文章，我会写：

`Hermes Agent 最值得学的，不是它会多少工具，而是它已经把 agent 自主进化做成了一个由 review、memory、skills、session retrieval 和 user model 共同组成的工程闭环。`

而对我来说，这个项目最大的启发也不是“如何做一个更能干的 agent”，而是：

`如何做一个会在长期运行中逐步变强的 agent。`

这才是我继续研究 Hermes 的原因。
