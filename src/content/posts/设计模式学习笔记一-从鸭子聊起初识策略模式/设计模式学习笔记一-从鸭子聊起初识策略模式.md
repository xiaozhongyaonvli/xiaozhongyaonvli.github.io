> AI 时代，写代码的时间被大大解放了，但我反而越来越觉得：花在 AI 交互文档和代码设计上的时间会更多。好的代码架构像艺术品一样，我希望通过系统学习设计模式，让自己写出来的代码（以及指挥 AI 写出来的代码）能更上一层楼。

## 为什么开始这一系列的学习？

AI 时代对程序员的冲击很大，需要去寻求破局之路。

我现在 vibe coding 几乎只讨论一个端到端的计划文档，看看需求、验收标准，自己的项目几乎不 view 代码了（view 了基本也不改哈哈）。但我一直在思考一个问题：

**程序员现在毫无疑问写代码的时间被大大解放了，那么省下来的时间到底应该花在哪？**

我自己的答案是：会有更多时间放到与 AI 交互的文档上。不仅要关注需求、关注是不是用户痛点，也需要花更多时间去思考更好的设计。感觉好的代码架构像艺术品一样，希望能通过学习设计模式来让自己的代码能力更上一层楼。

换个角度说，AI 越能写代码，"会写代码"这件事就越不值钱；但"知道什么是好代码、好架构"反而更值钱了——因为这是你能给 AI 立规矩、判断 AI 输出好坏的底气。

## OO 设计原则：先把地基打好

策略模式之前，先聊聊几个 OO 设计原则。这些原则是后面所有模式的"思想根基"，单独看似乎都很朴素，但放在一起就能解释为什么很多代码会越写越烂。

### 1. 单一职责原则

一个类只负责一件事。

我个人的理解是：**收敛职责范围，克制**。

这个原则我认为非常有效。不应该将代码都混在一起——一方面不利于人阅读理解和维护修改，另一方面 AI 读你的代码时如果一个类东一榔头西一棒槌，它也很难给出靠谱的修改建议。

### 2. 开闭原则

对扩展开放，对修改关闭。

经过验证的、可执行的模块，不应该去修改它的 core，除非必要。不然如果回归测试漏掉某些情况，可能会因为修改带来的新情况而导致异常。

但同时，模块的创立也不应该完全的固定死、完全不考虑未来的扩展。**留一些扩展点，是有益于长期项目发展的。**

### 3. 里氏替换原则

子类可以替换父类出现的位置，程序行为不受影响。

这是在用继承的语言里需要重点考虑的——一旦子类替换父类后行为发生了意料之外的变化，就说明继承关系设计得有问题。

### 4. 依赖倒置原则

高层模块不依赖低层模块，高层通过接口（抽象）而不是直接依赖具体实现。

我认为这是非常好的原则。**高内聚低耦合，是我经常给 AI 强调的一点。** 防腐层的设计能让你替换底层实现而不用修改高层模块——这一点在长期维护的项目里非常重要。

### 5. 接口隔离原则

不强迫类实现它不需要的方法，让类的职责清晰，不被相关功能污染。

这条和单一职责其实是一对孪生兄弟，只不过一个站在类的角度，一个站在接口的角度。

## 开始第一个模式：策略模式

这个模式之前没有系统学过。该说不说，我认为《Head First 设计模式》这本书讲解得非常易懂，它通过层层递进、不断改良的方式把一个模式自然推导出来，而不是上来就甩定义。

下面我按书里的演进过程梳理一遍。

### 场景设定

鸭子应用：游戏中有各种类型的鸭子，已经实现了一个鸭子超类，每种鸭子都继承这个超类。

现在需要对这个游戏进行改进——**注意，此时是新增需求，而不是设计游戏的时候，项目已经发售后了**。这点很重要，因为它决定了我们不能推倒重来，只能在已有结构上改。

需求：给鸭子加入"飞"这个功能。

### 初版：直接在超类上加飞功能

最直觉的做法：在超类 Duck 上加一个 `fly()` 方法，所有子鸭因为继承，都自动拥有了这个功能。

看起来很简洁，但问题马上就出现了：

- 不同类型的鸭子，飞行行为应该不同
- 有些鸭子（比如橡皮鸭）根本不应该会飞

**第一个经验：当设计维护时，为了复用而使用继承，并不是一个好办法。**

那如果采用覆盖呢？子鸭类对 `fly()` 进行重写覆盖——但如果出现有些鸭子不会飞，那么这里覆盖只能什么都不写不做，但仍然要保留这段空的重写代码。每加一种鸭子就要写一遍，重复且容易遗漏。

### 第二版：把飞行抽成接口

为了不每次新增鸭子种类就重写覆盖方法，想到了接口实现。

（其实这里基本就是我没学习前大概采用的方法了，我可能只能想到这层哈哈。）

把 `fly` 从鸭超类中提取出来，做成一个 `Flyable` 接口。会飞的鸭子实现这个接口，不会飞的就不实现。

但是对于 Java 而言，接口是没有代码实现的，意味着**每个实现这个接口的鸭子类都需要写一次实现，代码复用性没有**。两只飞行姿势相同的鸭子，要写两遍一模一样的飞行代码。

### 第三版：把变化的部分独立出来

书中在这里引入了一个非常关键的设计原则：

> **找出应用中可能需要变化的部分，把它们独立出来，不要和不需要变化的代码混在一起。**

我认为这是一个非常有意思的点，因为它关注的是代码后续维护性的工作，我觉得这可能是比较容易被忽视的地方。

具体怎么做？

把"飞行行为"抽象成一个接口 `FlyBehavior`，同时用一组实现类来对应不同的飞行行为：`FlyWithWings`、`FlyNoWay`、`FlyRocketPowered` 等。鸭子类里持有一个 `FlyBehavior` 类型的成员变量，把"怎么飞"这件事委托给具体的行为对象。

这背后用到的，是另一条更核心的设计原则：

> **针对接口编程，而不是针对实现编程。**

利用接口编程的关键就在于**多态**。利用多态，程序可以针对超类型编程——也就是说，变量的声明是超类型（一个抽象类或者一个接口），具体实现此超类型的类的对象都可以指定给这个变量。这意味着，声明类时不用理会以后执行的真正对象类型（**非常好的实现，将鸭和行为解耦**）。

再进一步，例如提供 `setFlyBehavior()` 方法，可以动态地修改这只鸭子对应的飞行行为，**而不局限于初始化时的指定**。一只原本不会飞的橡皮鸭，被赋予火箭引擎之后就能飞了——行为可以在运行时切换。

### 用一段伪代码看一下结构

```java
// 行为接口
public interface FlyBehavior {
    void fly();
}

// 一组行为实现
public class FlyWithWings implements FlyBehavior {
    public void fly() { /* 用翅膀飞 */ }
}
public class FlyNoWay implements FlyBehavior {
    public void fly() { /* 不会飞 */ }
}

// 鸭子超类：持有行为引用，把动作委托出去
public abstract class Duck {
    protected FlyBehavior flyBehavior;

    public void performFly() {
        flyBehavior.fly();
    }

    public void setFlyBehavior(FlyBehavior fb) {
        this.flyBehavior = fb;
    }
}
```

鸭子不再"自己会飞"，而是**持有一个会飞的对象，并把飞这件事委托给它**。这就是策略模式的核心结构。

## 策略模式的定义

> **定义了算法族，分别封装起来，让它们之间可以互相替换。此模式让算法的变化独立于使用算法的客户。**

把这个定义对照前面的鸭子例子来看就很清楚了：

- **算法族** = 一组飞行行为（`FlyWithWings`、`FlyNoWay`...）
- **分别封装** = 每一种行为都是一个独立的类
- **可以互相替换** = 通过 `setFlyBehavior()` 在运行时切换
- **算法的变化独立于使用算法的客户** = 加一种新飞法不用动鸭子类

## 我从这一章拿到的最大收获

我认为这个模式最好的思考是：

> **在设计系统时，就预先去想未来哪些地方可能需要变化，提前在代码中加入这些弹性。**

软件开发后的维护和更新可能占据更多的时间，相比于最初的开发。所以**不应只看到继承的代码复用性，而要考虑到提高可维护性和可扩展性上的"复用程度"**。

继承复用的是"代码"，策略模式复用的是"能力"——能力是可以被组合、替换、动态调整的，代码不能。

回头看 OO 设计原则，策略模式其实把好几条原则都用上了：

- **单一职责**：飞行行为和鸭子各自负责自己的事
- **开闭原则**：加新飞法不用改鸭子类
- **依赖倒置**：鸭子依赖 `FlyBehavior` 接口，而不是具体的飞行类
- **里氏替换**：任意一个 `FlyBehavior` 实现都能替换进去

这也是为什么这一章会被放在第一章——它不只是介绍了一个模式，更是用一个模式把前面几条设计原则串了起来。

## 一点延伸思考：策略模式和 AI 时代

写到这里我突然意识到一件事。

当我用 AI 写代码的时候，我经常会让它"加一种新逻辑/换一种实现方式"。如果底层结构是策略模式这种**面向接口、行为可替换**的设计，AI 改起来就特别顺：只需要新增一个实现类，不用动核心流程。

反过来，如果底层是一堆 if-else 嵌套加硬编码，AI 改起来要么改得磕磕绊绊，要么改完一堆潜在副作用。

所以**写出对 AI 友好的代码结构，本身就是 AI 时代的一种"工程能力"**。而设计模式，正好就是这种结构的语言。
