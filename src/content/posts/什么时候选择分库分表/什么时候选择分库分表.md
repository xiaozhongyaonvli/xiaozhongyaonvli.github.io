> 之前学分库分表的时候，看了很多文章上来就讲怎么分、ShardingSphere 怎么配，但很少有人认真讨论一个前置问题：**你真的需要分库分表吗？** 后来看到一篇叫 "Don't shard yet!" 的文章，才意识到分库分表应该是最后的手段，不是第一反应。这篇笔记把"什么时候该分"和"分之前该做什么"都整理一下。

## 先泼盆冷水：分库分表的代价

在聊"什么时候该分"之前，得先搞清楚分库分表要付出什么代价，不然你可能低估了这个决策的重量。

**一旦分了，几乎不可能再合回去。** 这是最大的风险。

具体代价：

- **跨库 JOIN 做不了** —— 以前一条 SQL 搞定的关联查询，分片后要应用层组装或者同步到 ES（我之前写过一篇跨库查询方案的笔记，有 7 种方案，每种都有各自的坑）
- **分布式事务** —— 跨分片的事务要用两阶段提交或 Saga 模式，复杂度直线上升
- **全局唯一 ID** —— 自增主键不能用了，得上雪花算法或者号段模式
- **数据迁移和扩容** —— 后续加分片意味着数据重新分布，这是个大工程
- **运维成本翻倍** —— 从管 1 个库变成管 N 个库，备份、监控、DDL 变更全部翻倍
- **开发心智负担** —— 每写一条 SQL 都得想"分片键带了没""会不会全分片扫描"

> 所以说分库分表不是"技术进步"，是**被逼无奈的妥协**。能不分就别分。

## 分库分表之前，先试这些方案

按照成本从低到高排序，我整理了一个"逐级升级"的路径。**每一级都应该在前一级用尽之后再考虑。**

### 第一级：SQL 和索引优化（成本最低）

这个说起来简单，但大部分性能问题其实都出在这里。

- **慢查询优化** —— 先 `EXPLAIN` 看执行计划，该加索引加索引，该改 SQL 改 SQL
- **避免全表扫描** —— 索引没命中、函数套在索引列上、隐式类型转换... 这些是常见坑
- **减少不必要的查询** —— N+1 问题、重复查询、返回了不需要的列

```sql
-- 反面例子：索引列上套函数，索引失效
SELECT * FROM orders WHERE DATE(create_time) = '2024-01-01';
-- 改成范围查询，索引就能用上了
SELECT * FROM orders WHERE create_time >= '2024-01-01'
  AND create_time < '2024-01-02';
```

很多时候加一个合适的联合索引，查询性能就能提升几十倍。**在索引没有优化到位之前，谈分库分表都是耍流氓。**

### 第二级：缓存

读多写少的场景，加一层 Redis 缓存能解决大部分读压力。

```
请求 → Redis（命中直接返回） → 没命中才查数据库
```

热点数据缓存命中率能到 90%+，数据库的压力直接降一个数量级。Twitter 那种场景 —— 一条推文写入一次但被读取上百万次 —— 缓存就是最好的方案，根本不需要分库分表。

### 第三级：读写分离

如果读是瓶颈（大部分 Web 应用都是），主从复制 + 读写分离就很好使：

```
写请求 → Master（单点写入）
读请求 → Slave-1 / Slave-2 / Slave-3（多点读取）
```

配置简单，主流框架都支持（ShardingSphere、MyCat 都能做），对应用代码的侵入也很小。

**局限性**：主从延迟（毫秒级），不适合写入后立刻读取的场景。而且只能缓解读压力，**写瓶颈解决不了** —— 写还是只走 Master 一个节点。

### 第四级：垂直拆分（分库但不分表）

把一个大而全的数据库按业务域拆成多个独立的库：

```
ALL-IN-ONE DB
  → user_db（用户相关的表）
  → order_db（订单相关的表）
  → product_db（商品相关的表）
  → payment_db（支付相关的表）
```

每个业务域的数据库独立部署、独立扩展。这本质上是微服务拆分在数据库层面的体现。

垂直拆分的好处是每个库的规模变小了，而且不同业务之间的读写不互相影响。但它**没有解决单表数据量过大的问题** —— 如果 orders 表本身有 5 亿行，拆到单独的 order_db 里它还是 5 亿行。

### 第五级：表分区（Partitioning）

MySQL 自带的分区功能，**在单库内把大表切成小段**：

```sql
CREATE TABLE orders (
    id BIGINT,
    user_id BIGINT,
    create_time DATETIME,
    ...
) PARTITION BY RANGE (YEAR(create_time)) (
    PARTITION p2022 VALUES LESS THAN (2023),
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p_future VALUES LESS THAN MAXVALUE
);
```

查询带上分区键时，MySQL 只扫描相关分区，不用扫全表。

跟分库分表比起来，分区的最大好处是**对应用完全透明** —— SQL 不用改，还是一张逻辑表。但它有天花板：还是单机，CPU、IO、连接数这些瓶颈解决不了。

### 第六级：异构存储

不是所有查询都适合用 MySQL 来扛。把不同类型的查询分流到适合的存储引擎：

| 查询类型 | 推荐存储 |
|---------|---------|
| 复杂搜索、全文检索 | Elasticsearch |
| 实时分析、聚合报表 | ClickHouse / Doris |
| 时序数据、监控日志 | InfluxDB / TDengine |
| 冷数据归档 | HBase / 对象存储 |

比如把历史订单归档到 ClickHouse 做分析，MySQL 只保留最近 3 个月的热数据，表立刻小了很多。

**这一步往往能延缓分库分表很长时间。** 很多时候"表太大"不是因为热数据真的那么多，而是冷数据一直堆在那没清理。

### 第七级：硬件升级（垂直扩展）

简单粗暴但有效：升 CPU、加内存、换 SSD、上更高带宽的网络。

不要小看这个方案 —— 一台 64核 256GB 内存、NVMe SSD 的机器能扛的数据量和并发超乎想象。而且**硬件升级的成本通常远低于分库分表的工程成本**。

当然，硬件升级有天花板。当你已经用了市面上能买到的最好配置，还是撑不住，那就该考虑分库分表了。

## 真正该分库分表的信号

上面这些手段都试过了，还是顶不住 —— 这时候才该认真考虑分库分表。具体的信号：

### 信号一：单表行数过大

> MySQL 的 B+ Tree 索引，一般 3~4 层能支撑的数据量在**几千万行**左右。超过这个量级，即使有索引，查询性能也会明显下降。

经验值（不是绝对的，跟表结构、查询模式有关）：

| 数据量级 | 建议 |
|---------|------|
| 千万以内 | 单表完全没问题 |
| 千万到五千万 | 开始关注，优化索引和查询 |
| 五千万到一亿 | 认真考虑分表 |
| 一亿以上 | 基本上得分了 |

（这些数字是 MySQL InnoDB 的经验值。如果字段少、行短，单表撑到一亿也有可能；如果字段多、有大文本列，几百万行就可能变慢）

### 信号二：写入瓶颈

读的问题可以靠缓存 + 从库解决，但**写入只能走主库**。如果单库的写 TPS 已经到了极限（MySQL 一般在几千到一两万 TPS，取决于硬件和事务复杂度），加从库也没用，只能分库。

常见场景：高并发秒杀、IoT 设备上报、支付系统...

### 信号三：连接数打满

MySQL 的 `max_connections` 有上限（默认 151，生产一般设几百到几千）。微服务架构下几十个服务实例都连同一个库，连接数很容易打满。连接池只是缓冲，根本问题还是一个库要服务太多消费者。

### 信号四：磁盘容量

单机磁盘的上限总会到。数据量增长到磁盘装不下，或者 IO 带宽成为瓶颈，就得考虑把数据分散到多台机器。

### 信号五：硬件升级已到顶

已经用了能买到的最好的机器，还是扛不住。这是最明确的信号 —— 垂直扩展到头了，只能水平扩展。

## 分库 vs 分表 vs 既分库又分表

这几个概念容易搞混，整理一下：

**只分表不分库**：数据还在同一个数据库实例里，只是从一张大表拆成多张小表（比如 orders_0, orders_1, ... orders_99）。解决的是**单表数据量过大**的问题（索引太大、查询变慢）。但 CPU、内存、连接数这些单机瓶颈还是没解决。

**只分库不分表**：数据分散到多个数据库实例。解决的是**单机性能瓶颈**（CPU/IO/连接数），但如果每个库里还是一张大表，单表问题还在。

**既分库又分表**：两个问题一起解决。最常见的做法。

```
什么时候只分表不分库？
  → 单表太大（几千万到上亿行），但单机性能还够用

什么时候只分库不分表？
  → 按业务域拆分（垂直分库），每个业务的表不算大

什么时候都分？
  → 数据量大 + 并发高，两个瓶颈都遇到了
```

## 一个简单的决策流程图

```
数据库性能有问题了？

  SQL 和索引优化了吗？ → 没有 → 先优化
  热数据加缓存了吗？ → 没有 → 加 Redis
  读是瓶颈？ → 是 → 读写分离 + 从库
  表太大查询慢？ → 是 → 先试分区 / 归档冷数据
  特定查询模式很慢？ → 是 → 异构存储（ES/ClickHouse）
  硬件还能升级吗？ → 能 → 升配置
  以上都做了还是扛不住？
    单表数据量过大 → 分表
    单机性能打满 → 分库
    都有 → 分库 + 分表
```

## 面试怎么答这个问题

> 分库分表应该是数据库优化的最后手段，不是第一选择。在分之前，应该先把 SQL 和索引优化做到位，该加缓存加缓存，读压力大就读写分离，单表大就先试分区或冷数据归档，特定查询瓶颈可以用 ES 或 ClickHouse 做异构存储。
>
> 真正需要分库分表的信号是：单表行数到了几千万甚至上亿，索引优化后查询还是慢；或者单机的写入 TPS 到了极限，加从库也没用因为写只走主库；或者连接数打满了，硬件也升到顶了。
>
> 具体是分库还是分表，看瓶颈在哪 —— 单表数据量大就分表，单机性能不够就分库，通常两者一起做。但分库分表的代价很大：跨库 JOIN、分布式事务、全局 ID、数据迁移这些问题全部会冒出来，一旦分了几乎不可能合回去，所以这个决策要非常谨慎。

---

## 小结

分库分表的决策本质上是一个**成本收益分析**：分了之后确实能解决容量和性能问题，但引入的复杂度是永久性的。能用更简单的方案解决就用更简单的方案，只有当所有"更便宜"的手段都用尽了，再考虑这一步。面试里把这个思路讲清楚，比直接背分库分表的方案更有说服力。
