> 最近在搞知识库相关的项目，RAG 这个词天天见，但仔细想想发现自己理解得还挺模糊的。花了点时间把概念、流程、和评估方法捋了一遍，记录一下。

## 先说 RAG 是啥

RAG，全称 Retrieval-Augmented Generation（检索增强生成），2020 年由 Meta 的 Lewis 等人在论文里正式提出的。

一句话解释：**让大模型在回答问题之前，先去外部知识库里查一查相关资料，然后带着这些资料再生成回答。**

打个比方的话——普通的 LLM 回答问题就像闭卷考试，全靠训练时候"背"下来的东西；而 RAG 就是开卷考试，允许你翻书、查笔记，然后再作答。

为什么需要这个东西？因为纯靠大模型自己回答有几个硬伤：

- **知识有截止日期**。模型训练完之后，新发生的事情它不知道
- **会"一本正经地胡说八道"**（Hallucination / 幻觉），编得跟真的一样
- **企业私有数据它接触不到**，比如内部文档、业务数据

RAG 就是来解决这些问题的——在生成之前加一个"检索"步骤，让模型有据可依。

## RAG 的工作流程

一个标准的 RAG 流程大致分四步：

### 1. Ingestion（数据摄入）

把你的知识库文档切块 → 用 Embedding 模型转成向量 → 存到向量数据库里。

```
原始文档 → 文本分块（Chunking）→ Embedding → 向量数据库（如 Pinecone、Milvus）
```

这里有个细节要注意：**分块策略（Chunking Strategy）很关键**。块太大了，检索出来的内容噪音多；块太小了，上下文信息容易断裂。我见过有人按固定 token 数切的，也有按段落语义切的，得根据实际数据调。

### 2. Retrieval（检索）

用户提问进来，先把问题也转成向量，然后去向量数据库里做相似度搜索，找出最相关的 top-k 个文档块。

```
用户问题 → Embedding → 在向量库中做 ANN 搜索 → 返回 top-k 相关文档
```

> 这里比较推荐用混合检索（Hybrid Search），既做语义匹配（dense vector）又做关键词匹配（sparse vector / BM25）。尤其是遇到专有名词、缩写这类东西，纯语义搜索经常不太行，加上关键词匹配会好很多。

### 3. Augmentation（增强）

把检索到的文档块拼到 prompt 里，跟用户的原始问题一起喂给大模型。

```
SYSTEM: 你是一个知识助手，请根据以下参考资料回答用户问题。如果资料中没有相关信息，请说明。

CONTEXT:
{检索到的文档块1}
{检索到的文档块2}
...

USER: {用户的问题}
```

### 4. Generation（生成）

大模型根据增强后的 prompt 来生成回答。因为有了外部知识的"加持"，回答通常会更准确、更有据可依。

整个流程一张图：

```
用户提问 → Query Embedding → 向量检索 → Top-K 文档块
                                              ↓
                                    构建增强 Prompt
                                              ↓
                                      LLM 生成回答
```

## 跟传统"检索 + 模型生成"有啥不同？

可能有人会问：以前搜索引擎不也是先检索、再展示结果吗？加个大模型总结一下不就行了？RAG 有什么特别的？

这个问题刚开始我也搞混过，仔细对比了一下发现区别还是挺大的：

| | 传统检索 + 生成 | RAG |
|---|---|---|
| **检索方式** | 关键词匹配为主（TF-IDF、BM25） | 语义检索为主，支持混合检索 |
| **理解能力** | 字面匹配，不理解语义 | 能理解问题的"意思"，匹配更准 |
| **生成质量** | 要么直接返回文档片段，要么用简单模板拼接 | LLM 理解上下文后生成自然语言回答 |
| **数据来源** | 通常是结构化索引 | 可以是各种非结构化数据（PDF、文档、网页等） |
| **回答形式** | 返回文档列表/摘要 | 直接给出整合后的答案 |
| **幻觉控制** | 不存在幻觉（因为不"生成"） | 有幻觉风险，但通过检索接地来降低 |

再具体说一下核心差异：

**1. 检索维度不同**

传统检索本质上是"词袋匹配"——你问"怎么解决 OOM"，它只会去找包含 "OOM" 这个关键词的文档。而 RAG 做的是语义级检索，即使文档里写的是"内存溢出排查方法"，照样能匹配上。

**2. 生成方式完全不同**

传统方式最多做个摘要抽取（extractive），把文档里的原句抠出来展示。RAG 的生成是理解式的（abstractive），大模型会综合多个文档的信息，用自己的话重新组织答案。

**3. RAG 天然支持多轮对话**

传统检索基本是一问一答，没有上下文概念。RAG 架构下，你可以把对话历史也放进 prompt 里，实现连贯的多轮问答。

（不过也不是说 RAG 就完美了，它也有自己的坑，后面评估那块会提到）

## 怎么评价一个 RAG 系统是否 work？

这块是我觉得最实用的部分了。做出一个 RAG 不难，但怎么知道它到底好不好？

核心思路：**分开评估检索和生成两个环节**，不要只看最终输出。因为最终答案不好，可能是检索没召回对的文档，也可能是检索到了但模型没用好，得定位问题出在哪。

### 检索质量评估

检索环节关心的是：**找回来的文档到底相不相关？有没有遗漏？**

几个关键指标：

- **Precision@k（精确率）**：检索回来的 top-k 文档里，有多少是真正相关的。比如取 top-10，其中 7 个相关，Precision@10 = 0.7
- **Recall@k（召回率）**：所有相关文档中，你检索回来了多少。如果知识库里有 10 个相关文档，你只召回了 6 个，Recall = 0.6
- **MRR（Mean Reciprocal Rank）**：第一个相关文档出现在第几位？排名越靠前越好
- **nDCG（归一化折损累积增益）**：不仅看相不相关，还看相关文档的排序是否合理

> 我个人觉得对于大多数 RAG 场景，最值得关注的是 **Recall** 和 **Precision 的平衡**。Recall 太低说明该找到的没找到（答案不完整），Precision 太低说明塞了太多无关内容进 prompt（可能干扰生成）。

### 生成质量评估

生成环节关心的是：**模型的回答是否准确、忠实于检索结果、并且切题？**

几个核心指标：

- **Faithfulness（忠实度）**：回答有没有编造检索结果里不存在的内容？这个指标直接衡量幻觉程度
- **Answer Relevancy（答案相关性）**：回答是否真正回答了用户的问题？有些模型回答得很长但答非所问
- **Contextual Precision（上下文精确度）**：传给模型的上下文中，相关信息的排序是否合理？
- **Contextual Recall（上下文召回率）**：要生成理想答案所需的信息，在检索结果中是否都包含了？

### 实际怎么做评估？

目前业界主流两种路子：

**方法一：有标准答案的评估（Reference-based）**

事先准备一批"问题 - 标准答案"对（Gold Standard Dataset），然后拿 RAG 的输出跟标准答案比。可以用 BLEU、ROUGE、BERTScore 这些 NLP 指标。

**方法二：用 LLM 当评委（LLM-as-a-Judge）**

没有标准答案的时候，可以用另一个 LLM 来打分。比如让 GPT-4 评估回答的忠实度、相关性等。RAGAS 和 DeepEval 这两个开源框架就是干这个的。

用 DeepEval 做评估的代码大概长这样：

```python
from deepeval.metrics import ContextualRelevancyMetric
from deepeval.test_case import LLMTestCase

metric = ContextualRelevancyMetric(
    threshold=0.7,
    model="gpt-4"
)

test_case = LLMTestCase(
    input="什么是向量数据库？",
    actual_output="向量数据库是专门用于存储和检索高维向量数据的数据库系统...",
    retrieval_context=["向量数据库的定义和用途...", "常见向量数据库对比..."]
)

metric.measure(test_case)
print(f"Score: {metric.score}")  # 0.0 ~ 1.0
print(f"Reason: {metric.reason}")
```

### 几个实用建议

1. **一定要在项目早期就建评估数据集**，不然后面改一个参数都不知道是变好了还是变差了
2. **改东西的时候一次只改一个变量**——换了个 Embedding 模型，就别同时改 chunk size，不然分不清效果归因
3. **不要只看自动化指标，人工抽检也很重要**。有些幻觉很隐蔽，自动指标不一定能抓到
4. **别忘了安全测试**——prompt 注入、敏感数据泄露这些，评估的时候也要考虑

> Google 在 ICLR 2025 上发了一个挺有意思的发现：RAG 虽然整体上提升了回答质量，但反而降低了模型"拒绝回答"的能力。就是说加了检索上下文之后，模型会变得更"自信"，即使信息不足也倾向于硬答，而不是说"我不确定"。这个挺值得注意的，意味着你的 RAG 系统可能需要额外加一个"充分性检查"模块。

## 小结

RAG 的核心价值就是让大模型从"全凭记忆"变成"有据可查"，这个思路本身挺直觉的。但实际做起来，检索质量、分块策略、prompt 工程、评估体系这些每个环节都有坑要踩。最关键的一点：**不要只盯着最终回答看，要把检索和生成拆开来分别评估，才能定位问题出在哪里。**
