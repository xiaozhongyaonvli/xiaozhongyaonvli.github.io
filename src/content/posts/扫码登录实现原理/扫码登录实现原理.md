> 这个问题面试里出现频率挺高的，尤其是中大厂。核心考察的其实是你对**多端协作**、**状态同步**和**轮询/长连接**这些东西的理解。

## 先搞清楚三个角色

扫码登录这件事，绕来绕去就三个角色：

- **PC 端（Web 浏览器）**：想要登录的那个
- **手机端（APP）**：已经登录了的那个
- **服务端**：负责校验和传递数据的中间人

一句话概括：**用手机上已有的登录态，帮 PC 端完成认证**。说白了就是"借身份"。

## 整体流程 — 三个阶段

我理解这个流程其实可以拆成三个阶段来看，每个阶段各端的职责很明确。

### 阶段一：待扫描

```
PC端 ——请求生成二维码——> 服务端
PC端 <——返回二维码ID+二维码图片—— 服务端
```

1. 用户在 PC 打开登录页
2. PC 端向服务端请求生成一个**二维码**
3. 服务端生成一个**全局唯一的 uuid**（作为这次扫码登录会话的标识），存到 Redis 里，设置过期时间（一般 2~5 分钟）
4. 把这个 uuid 编码成二维码返回给 PC 端展示
5. PC 端**开始轮询**，不断问服务端："这个 uuid 有人扫了没？"

（这里有个细节：uuid 一定要有过期时间，不然恶意用户截图保存二维码，以后随时能用，就有安全问题了）

### 阶段二：已扫描，待确认

```
手机APP ——扫码获取uuid——> 二维码
手机APP ——发送uuid + APP token——> 服务端
服务端 ——返回临时token——> 手机APP
```

1. 用户用 APP 扫二维码，解析出 uuid
2. APP 把 uuid 和自己的**登录凭证（token）**一起发给服务端
3. 服务端收到后：
   - 校验 APP 的 token 是否有效
   - 把 uuid 和用户信息**关联**起来（存 Redis）
   - 把二维码状态改为"已扫描"
   - 生成一个**临时 token** 返回给 APP（用于后面确认操作）
4. 此时 PC 端轮询发现状态变了，页面可以显示"xxx 已扫码，请在手机上确认"

> 为什么要生成临时 token？因为确认登录是第二步操作，需要一个凭证来证明"确认的人就是刚才扫码的人"，防止别人伪造确认请求。

### 阶段三：确认登录

```
手机APP ——携带临时token，确认登录——> 服务端
服务端 ——更新二维码状态为"已确认"——> Redis
PC端轮询 ——发现已确认——> 服务端返回PC端的token
```

1. 用户在 APP 上点"确认登录"
2. APP 带着临时 token 请求服务端
3. 服务端校验临时 token，通过后：
   - 更新二维码状态为"已确认"
   - 为 PC 端生成正式的**登录 token**
4. PC 端下次轮询时拿到这个 token，登录成功，跳转到首页

整个流程走完了。其实理解了就不复杂，**核心就是通过一个 uuid 把三端串起来**。

## PC 端怎么知道状态变了？

这块是面试官经常追问的点，有几种方案：

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| **短轮询** | 每隔 1~2 秒发一次 HTTP 请求 | 实现简单，但浪费资源，大量无效请求 |
| **长轮询** | 发请求后服务端 hold 住，有变化再返回 | 比短轮询省资源，但服务端要维护连接 |
| **SSE** | 服务端单向推送 | 天然适合这种场景，单向通知就够了 |
| **WebSocket** | 双向通信 | 功能最强但有点杀鸡用牛刀了 |

我觉得实际项目中**长轮询**或者 **SSE** 是比较合理的选择。短轮询太浪费，WebSocket 这个场景有点重了。

## 简化版代码思路

服务端的核心接口大概就这几个：

```java
// 1. 生成二维码
@GetMapping("/qrcode/generate")
public QrCodeVO generateQrCode() {
    String uuid = UUID.randomUUID().toString();
    // 存Redis，设置过期时间
    redis.set("qr:" + uuid, "WAITING", 300, TimeUnit.SECONDS);
    // 生成二维码图片（内容就是这个uuid，或者一个包含uuid的URL）
    String qrImageBase64 = QrCodeUtil.generate(uuid);
    return new QrCodeVO(uuid, qrImageBase64);
}

// 2. 轮询二维码状态
@GetMapping("/qrcode/check")
public QrCodeStatusVO checkQrCode(@RequestParam String uuid) {
    String status = redis.get("qr:" + uuid);
    if (status == null) return QrCodeStatusVO.expired();
    if ("CONFIRMED".equals(status)) {
        // 取出关联的用户信息，生成PC端token
        String pcToken = generatePcToken(uuid);
        return QrCodeStatusVO.success(pcToken);
    }
    return QrCodeStatusVO.of(status); // WAITING 或 SCANNED
}

// 3. APP扫码
@PostMapping("/qrcode/scan")
public TempTokenVO scanQrCode(@RequestParam String uuid,
                               @RequestHeader("Authorization") String appToken) {
    // 校验APP token，拿到用户信息
    UserInfo user = validateAppToken(appToken);
    // 关联用户和uuid
    redis.set("qr:" + uuid, "SCANNED");
    redis.set("qr:user:" + uuid, user.getId());
    // 返回临时token
    String tempToken = generateTempToken(uuid);
    return new TempTokenVO(tempToken);
}

// 4. APP确认登录
@PostMapping("/qrcode/confirm")
public void confirmLogin(@RequestParam String tempToken) {
    // 校验临时token，拿到uuid
    String uuid = validateTempToken(tempToken);
    redis.set("qr:" + uuid, "CONFIRMED");
}
```

（这只是核心逻辑的简化版，实际生产中还要考虑很多边界情况）

## 安全方面要注意的

这块面试也可能会问到：

- **二维码要设置过期时间**，一般 2~5 分钟，过期后前端要自动刷新
- **临时 token 一次性使用**，确认完就失效
- **HTTPS 传输**，防止中间人拦截 uuid 或 token
- **APP 扫码时要校验来源**，确认这个二维码确实是自家服务端生成的，防钓鱼
- 可以加入**设备指纹**或者 **IP 校验**做风控，比如扫码的手机和 PC 不在同一个城市就触发二次验证

> 这里有个容易忽略的点：二维码里最好不要直接放 uuid 明文，而是放一个加密后的字符串或者一个短链接 URL，APP 通过这个 URL 去服务端获取实际的会话信息。这样即使二维码被截图了，别人也没法直接伪造请求。

## 面试怎么答

如果面试被问到这个题，我觉得可以按这个思路来：

1. **先说三个角色**：PC、APP、服务端
2. **再说三个阶段**：待扫描 → 已扫描待确认 → 已确认
3. **画个时序图**（如果有白板的话），把请求流向标清楚
4. **提一下轮询方案**的选择（长轮询/SSE）
5. **最后聊安全**：过期时间、临时 token、HTTPS、防钓鱼

能把这几点讲清楚，基本上没什么问题了。

## 小结

扫码登录说到底就是"已登录的端帮未登录的端完成认证"，通过一个 uuid 把多端串起来，配合状态机（待扫描→已扫描→已确认）来推进流程。理解了本质，具体实现就是 API 设计 + Redis 存状态的事儿了。
